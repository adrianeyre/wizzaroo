# Sessions and syncing

[← Back to the README](../../README.md) · [All guides](README.md)

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

A Family Device never sends the server its state, only events, and the server alone works out what they add up to. The events are **Session started**, when a Child opens their Character, **Session ended**, when they tap **Finish playing** (from the Menu on the World Map, or its own button anywhere else), while they play a Mission, **Question answered** and **Activity finished**, and, in the wardrobe, **Item bought**, **Character dressed**, **Outfit saved** and **Outfit worn**, and, in the Room, **Room furnished**. Hiding the game, by switching app, locking the tablet or closing the tab, ends the Session too, and coming back to it starts a new one, so time the game sits unseen never counts.

- **The outbox.** Each event goes into an IndexedDB outbox on the device, `wizzaroo-play-event-outbox`, with an ID the device makes (`crypto.randomUUID`) and the time by the device's clock. Events are only ever added to it, and a batch leaves it only once the server has taken it, so Sessions played with no network wait there.
- **Syncing.** The device uploads up to 100 events at a time to `POST /api/play/events`: after each event, whenever the game page opens, when the browser comes back online, and every minute, which catches the home server or the tunnel coming back while the network stayed up. Anything the server doesn't take stays waiting for the next try. A device the server answers 401, as when its Family has been deleted or a Parent has signed it out, lets go of everything waiting in its outbox and of its unsynced play, since nothing there would ever be taken. A device the server answers 409, because some events' IDs are already other events', gives each event it names a new ID (`crypto.randomUUID`), moves the play it shows onto the new IDs, and sends the batch again at once, so no play is lost; after three such answers in a row it leaves the batch for the next try.
- **Storing.** Uploading is idempotent: an event already stored by the Family with the same body is skipped, so uploading the same batch twice stores each event once. An ID is bound to its owner and its body: an event whose ID is already stored for another Family, or for this one with another child, type, time or payload, or that one batch sends twice with different bodies, is refused with `409` and `{"takenPlayEventIds": [...]}`, and nothing in the batch is stored. `play_events` keeps each event with the Family Device and the Family taken from the device's credential, the device's time (`happened_at`) and when the server received it (`received_at`). An event naming a Child who isn't in the device's Family, as when the Child was deleted after the device played, or a gift for one, is let go and the rest of the batch is stored, so one deleted Child doesn't hold up their siblings' play. The server then answers `200` with how many events it let go (`{"letGoPlayEventCount": 1}`) and names no Child, so a Child deleted from the Family and one that was never in it are answered exactly alike; with nothing let go it answers `204`. Either way the device forgets the batch. The server lets go the same way of an event it can't stand behind ([ADR 0004](../architectural-decision-record/0004-offline-play-records-events-the-server-decides.md#what-the-server-sets-aside)): one that happened, by the device's clock, more than an hour after the server received it or more than 400 days before, the time a Family Device lasts unused; one whose local date is later than the UK's tomorrow or more than 401 days before its today; and a finished Check with more questions than its paper asks, or a right answer given in under 200 ms. A Check History lists the latest Check finished first, by its time, and never later than when the server received it. A batch holding an event whose time falls before year 1 or after year 9999, which Postgres can't hold, or a number that isn't finite, such as `"secondsSpent": "Infinity"`, is refused whole with a 400, and nothing in it is stored ([security](security-and-backups.md#numbers-and-dates-postgres-cant-hold)). Postgres holds the same rule for every writer: a `play_events` row's Child must be one of the row's Family's, through a foreign key on (`child_id`, `family_id`) and the reach's policy, so a query that skips the API's check still can't put play into another Family's Child's progress. Each stored batch also refreshes `room_showcases`: for each of the Family's Children, only what a Classmate may see (the Character's look, the Room and its Trophies). A Family Device reads a Classmate's row only through `wizzaroo_can_visit_classmate_room`, which needs both Children's Parents to have turned Classmate visits on, the same School, which the Admin has approved for Classmate visits, the same Year, and different Families ([ADR 0031](../architectural-decision-record/0031-classmates-can-see-each-others-rooms.md)).
- **Time spent.** The **Children** panel shows each Child's time spent playing, which the server works out from the events whenever the dashboard asks: each Session from its start to its end, by the device's clock, added together. A Session counts once its end has arrived, and one that ends before it starts, as when a device's clock is put back, counts as nothing. One Session counts for no more than a day, however far apart the device's clock put its start and end, and the total is added up in a number no amount of play overflows, so one Child's clock can never stop a Teacher's or the Admin's list answering. Play on a device that had no network appears once that device has synced.
