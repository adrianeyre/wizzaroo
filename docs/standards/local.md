# Local standards

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

How Wizzaroo's toolchain, layout and deployment differ from the estate setup it started from, and why: Wizzaroo is a self-hosted family app, not an AWS service.

| `pr-checks.yml` runs the build, typecheck, lint, Prettier and tests, and nothing else | It also runs two dependency jobs: `dependency-advisories` (`pnpm audit`) and `dependency-review` (GitHub's dependency review action), each failing at the level below. `dependency-review` runs only while the repository is public, since GitHub refuses it (`403`) on a private repository without Advanced Security. A third workflow, `scheduled-audit.yml`, runs the same `pnpm audit` every day, and `island-sweeps.yml` runs the Island sweeps (`pnpm test:sweeps`) every day, too slow for every pull request. A fourth, `release.yml`, runs only when a pull request is merged into `main`: semantic-release reads the conventional commits since the last tag, and for a `feat`, `fix`, `perf` or breaking change sets `package.json`'s `version`, commits it to `main` as `chore(release): X.Y.Z [skip ci]` (`@semantic-release/exec` and `@semantic-release/git`), tags that commit `vX.Y.Z` and makes a GitHub Release from them. It never publishes to npm. `main`'s ruleset blocks only deletion and force pushes, so its `GITHUB_TOKEN`, with `contents: write`, can push the release commit, and a push by the `GITHUB_TOKEN` starts no workflow. `@semantic-release/npm` isn't used, since `npm` refuses to run in a repository whose `devEngines` names pnpm. The footer's version is the highest `vX.Y.Z` tag, read from `.git`'s tag files at build time (`src/release-version.ts`), or `development` without one, and links to the GitHub Releases. Every action in every workflow is pinned by full commit SHA, with its release in a comment beside it, and `.github/dependabot.yml` proposes updates to the `npm` packages and the `github-actions` pins, daily | A package with a known advisory fails the pull request that brings it in, and one published after it is merged fails the next day's scheduled audit rather than an unrelated pull request (#334). `pnpm audit` reads `pnpm-lock.yaml`, so it sees the whole tree; GitHub's dependency graph reads manifests and can miss most of a pnpm tree, so dependency review is a second view, not the gate, and not a required check on `main`. A tag can be moved by its publisher, so a SHA is the pin and Dependabot is what moves it (#333) |

## Dependency advisories

The level is **`high`**: a high or critical advisory against any package in `pnpm-lock.yaml`, production or development, fails the pull request. Moderate and low advisories are counted in the `dependency-advisories` job's log and don't fail it; `pnpm audit` with no level lists them.

- Development packages count, because they run in CI and build the image.
- `moderate` was turned down: most moderate advisories in a JavaScript tree are denial-of-service in development tooling, often fixed only in a new major of a tool's own dependency, and a check that is red on every pull request stops being read.
- The level is written in three places: `pnpm audit --audit-level=high` and the dependency review's `fail-on-severity: high` in `.github/workflows/pr-checks.yml`, and `pnpm audit --audit-level=high` in `.github/workflows/scheduled-audit.yml`. All three change with this section, in one commit.
- An advisory that can't be fixed is waived only with the owner's written reason in an issue, by its GHSA id in `auditConfig.ignoreGhsas` in `pnpm-workspace.yaml` and in the dependency review's `allow-ghsas`.
