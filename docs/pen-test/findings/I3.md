# I3: Secrets and fail-closed configuration

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #222 (I3), which answers the configuration half of [H13](../../product-requirements-document/pen-testing.md#h13-secrets-and-containers-are-fail-closed-but-not-hardened--medium): missing and weak variables, `SMTP_SECURE` and the tunnel token. The containers half (image digests, `read_only`, `cap_drop`, `no-new-privileges`, the `restore-drill`'s `trust`, the B2 key and Object Lock) is I4's. This note names exploit chains, so it is kept private on the same terms as the PRD.

- **Trust boundary:** the configuration the server and its containers start from. Section 9 of `wizzaroo.md` ("Hosting") keeps the secrets in a `.env` kept out of git: the database password, the tunnel token and the SMTP credentials. Its "Email" section sends password resets, Invites, address checks and security notices through an SMTP provider set in `.env`. [ADR 0002](../../architectural-decision-record/0002-self-hosted-behind-a-cloudflare-tunnel.md) puts the tunnel in front of the app with no Cloudflare Access, so Wizzaroo's own sign-in, and the reset links that email carries, are the only gate.
- **Code:** `src/server/config/vars.ts` (the one reader of the environment), `src/server/index.ts` (the composition root that loads it, opens the database and builds the SMTP transporter), `src/server/email/send-email.ts` (the transporter), `docker-compose.yml` (the production stack and its `${…:?}` and `${…:-}` interpolations) and `.env.example`.
- **Documented behaviour:** [Email](../../guide/email.md), [Development](../../guide/development.md) and [deploying to the home server](../../processes/deploying-to-the-home-server.md), whose `.env` table asks for `openssl rand -hex 32` as the database password.
- **Probes:** the `pen test I3: secrets and fail-closed configuration` block in `src/integration.test.ts`, in the gated run against a real Postgres. A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now. A refuted probe is a passing test. The probes take three shapes:
  - **Booting the server.** Each boot spawns the real composition root, `node --import tsx src/server/index.ts`, with an environment of the probe's choosing and nothing else from the test's, on a free port, against the suite's Postgres container. A boot has **started** when `GET /health` answers 200, and was **refused** when the process exits first. For a weak database password, the probe makes a login role with that password (`i3_one_character_password`, `x`; `i3_whitespace_password`, three spaces), a superuser as the production app's user is (H4), and drops both afterwards.
  - **Sending email.** An SMTP stand-in on `127.0.0.1` that offers `AUTH PLAIN` and no `STARTTLS`, as a server would whose `STARTTLS` line an on-path attacker had stripped, records every byte it is sent. The probe builds the server's mail sender exactly as the composition root does, `createSmtpTransporter(loadVars().smtp)`, and asks for a reset link for a confirmed Parent of its own (`i3-reset-probe@example.com`).
  - **Reading Compose.** `docker compose --profile tunnel config` on `docker-compose.yml` alone, as production runs it, with an empty env file so a developer's `.env` can't leak in and the probe's variables passed exactly. Every value is a placeholder. These need `docker compose`, and are skipped loudly without it.

H13's configuration half is **confirmed**. Missing variables fail closed, as H13 says. Weak ones don't: the server and Compose ask only whether a secret is empty. A secret of one character or of spaces, the development values and an empty tunnel token all start, with no warning. `SMTP_SECURE=false` is the one weak setting with a direct consequence: it sends reset links, and the provider's key, wherever the network lets them go in plain text. H13's "Compose uses `:?` for every secret" is refuted for the tunnel token, which is `:-`.

## Unsetting each variable: refuted

`vars.ts` reads nine variables. `required()` throws `<NAME> must be set` when a variable is missing or empty, and the composition root loads the variables before it touches the database, so the process exits with that message and never listens.

- **Required.** The probe boots the server five times, with `DATABASE_URL`, `PUBLIC_URL`, `SMTP_HOST`, `SMTP_USERNAME` and `SMTP_PASSWORD` each left out in turn. Each is refused, and its standard error names the variable.
- **Optional.** `SMTP_PORT`, `SMTP_SECURE` and `SECOND_SCHOOL_GATE_MET`, each left out in turn, start the server. `loadVars` with those three and `PORT` unset gives port 465, TLS, the gate shut and port 4310. Each default is the safe one, so leaving a variable out never opens anything. `PORT` is read in-process rather than booted, so the probe never binds 4310 on the host.
- **Compose.** `docker-compose.yml` refuses `POSTGRES_PASSWORD`, `SMTP_HOST`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `BACKUP_AGE_RECIPIENT`, `BACKUP_RCLONE_REMOTE`, `BACKUP_RCLONE_OFFSITE_REMOTE` and `BACKUP_RCLONE_CONFIG_FILE`, each left out in turn, with its `:?` message naming it. `SMTP_PORT`, `SMTP_SECURE` and `SECOND_SCHOOL_GATE_MET` reach the app empty, which it reads as unset. `BACKUP_KEEP_NIGHTS` and `BACKUP_HOUR_UTC` reach the backup as 30 and 2. The backup's own script refuses its four required variables again with `:?` (`backup/backup.sh`), read and not run.

Tests:

- `refuses to start without each variable it requires, naming it`
- `starts without each optional variable, falling back to TLS on port 465, a shut second-School gate and port 4310`
- `refuses the production stack without each secret and required setting, naming it`
- `gives the app no value for an unset optional setting, so it falls back to TLS on port 465 and a shut second-School gate, and the backup keeps 30 nights at 2 o'clock`

## A one-character secret, and a secret of whitespace: confirmed

`required()` refuses `undefined` and `""`, and nothing else. Compose's `${NAME:?}` refuses unset and empty, and nothing else. Neither has a minimum length, and neither trims, so a value of spaces counts as set.

The server holds two secrets: `SMTP_PASSWORD`, and the password inside `DATABASE_URL`. The probe boots it four times:

| Secret                      | `x`     | Three spaces |
| --------------------------- | ------- | ------------ |
| `SMTP_PASSWORD`             | started | started      |
| The `DATABASE_URL` password | started | started      |

The database boots are a real login: the URL carries the role and its password (three spaces travel as `%20%20%20`, and `pg` decodes them), Postgres accepts it, the server applies its migrations as that role and answers `/health`. Postgres has no minimum either, so nothing between `.env` and a superuser connection asks for one.

Compose holds three: `POSTGRES_PASSWORD`, `SMTP_PASSWORD` and `CLOUDFLARE_TUNNEL_TOKEN`. Each, set to `x` and to three spaces in turn, is accepted, and reaches its container's environment: Postgres's `POSTGRES_PASSWORD` and the backup's `PGPASSWORD`, the app's `SMTP_PASSWORD`, and `cloudflared`'s `TUNNEL_TOKEN`.

Consequence. The database password is the only thing between any container on the `database` network and the superuser that bypasses row-level security (#273). The deployment guide asks for 32 random bytes in hex; nothing checks that it got them. A typo, a half-pasted value or a placeholder starts the stack. An SMTP password or tunnel token of spaces starts too, and fails only at its first use: the tunnel never connects, and every email fails while sign-in, Invites and resets carry on as if it had been sent. No warning is logged at start in any of these cases. A control is weaker than its documentation says. Filed as #306 (medium).

- `refuses a one-character SMTP password, and a one-character database password, naming each (regression)`, which was `today_ starts with a one-character SMTP password, and with a one-character database password`
- `refuses to start with a one-character SMTP password or database password`, which was an `it.fails`
- `refuses an SMTP password of three spaces, and a database password of three spaces, naming each (regression)`, which was `today_ starts with an SMTP password of three spaces, and with a database password of three spaces`
- `refuses to start with an SMTP password or database password of whitespace`, which was an `it.fails`
- `refuses a one-character or whitespace POSTGRES_PASSWORD, SMTP_PASSWORD and CLOUDFLARE_TUNNEL_TOKEN, naming each, so none reaches its container (regression)`, which was `today_ passes a one-character or whitespace POSTGRES_PASSWORD, SMTP_PASSWORD and CLOUDFLARE_TUNNEL_TOKEN through to their containers`
- `refuses a one-character or whitespace secret before any container starts`, which was an `it.fails`

What length is enough, and whether the server or Compose (or both) refuses, belongs to the fix's issue. The `it.fails` pins only that a one-character or blank secret is refused before anything starts.

**Fixed, unverified (#306).** The server refuses `SMTP_PASSWORD`, and the password in `DATABASE_URL` or `DATABASE_OWNER_URL`, under 8 characters once spaces at either end are left out, naming the variable but not the value. A database URL with no password is still left to Postgres. Compose can't measure a value, so `docker-compose.yml` has a never-started `check-<NAME>` service for each of `POSTGRES_PASSWORD`, `APP_DATABASE_PASSWORD`, `BACKUP_POSTGRES_PASSWORD`, `SMTP_PASSWORD` and `CLOUDFLARE_TUNNEL_TOKEN`, whose container name is that secret. Compose refuses a container name without a letter or digit followed by another, or by `_`, `.` or `-`, so one character, spaces or nothing at all is refused by name before any container starts. An unset tunnel token is still #309's.

## Each secret at its `.env.example` value: confirmed for SMTP, refuted for the database

`.env.example` holds the development values on purpose ([local standards](../../standards/local.md)): `cp .env.example .env` gives a working development setup, against the trusting development Postgres and Mailpit. Its secrets are `SMTP_PASSWORD=anything`, beside `SMTP_SECURE=false`, `SMTP_HOST=localhost` and `SMTP_PORT=43125`, and a `DATABASE_URL` with no password at all. `vars.ts` reads no variable that says whether it is development or production, so the server can't tell the two apart.

- **The server.** Booted with every `.env.example` value, its `DATABASE_URL` pointed at the suite's Postgres (the example's points at a development Postgres the probe mustn't touch), it starts. `anything`, `SMTP_SECURE=false` and `http://localhost:4310` are each taken as given.
- **The database password.** A `DATABASE_URL` with no password, against a Postgres that asks for one, is refused: the server exits when the login fails. In production that Postgres is the Compose one, which always asks, and Compose builds the app's URL itself from `POSTGRES_PASSWORD`, which `.env.example` doesn't hold. So the example's database secret can't reach production. Refuted, by Postgres and Compose rather than by the server, which would start on a trusting Postgres.
- **Compose, from `.env.example` alone.** Refused, for want of `POSTGRES_PASSWORD`. Refuted.
- **Compose, from `.env.example` plus the Compose-only lines** (`POSTGRES_PASSWORD`, `CLOUDFLARE_TUNNEL_TOKEN` and the four backup lines, as a `.env` started from the example and finished from the deployment guide would hold): accepted, and the production app is given `SMTP_HOST=localhost`, `SMTP_PORT=43125`, `SMTP_SECURE=false` and `SMTP_PASSWORD=anything`. Compose replaces only `DATABASE_URL` and `PUBLIC_URL`.

Consequence. Inside the app container nothing listens on `localhost:43125`, so every email fails: reset links, Invites, address checks and the security notices that F1 and A3 lean on as the Parent's only signal. Nothing says so at start. Were anything to listen there, it would be sent the SMTP login in plain text (#307). The deployment guide builds `.env` from its own list and never from the example, so this needs the owner to take the development route on the server; that is why it is low. Filed as #308 (low).

**Fixed, unverified (#308).** The server refuses `.env.example`'s own secrets, `SMTP_PASSWORD=anything` and its `TOTP_SECRET_KEY`, by name, unless it was started from development's entry point, `src/server/development.ts`, which `pnpm run:local`, `pnpm migrate` and `pnpm seed:owner` run. No variable turns development on, and every container runs `index.ts`. `.env.example` now holds `SMTP_ALLOW_PLAIN_TEXT=true` for Mailpit (#307), and `docker-compose.yml` refuses a `.env` that holds it, by name, so the production app is given none of the development SMTP settings.

- `refuses .env.example's SMTP password outside development, naming it as the example's, given a database it can reach (regression)`, which was `today_ starts with .env.example's SMTP password, SMTP_SECURE=false and public URL, given a database it can reach`
- `refuses to start with .env.example's development SMTP password and SMTP_SECURE=false`, which was an `it.fails`
- `refuses to start on a database URL with no password, as .env.example's, against a Postgres that asks for one`
- `refuses .env.example on its own, which holds none of the production stack's secrets`
- `refuses .env.example's development SMTP settings for the production app once the Compose-only lines are added, naming SMTP_ALLOW_PLAIN_TEXT, so the app is given none of them (regression)`, which was `today_ passes .env.example's development SMTP settings to the production app once the Compose-only lines are added`
- `refuses .env.example's development SMTP settings for the production app`, which was an `it.fails`

## `SMTP_SECURE` off: confirmed

`createSmtpTransporter` hands Nodemailer `secure: isSecure` and nothing else about TLS. With `secure: true`, the default, the connection is TLS from its first byte. With `secure: false`, Nodemailer upgrades with `STARTTLS` only if the server offers it, and otherwise carries on in plain text, logging in and sending the message. `requireTLS` would refuse instead, and is never set. [The email guide](../../guide/email.md) documents `false` "for Mailpit"; nothing confines it to development.

The probe asks for a reset link for its Parent, through the stand-in that offers no `STARTTLS`:

- **`SMTP_SECURE` unset.** The stand-in receives a TLS ClientHello and nothing else: no `EHLO`, no login and no link. The send fails, so the reset link is never delivered, which is fail-closed.
- **`SMTP_SECURE=false`.** The stand-in receives, in plain text, `AUTH PLAIN` with the base64 of the SMTP username and password, then the whole reset email. Decoded from quoted-printable, it carries `https://wizzaroo.example/parent/#reset-password=<token>`, and the token's hash is a live row in `password_resets`. Neither the server nor Nodemailer logs a warning.

Consequence. Anyone on the path between the home server and the SMTP provider who can strip one line of the provider's `EHLO` answer reads every email in flight and the provider's API key. A reset link is a takeover of its adult for its hour, and the same holds for an Invite link, which signs whoever opens it in as that adult. One `false` in `.env`, set by following the guide's Mailpit line, turns that on with no warning. The default is safe, and the setting is in the owner's hands, so this is a control weaker than its documentation says rather than an open door. Filed as #307 (medium).

- `speaks TLS from the first byte when SMTP_SECURE is unset, so a server that offers none is sent no password and no link`
- `insists on STARTTLS when SMTP_SECURE is false, so a server that offers none is sent no login, no message and no live reset link (regression)`, which was `today_ sends the SMTP password, and a live password-reset link, in plain text when SMTP_SECURE is false and the server offers no STARTTLS`
- `sends no SMTP password and no reset link in plain text, whatever SMTP_SECURE says`, which was an `it.fails`

The `it.fails` is one way the property could be met. `requireTLS` with `secure: false` keeps port 587 open to providers that need `STARTTLS`. Refusing `false` outside development is another; that choice belongs to the fix's issue, and Mailpit in development and in the pen-test deployment needs an answer either way.

**Fixed, unverified (#307).** `createSmtpTransporter` sets `requireTLS` whenever `SMTP_SECURE` is `false`, so Nodemailer asks for `STARTTLS` and sends neither the login nor the email if the upgrade fails. Port 587 still works. Plain text goes only to a mail catcher, where `SMTP_ALLOW_PLAIN_TEXT=true` says so: `.env.example` sets it for development's Mailpit, and `docker-compose.pen-test.yml` sets it on the pen-test deployment's app for its Mailpit, on an internal network. `docker-compose.yml` never passes it to the production app, and refuses a `.env` that holds it.

## `TUNNEL_TOKEN` empty: confirmed

`docker-compose.yml` passes `TUNNEL_TOKEN: ${CLOUDFLARE_TUNNEL_TOKEN:-}`, the one secret it doesn't guard with `:?`. With the `tunnel` profile on, as the deployment guide's `COMPOSE_PROFILES=tunnel` turns it on, and `CLOUDFLARE_TUNNEL_TOKEN` unset, `docker compose config` succeeds and gives `cloudflared` an empty `TUNNEL_TOKEN`.

Read, and not run here: `cloudflared tunnel --no-autoupdate run` with no token and no named tunnel exits with an error, and `restart: unless-stopped` starts it again, for ever. The app is up and healthy behind it, reachable on `127.0.0.1:4310` only. So the failure is closed in effect, since nothing reaches the internet, but it isn't refused: `docker compose up` reports success, and the only sign is a container restarting in `docker compose ps`. The `:-` lets the stack start without the tunnel, as on a laptop; whether a `:?` can be kept to the `tunnel` profile is for the fix's issue. Filed as #309 (low).

- `today_ starts the tunnel profile with an empty TUNNEL_TOKEN when CLOUDFLARE_TUNNEL_TOKEN is unset`
- `it.fails`: `refuses the tunnel profile without CLOUDFLARE_TUNNEL_TOKEN, naming it`

| #307    | medium   | `SMTP_SECURE=false` sends the SMTP password and reset links in plain text when the server offers no `STARTTLS` |

#309 is fixed, unverified: `docker-compose.yml` passes `TUNNEL_TOKEN: ${CLOUDFLARE_TUNNEL_TOKEN:?…}`, so Compose refuses the file without it, naming it, as it does every other secret. Compose interpolates every service whether or not its profile is on, so it is refused with the `tunnel` profile off too. The pen-test deployment runs no tunnel, and its `.env` holds `CLOUDFLARE_TUNNEL_TOKEN=none-the-pen-test-deployment-runs-no-tunnel` only so Compose reads the file. `pnpm pen-test:up` adds the line to an older `.env`. `refuses the tunnel profile without CLOUDFLARE_TUNNEL_TOKEN, naming it` now passes, and the `today_` probe is a `(regression)` test that an empty token is refused as well.

## What this round didn't run

The probes were written, typechecked and linted in a sandbox with no container runtime and no `docker compose`, so the gated run skipped them there. What was run there, against no Postgres: the composition root refusing a missing `SMTP_HOST` by name, and passing an `SMTP_PASSWORD` of one space through configuration to the database connection; and the SMTP stand-in against the real Nodemailer transporter, which logged in and sent a reset-shaped message in plain text with `secure: false`, and failed its TLS handshake with `secure: true`. The verdicts above rest on that, on reading the code, and on the probes as written, until the gated run is executed on a host with Docker and its output posted on #222. What `cloudflared` and the Postgres image do with a weak or empty secret was read, not run. Nothing here was exercised against the pen-test deployment itself.
