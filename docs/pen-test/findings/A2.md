# A2: TOTP and recovery codes

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #204 (A2), which answers [H17](../../product-requirements-document/pen-testing.md#h17-second-factor-secrets-are-stored-in-the-clear--low). It names exploit chains, so it is kept private on the same terms as the PRD.

- **Trust boundary:** the second factor an adult signs in with after their password: a TOTP code or a recovery code. For Teachers and the Admin it is required (section 8 of `wizzaroo.md`, [ADR 0026](../../architectural-decision-record/0026-schools-and-teachers.md)); for Parents it is optional.
- **Code:** `src/server/auth/two-factor.ts`, `src/server/auth/two-factor-routes.ts`, the code step in `src/server/auth/sign-in-routes.ts`, and the policies on `users` and `recovery_codes` in `src/server/drizzle/0018_row-level-security.sql` and `0020_schools-and-teachers-reach.sql`.
- **Documented behaviour:** the "Two-factor authentication" item in [signing in](../../guide/signing-in.md#passkeys-and-two-factor-authentication), and what a Parent reaches in [keeping data safe](../../guide/security-and-backups.md#keeping-families-apart-in-postgres).
- **Probes:** the `pen test A2: TOTP and recovery codes` block in `src/integration.test.ts`, in the gated run against a real Postgres. It loads [the fixtures](../fixtures.md) into a database of its own and loads them again before every probe, so each probe starts from the plan. It freezes the clock at the start of a TOTP step. `parentA1` is the Parent with a second factor, `parentB` the Parent without, `coParentA1` the other adult in Family A1, `teacherAYear3` and `admin` the staff whose only second factor is TOTP, and `teacherAYears5And6` a Teacher with a passkey and no TOTP.

H17 is **confirmed**: the TOTP secret is stored in the clear (#254) and the recovery codes as unsalted SHA-256 (#255). Its claim that both are "a second factor for every adult" once the database is read holds in full for the TOTP secret, and only at a cost for recovery codes (below).

## Code replay: refuted

`redeemTwoFactorCode` accepts a TOTP code only by moving `users.totp_last_used_step` forward, in one `UPDATE … WHERE totp_last_used_step < step`. So a code works once per adult, whichever route it is sent to, and a code from an earlier step stops working once a later one has been used. Turning TOTP on records its step too, so the code that turned it on can't then sign in.

- `refuses a two-factor code that has already signed in, both in a second pending sign-in and to turn two-factor off`
- `refuses a code from an earlier step once a later step's code has been used`
- `signs in just one of two pending sign-ins racing with the same code`: the row lock decides the race, and the loser gets 401.

## Drift window: refuted

`findTotpStep` accepts the current 30-second step and one either side (`totpDriftSteps = 1`), so a code is good for at most 90 seconds. That is RFC 6238's recommended allowance, and [signing in](../../guide/signing-in.md#passkeys-and-two-factor-authentication) documents it ("one step either side accepted"). Codes two steps away are refused.

- `accepts a code from one step either side of the server's clock, and refuses one from two steps away`

## The 5-try limit per pending sign-in: refuted as a weakness, and confirmed as a bound

**Per pending sign-in, the limit holds.** `checkSignInCode` locks the pending sign-in `FOR UPDATE`, counts each wrong code, and deletes the pending sign-in at the fifth. When ten wrong codes for one pending sign-in arrive at once, exactly five are checked and five are told to sign in again. The right code is then refused too.

- `checks no more than five codes for one pending sign-in, even when ten wrong ones arrive at once`

**For the account, it bounds nothing.** Anyone who has the password can start as many pending sign-ins as they like, each with five fresh tries. Nothing counts wrong codes against the account, and nothing limits the requests (H8). Three accepted codes (one step either side) out of 10⁶ give each guess a 3 × 10⁻⁶ chance. So 231,049 guesses give even odds and 767,528 give 90%. At five guesses per pending sign-in, that is 46,210 or 153,506 password checks. One argon2 check with the library's defaults, as the sign-in uses them, measured 7.6 ms on one core in the sandbox. So about 6 minutes of one server core gives even odds and about 19 minutes gives 90%, worked out by arithmetic and not exercised. Every wrong code does write a `sign-in.failed` entry, so the Audit Log shows it afterwards, but nothing acts on it. Filed as #256; fixed, unverified (#256).

- `today_ gives every new pending sign-in five fresh tries, so fifteen wrong codes across three of them are each checked and the right code then signs in`
- `it.fails`: `stops checking codes for an adult once five wrong ones have been given, however many pending sign-ins carry them`

## Recovery codes

**Single use: refuted.** Using a recovery code deletes its row with `DELETE … RETURNING`, so it works once, wherever it is sent. Two pending sign-ins racing with the same code sign in once between them. A used code can't turn TOTP off either.

- `signs in with a recovery code once and only once, even when two pending sign-ins race with it, and won't then turn two-factor off with it`

**Entropy: refuted.** Turning TOTP on hands out ten codes. Each is twelve characters drawn by `crypto.randomInt` from a 31-character alphabet with no `i`, `l`, `o`, `0` or `1`, so it carries 12 × log₂ 31 ≈ 59.45 bits. Online, a guess also spends one of a pending sign-in's five tries, and ten live codes give each guess about a 1.3 × 10⁻¹⁷ chance. The TOTP secret is 20 bytes, as RFC 4226 recommends.

- `hands out ten different recovery codes, each twelve characters from a 31-character alphabet`

**Storage: confirmed.** `recovery_codes.code_hash` is `sha256(code)` of the lower-cased code with its hyphens removed: no salt, no stretching, the same function as every single-use token. For a 256-bit token that is enough. For a 59.45-bit code it means anyone with a copy of the table (H4, H7, a backup and its key, H14) tests one guess against every stored code at once, with one SHA-256 per guess. The fixtures hold four adults with TOTP, so 40 hashes. 31¹² ≈ 7.9 × 10¹⁷ codes then need about 1.9 × 10¹⁶ hashes to find the first match. At an assumed 2 × 10¹⁰ SHA-256 a second, roughly what one current GPU is reported to reach, that is about 11 days of one GPU, and less with more adults or more GPUs. A per-code salt alone would raise it to about 228 days per code, and a password hash to far beyond that. NIST SP 800-63B asks for look-up secrets with less than 112 bits to be salted and hashed with a key-derivation function. Today this matters less than #254, since the same copy holds every TOTP secret in the clear. Once that is fixed, these hashes become the weakest stored second factor. Filed as #255; fixed, unverified (#255): each code is now argon2id with a salt of its own.

- `today_ stores each recovery code as one unsalted SHA-256 of the code`
- `it.fails`: `stores recovery codes salted and stretched, so no stored hash is a single SHA-256 of its code`

## TOTP secret storage: confirmed

`users.totp_secret` holds the secret as the hex it was issued in, and `totp_setups.secret` holds a secret being set up the same way for its 10 minutes. Reading the column is enough to make a code that signs in. Nothing in the guides or ADRs records this as a decision: [signing in](../../guide/signing-in.md#passkeys-and-two-factor-authentication) says recovery codes are kept only as hashes and says nothing of the secret, and the [Family export](../../guide/family-data-and-admin.md) leaves the secrets out. Anyone who reads the database therefore holds the second factor of every adult who has one, Teachers and the Admin included. They still need the password, which is argon2. Filed as #254; fixed, unverified (#254): both columns now hold the secret sealed under `TOTP_SECRET_KEY`, which the database never holds.

- `today_ keeps each TOTP secret, and each secret being set up, in Postgres as issued, so the column alone makes codes that sign in`
- `it.fails`: `keeps TOTP secrets, and secrets being set up, in Postgres in a form that doesn't make codes`

## Turning TOTP off

**What it requires.** `DELETE /api/two-factor` needs a sign-in (any sign-in, through `runAsSignedInUser`) and a right code: a TOTP code or a recovery code. It doesn't need the password. That much is documented ("Turning it off takes a code too") and holds:

- `needs a sign-in and a right code, not the password, to turn two-factor off`
- `won't turn off a Teacher's or the Admin's only second factor through the API, even with their own right code`: 409, through `LastSecondFactorError`.

**But the code check has no limit.** Unlike the sign-in step, there is no try count. A wrong code answers 403 and is written only to the container log, never to the Audit Log, and the next one is checked just the same. So anyone holding a session, a stolen cookie for instance, can guess codes until one fits: 231,049 requests for even odds, none of them an argon2 check, none of them logged. TOTP is then off, no email tells the owner, and the session can go on to the email change and reset chain in H3 to keep the account, password and all. Filed as #257; fixed, unverified (#257): wrong codes sent there now count against the adult with the sign-in step's bound, each refusal is in the Audit Log, and turning TOTP off emails the owner.

- `today_ checks every code sent to turn two-factor off, so twenty wrong ones are each refused, none is logged, and the right one then turns it off`
- `it.fails`: `holds turning two-factor off to five wrong codes, as signing in is`

**Whether staff can, through the API: refuted.** The two-factor surface is four routes (`POST /api/totp-setups`, `POST` and `DELETE /api/two-factor`, `POST /api/sign-in/two-factor-code`). None takes a user id. Each acts on the signed-in adult alone. A Parent's code sent by the Admin or a Teacher to their own `DELETE /api/two-factor` leaves the Parent's TOTP and recovery codes as they were.

- `offers no route that turns off another adult's two-factor authentication, and the Admin's and a Teacher's own route leaves a Parent's on`

**Whether staff can, in Postgres: confirmed.** The `users` policies decide rows, not columns (H5), and `recovery_codes_within_reach` lets the Admin through. Inside a reach transaction, with no API involved:

- a co-Parent's reach reads the other Parent's `totp_secret`, and clears it, after which that Parent signs in with the password alone. [Keeping data safe](../../guide/security-and-backups.md#keeping-families-apart-in-postgres) says a Parent reaches "their own sign-ins, passkeys and codes, but not their co-Parents'".
- a Teacher's reach reads the `totp_secret` of every Parent in their reach. It can't change it, since Teacher policies on `users` are `SELECT` only.
- the Admin's reach reads every adult's `totp_secret`, clears a Teacher's only second factor, and deletes their recovery codes. Through the API, `LastSecondFactorError` forbids exactly that.

The rule is enforced in the API alone, and only an API bug would reach the database layer. That is the case the second wall exists for. Filed as #258; fixed, unverified (#258).

- `today_ lets a co-Parent's, a Teacher's and the Admin's reach read a Parent's TOTP secret in Postgres, and the Admin's turn a second factor off there, though no longer the co-Parent's (#274)`
- `it.fails`: `keeps an adult's TOTP secret out of every other adult's reach in Postgres`

## What this round didn't run

The probes were written, typechecked and linted in a sandbox with no container runtime, so the gated run skipped them there. The verdicts above rest on reading the code and on the probes as written, until the gated run is executed on a host with Docker and its output posted on #204. Nothing here was exercised against the pen-test deployment itself, and the rates above are arithmetic, not load.
