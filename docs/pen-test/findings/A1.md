# A1: passwords and sessions

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #203 (A1) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers the session-lifetime and revocation half of H3, the password-guessing bullet of H8, and H11. It names exploit chains, so it is kept private on the same terms as the PRD.

- **Read against:** the tree at the commit that adds this note, and the [fixtures](../fixtures.md) by handle. No credential appears here.
- **The probes** are the tests under `pen test A1: passwords and sessions` in `src/integration.test.ts`. They run against a real Postgres in a database of their own, load the fixtures again before every probe, and sign in through [the credentials package's harness](../credentials-package.md). A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now; a refuted probe is a passing test.
- **Left to other scope issues:** the email-change takeover chain, the security notices and the "already uses that email address" oracle in H3 are A4's. H8's other bullets (pending sign-ins for TOTP, the argon2 cost of resets and Invites, passkey sign-in options) are I2a's. The Audit Log rows a failed guess writes are counted below for H21, whose verdict is D6's.

## Session lifetime

A sign-in is a random 32-byte token, kept as its SHA-256, in a row that expires 30 days after it was made (`src/server/auth/sign-in-routes.ts`). The cookie's `Max-Age` is the same 30 days. Using it changes nothing: there is no last-used time, so no idle timeout and no sliding expiry, for a Parent or for staff. The 30 days is documented in [Signing in](../../guide/signing-in.md); the absence of an idle timeout, and the same lifetime for the Admin and Teachers, who reach many Families, are not. The probe moves a fresh sign-in for `coParentA1` and one for `admin` 29 days into the past and both are still served.

**Fixed, unverified (#244).** `sign_ins.last_used_at` moves on when a sign-in is used, at most once a minute. A Parent's sign-in left unused for 14 days is refused, and lasts 30 days in all as before; the Admin's and a Teacher's are refused after 12 hours unused or 7 days in all. [ADR 0049](../../architectural-decision-record/0049-sign-ins-end-when-left-unused.md) records the figures and their review on 31 March 2027.

## Which events end which sign-ins

| Event                                                | Ends                                                      | How it was found |
| ---------------------------------------------------- | --------------------------------------------------------- | ---------------- |
| Signing out                                          | That browser's sign-in only                               | Probe 2          |
| Changing a password (`PUT /api/password`)            | Every other sign-in; keeps the one that asked             | Probe 3          |
| Resetting a password from the emailed link           | Every sign-in, and every pending sign-in                  | Probe 4          |
| Setting a password (`POST /api/password`)            | **None**                                                  | Probe 5          |
| Accepting an Invite                                  | **None** of the login's earlier sign-ins; makes a new one | Probe 6          |
| Confirming an email address change                   | **None**                                                  | Probe 7          |
| Removing a password (`DELETE /api/password`)         | Every other sign-in                                       | Read, not probed |
| The Admin deactivating an adult                      | Every sign-in, pending sign-in and password reset         | Read, not probed |
| Making a Family Device                               | That browser's own sign-in                                | Read, not probed |
| Turning TOTP on or off, adding or removing a passkey | None                                                      | Read, not probed |

Pending sign-ins (the five minutes between a right password and its code) survive a password change but not a reset. They still need the code, so this isn't filed.

There is no way to see or end one's other sign-ins directly. Changing the password is the documented way, and a passkey-only adult has no password to change: they can only set one, which ends nothing, and then remove it again. Signing out ending one browser is the usual meaning of signing out and stays a documented decision; the missing way to end the others is part of #245. _Fixed, unverified (#245):_ **Sign out your other browsers** on Your account (`DELETE /api/other-sign-ins`) now ends them with no password.

## Cookie flags and fixation

`wizzaroo_sign_in` is `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/` and lasts 30 days. `wizzaroo_pending_sign_in` has the same flags, `Path=/api/sign-in` and five minutes. Every sign-in mints a new token on the server and ignores any cookie the browser already held, and a token the server didn't make never signs anyone in.

The name has no `__Host-` prefix, so a page on any other host under the same registrable domain can set `wizzaroo_sign_in` with `Domain=adrianeyre.co.uk` and a longer `Path` such as `/api`. The browser then sends that cookie first, and `@fastify/cookie` serves the first of two. The probe sends `parentB`'s token ahead of `coParentA1`'s and is answered as `parentB`. A victim signed in to the attacker's account who then adds a Child, or sets a Picture Password, writes into the attacker's Family.

**Fixed, unverified (#248).** The cookie is now `__Host-wizzaroo_sign_in`, with `Secure`, `Path=/` and no `Domain`, so a browser takes it only from Wizzaroo's own host. A planted `wizzaroo_sign_in` is no longer read at all.

## Guessing a password

Nothing limits `POST /api/sign-in`: no rate limit, no lockout, no delay. The probe sends `coParentA1` 101 wrong passwords in a row (one more than the 100 consecutive failures NIST SP 800-63B lets any limit allow) and gets 101 identical 401s, each writing one `sign-in.failed` Audit Log entry, and then signs in with the right one.

**What bounds the rate is argon2 alone.** Every attempt runs one argon2id verify, `m=19456 KiB, t=2, p=1` (the `@node-rs/argon2` defaults the app uses), for an unknown email as well as a known one. `@node-rs/argon2` runs on Node's libuv pool, four threads unless `UV_THREADPOOL_SIZE` is set, and nothing sets it. Measured in the sandbox this note was written in: **7.9 ms per verify on one thread, about 400 verifies a second with four**. The home server's CPU isn't known here, so the table also gives a quarter of that.

| At                                      | 400 guesses/s (the ceiling measured) | 100 guesses/s (a CPU four times slower) |
| --------------------------------------- | ------------------------------------ | --------------------------------------- |
| An hour                                 | 1,440,000                            | 360,000                                 |
| A day                                   | 34,560,000                           | 8,640,000                               |
| A list of 1 million candidate passwords | 42 minutes                           | 2.8 hours                               |
| A list of 10 million                    | 6.9 hours                            | 28 hours                                |
| 12 random lowercase letters (26¹²)      | about 7.5 million years              | about 30 million years                  |
| Failed-sign-in Audit Log entries (H21)  | 1,440,000 an hour                    | 360,000 an hour                         |

- The password rule is a length of 12 or more (`src/server/auth/password.ts`), with no check against common or breached passwords. A random password is out of reach; a person's own choice of twelve characters is the kind a candidate list holds, and one account's list of a million goes in under an hour.
- **Spraying** one common password across every adult costs one guess per account, so the whole user table is tried at the same rate.
- The attempts are all served by one process with the Audit Log growing in step, so the guessing also costs every other user their sign-ins' share of argon2 (H8, H21).
- **The chain to H1:** a Teacher with no second factor yet (`teacherBYear3`'s shape) whose password falls to a list can then enrol their own TOTP. That chain is A5's to probe.

**Fixed, unverified (#246).** Wrong passwords now count against the normalised email address, with an account or without, by [the request-rate policy](../../product-requirements-document/pen-testing.md#pre-condition-the-request-rate-policy-before-a-second-school): 10 an hour, and 5 in any one minute. Past that, `POST /api/sign-in` answers `429` before checking any password, the right one included, and writes one `sign-in.rate-limited` entry for the run of refusals. The sign-in route, its code step, both reset routes, Invite acceptances and passkey sign-in options also count together per caller's address: 100 in 15 minutes, and 20 in any one minute.

## Requests from another host on the same site

Every host under `adrianeyre.co.uk` is the same _site_ as `wizzaroo.adrianeyre.co.uk`, so `SameSite=Strict` cookies go with its requests. There are no CSRF tokens and nothing checks `Origin` or `Sec-Fetch-Site`. What a page there can make the signed-in adult's browser send:

- **No `DELETE`, `PUT` or `PATCH`.** They need a CORS preflight, and the server grants none (refuted, probe 13).
- **No JSON body.** A form or a no-CORS `fetch` can send only `text/plain`, `application/x-www-form-urlencoded` or `multipart/form-data`. Fastify refuses the last two with 415, and a `text/plain` body fails every route's JSON schema with 400 (refuted, probe 12).
- **Every `POST` that takes no body,** from `<form method="post" enctype="text/plain">` or `fetch(url, { method: "POST", mode: "no-cors", credentials: "include" })`. These nine reach their handlers (probe 14):

  | Route                                                | Who it acts as       | What it does                                                     |
  | ---------------------------------------------------- | -------------------- | ---------------------------------------------------------------- |
  | `POST /api/admin/deletion-requests/:id/confirmation` | The Admin            | Deletes a Family or Child, given a pending deletion request's id |
  | `POST /api/people/:userId/deactivation`              | The Admin            | Deactivates any adult and ends their sign-ins, given their id    |
  | `POST /api/people/:userId/password-resets`           | The Admin, a Teacher | Emails an adult a password reset, given their id                 |
  | `POST /api/sign-out`                                 | Anyone signed in     | Signs them out                                                   |
  | `POST /api/totp-setups`                              | Anyone signed in     | Starts, or replaces, a TOTP setup                                |
  | `POST /api/passkey-registration-options`             | Anyone signed in     | Stores a passkey registration challenge                          |
  | `POST /api/passkey-confirmation-options`             | Anyone signed in     | Stores a passkey confirmation challenge                          |
  | `POST /api/passkey-hand-offs`                        | Anyone signed in     | Makes a QR hand-off token (its reply can't be read cross-origin) |
  | `POST /api/passkey-sign-in-options`                  | No one               | Stores a sign-in challenge; unauthenticated anyway (H8)          |

- **A `GET` that writes:** `GET /api/children/:childId/progress` writes an Admin access log row when the Admin reads it. An `<img>` on a same-site page does it, so the log says the Admin opened a Child's progress that the Admin never looked at.

Ids aren't secret to everyone: a Teacher sees their Parents' ids, and a deletion request's id is in the Admin's own list. The probe makes the Admin's sign-in, from a same-site page, log Ada's progress as opened, deactivate `coParentA1` and confirm `deletionRequestFamilyB`, and Family B is gone.

**The other hosts (probe 15).** The repository names one host under `adrianeyre.co.uk`: `wizzaroo.adrianeyre.co.uk`, which also sends the email, from `noreply@wizzaroo.adrianeyre.co.uk`. The apex, and any other name the zone serves now or later, is the same site whatever it is. Listing the names from DNS and certificate transparency logs was still an **OWNER TO CONFIRM** item in the [rules of engagement](../rules-of-engagement.md#out-of-scope) when A1 ran (the owner confirmed it on 17 November 2026, after this probe), so it wasn't done, and who controls each name is for the owner to answer. The verdict doesn't wait on the list: the defence is only as strong as the least-guarded host the owner's zone ever points somewhere, which is the dependency #247 records.

On the pen-test deployment the same holds for any page served from `localhost` on another port, Mailpit's at `localhost:43380` included, because ports don't change the site. That is how a tester reproduces #247 and #248 there.

**Fixed, unverified (#247).** Every request under `/api/` whose `Sec-Fetch-Site` is sent and is neither `same-origin` nor `none` is refused with 403, and so is any request other than a `GET`, `HEAD` or `OPTIONS` whose `Origin` is sent and isn't `PUBLIC_URL`'s. The check runs before the route's reach check and before its body is read, so a refused request changes nothing and logs nothing in the Admin access log. A request with neither header, as curl and the harness send, is let through.
