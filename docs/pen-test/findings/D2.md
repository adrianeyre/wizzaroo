# D2: The Admin access log

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #211 (D2), which answers [H6](../../product-requirements-document/pen-testing.md#h6-some-admin-reads-are-not-logged-and-the-log-can-be-changed--high). It names exploit chains, so it is kept private on the same terms as the PRD.

- **Trust boundary:** the Admin reaches every Family's Children. What keeps that reach honest is the Admin access log: "the Admin everything, logged" (section 9 of `wizzaroo.md`, under "Keeping Schools and Families apart"), "each time the Admin opens a Child's progress, it is logged" (section 8, "Dashboards"), and [ADR 0001](../../architectural-decision-record/0001-family-is-the-data-boundary.md) and [ADR 0026](../../architectural-decision-record/0026-schools-and-teachers.md). "Logged Admin access" is an item on the second-School gate (section 11). Each Family reads the log's rows about its own Children in its data export ([ADR 0041](../../architectural-decision-record/0041-security-actions-are-kept-in-an-audit-log.md), which keeps it apart from the Audit Log for that reason).
- **Code:** `admin_access_logs` and its grant and policies in `src/server/drizzle/0021_schools-and-teachers.sql`; its one writer, `GET /api/children/:childId/progress` in `src/server/children/children-routes.ts`; `GET /api/school-children` beside it; `src/server/admin/admin-routes.ts`; `GET /api/parents` in `src/server/people/people-routes.ts`; and the export in `src/server/family-data/family-export.ts`.
- **Documented behaviour:** [the Admin dashboard](../../guide/family-data-and-admin.md#the-admin-dashboard) and [keeping Families apart in Postgres](../../guide/security-and-backups.md#keeping-families-apart-in-postgres). Neither guide page describes the access log itself.
- **Probes:** the `pen test D2: the Admin access log` block in `src/integration.test.ts`, in the gated run against a real Postgres. It loads [the fixtures](../fixtures.md) into a database of its own and loads them again before every probe, so each probe starts from the plan. The loader doesn't touch `admin_access_logs`, so each probe also empties the log first. The Admin signs in through a sign-in row inserted for `admin`, marked two-step, so the probes test the log and not signing in (A1, A2 and A5 test that). `parentA1`, `teacherAYear3` and `familyDeviceA1` stand for the other reaches, and Ada (`childA1Year3`) is the Child the Admin opens.

H6 is **confirmed** on all three of its bullets. `GET /api/school-children` (#267) and `GET /api/admin/families` (#268) write no row, and neither do seven more reply paths. The Admin's reach can change or erase the log (#269). The one path that does log is the right shape. It writes the row in the read's own transaction, after the reach check and before the read, so a refused read leaves no row and a failed read rolls its row back. A `HEAD` request is the exception (#271, fixed, unverified).

## The progress route: refuted, with one exception

`GET /api/children/:childId/progress` runs within the caller's reach. It loads the Child through `loadSeenChild`, and only then, for the Admin, inserts `{ admin_user_id, child_id }` before loading the progress, all in one transaction. So:

- every read served writes exactly one row: two opens of Ada's progress and one of Eli's write three rows, each naming `admin` and the Child;
- a Child that doesn't exist (404), an id that isn't a UUID (400), an Admin sign-in without a second factor (403) and no sign-in at all (401) write none, since each is refused before the insert;
- read from the code rather than probed: a failure after the insert, while loading the progress, rolls the row back with the rest of the transaction.

Test: `writes one row naming the signed-in Admin and the Child each time the Admin is served a Child's progress, and none for a progress read that is refused`.

**`HEAD` is logged as a read: confirmed.** Fastify 5 answers `HEAD` on every `GET` route by default (`exposeHeadRoutes`). It runs the same handler and then drops the body, so the insert happens and the reply carries only the headers, `content-length` among them. Outside the suite, a bare Fastify 5.12.8 route counted one handler run for one `HEAD` with an empty body. So the Family's export shows the Admin opening a Child's progress that was never served. Nothing in the dashboard sends `HEAD`. The row is still a false record, and anything that can make the Admin's browser send one can plant it. A1 found that a same-site page can already plant `GET` reads (#247). Filed as #271 (low).

Fixed, unverified (#271). `logAdminAccess` writes no row for a `HEAD` request, on every route that logs. `HEAD` stays exposed on every `GET` route, and answers as `GET` does with no body. Pinned by `answers a progress read the Admin sends as HEAD with no body and logs nothing, while the same read as GET is logged once (regression)`, which sends `HEAD` to all five `GET` routes that log, beside `writes no access-log row for a HEAD request, which serves no progress`.

- `today_ logs a progress read the Admin sends as HEAD, though the reply carries no progress`
- `it.fails`: `writes no access-log row for a HEAD request, which serves no progress`

## `GET /api/school-children`: confirmed

`/api/school-children` runs `runAsSignedInStaff`, so the Admin reaches it. For the Admin, `loadSeenChildPlacements` is every Child, and the reply is `loadChildProgress` for each of them: the same `ChildProgress` that the progress route logs, with Mastery, daily practice, Stars, Region progress, limits and Check History. The route never touches `admin_access_logs`. So one request serves all five fixture Children's progress, and their Families' exports show nothing. It is the progress route's read for every Child at once, with no log. Filed as #267 (high: Admin access can go unlogged). Fixed, unverified (#267): the route now writes one row naming the Admin for each Child it serves, in the read's transaction, after the reach check and before the read.

- `today_ serves the Admin every Child's progress from /api/school-children and writes no access-log row`
- `it.fails`: `writes one access-log row for each Child whose progress /api/school-children serves the Admin`

## Every other reply path: confirmed

These are the routes whose reply carries a Child's data to the Admin. Every one answered 200 and wrote no row:

| Route                                         | What it serves the Admin                                                                                     | Children                              |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------- |
| `GET /api/admin/families`                     | Every Family with each Child's id and nickname                                                               | All five                              |
| `GET /api/parents`                            | Every Parent with each of their Children's id, nickname and Year                                             | All five                              |
| `GET /api/admin/deletion-requests`            | Each request's Child's nickname, with the Family's name and the requesting Parent's email                    | Ada, once a Parent asks to delete her |
| `PUT /api/children/:childId`                  | The Child: nickname, birth month and year, School, Character name, Phonics Programme, Year, Classmate visits | Ada                                   |
| `PUT /api/children/:childId/limits`           | The Child's limits and Teacher locks                                                                         | Ada                                   |
| `PUT /api/children/:childId/teacher-locks`    | The Child's limits and Teacher locks                                                                         | Ada                                   |
| `PUT /api/children/:childId/classmate-visits` | The Child, as above                                                                                          | Ada                                   |
| `PUT /api/children/:childId/birth`            | The Child, as above                                                                                          | Ada                                   |
| `PUT /api/children/:childId/school`           | The Child, as above                                                                                          | Ada                                   |

Each `PUT` above was sent with the values Ada already has, so it changed nothing and still served her data. The fixtures' one deletion request is for the whole of Family B and names no Child, so the probe adds one from `parentA1` for Ada before it lists the requests.

The canon asks for more than the progress route: "the Admin everything, logged" (section 9), and "a logged Admin action for reading another Family's data" (ADR 0001). The dashboard's directory (`/api/admin/families`, `/api/parents`) is the Admin's everyday view, so logging it would put a row against every Child on every visit. Whether that counts as access is the owner's call when triaging, and the finding records it. As built, nothing but the progress route logs. Filed as #268 (high: Admin access can go unlogged). Fixed, unverified (#268): each of the nine now writes one row naming the Admin for each Child it serves, in the reply's transaction, after the reach check.

- `today_ serves the Admin Children's data on nine other reply paths and writes no access-log row on any of them`
- `it.fails`: `writes one access-log row for each Child whose data a reply serves the Admin, on every reply path`

**Paths looked at and left out**, because none serves the Admin another Family's Child's data:

- `POST /api/families/:familyId/children` replies with a Child the Admin has just made from what they typed.
- `POST /api/admin/families/:familyId/family-chest-coin-awards` replies with a Family's chest count, not a Child's data.
- `POST /api/admin/children/:childId/star-awards`, `PUT /api/children/:childId/picture-password` and the deletions reply 204. The deletions are in the Audit Log.
- `GET /api/admin/audit-log-entries` names Children by id only.
- The Parent routes (`/api/children`, `/api/family`, `/api/family-export`, `/api/deletion-requests`) serve only the caller's own Family. The export runs within that Family's reach even for the Admin. The fixtures' Admin is in no Family, so these routes refuse them.
- The Family Device routes need a device credential, which the Admin doesn't hold.
- `POST /api/bulk/families/preview` tells staff whether a Child they typed already exists in an existing Parent's Family. It replies with what was typed, not stored data, so it is left to B3 (noted in the outbox).

## What a row records

**The person: refuted as a weakness.** `admin_user_id` is `caller.userId`, taken from the sign-in and never from the request. Today only the owner holds the Admin role, so it names a natural person. The foreign key is `ON DELETE CASCADE`, though, so deleting the Admin's account would delete every row they wrote. No route deletes an account in the Admin role today (a Family's deletion skips the Admin's own Family), so this is recorded here and not filed.

**The Child: refuted as a weakness.** `child_id` is the route's `:childId`, written only after `loadSeenChild` has found that Child within reach. Deleting a Child deletes their rows, as erasure asks.

**What was read: confirmed.** A row is `id`, `admin_user_id`, `child_id` and `opened_at`, and nothing else. Today one route writes it, so a row means "opened this Child's progress". It can't say so itself, though. Once any second path logs (#267, #268), its rows will look exactly like a progress read, in the log and in the Family's export. The PRD's checks ask that "the audit records what was served, on every reply path". Filed as #270 (low). Fixed, unverified (#270): each row now records what the reply served, one value of a closed set per reply path that logs, and the Family's export lists it. `admin_user_id` is no longer a foreign key, so a row outlives the Admin's account, as the Audit Log's entries do.

- `today_ keeps who, which Child and when in each row, and nothing that says what was read`
- `it.fails`: `records in each row what the Admin was served, so a progress read can be told from any other`

## Changing the log in Postgres

`0021_schools-and-teachers.sql` grants `wizzaroo_reach` `SELECT, INSERT, UPDATE, DELETE` on `admin_access_logs`. Its policies are:

- `admin_access_logs_within_reach`: `FOR ALL`, `USING (wizzaroo_caller_is_admin())`, with no `WITH CHECK`;
- `admin_access_logs_seen_by_family`: `FOR SELECT`, for the Family whose Child a row names.

**Every reach but the Admin's: refuted.** With one row logged through the API, a Parent's reach (`parentA1`, Ada's Parent, who can read the row), a Teacher's (`teacherAYear3`, who can't) and a Family Device's (`familyDeviceA1`) each rewrite 0 rows and erase 0 rows. Each is refused a new row by the policy (SQLSTATE 42501). No reach holds `TRUNCATE`, the Admin's included. The row is still there afterwards.

- `refuses a Parent's, a Teacher's and a Family Device's reach any change to the access log, and every reach a TRUNCATE`

**The Admin's reach: confirmed.** In one reach transaction each, with no API involved, the Admin's reach:

- rewrites the row that records them opening Ada's progress so that it names Eli and another time;
- writes a row saying `teacherAYear3` opened Cara's progress;
- deletes both.

The log the Family reads is then empty. The `FOR ALL` policy with no `WITH CHECK` lets any row the Admin can see be changed into any row, in anyone's name. The Audit Log, by contrast, is append-only to the reach role, in the caller's own name only ([ADR 0041](../../architectural-decision-record/0041-security-actions-are-kept-in-an-audit-log.md)). Only the API's code keeps the Admin from editing the record of what the Admin looked at. That is an audit rule enforced in one layer, the case the second wall exists for, and an API bug in any Admin route running within reach would reach it. Filed as #269 (high). Fixed, unverified (#269): the reach role now holds only `SELECT` and `INSERT` on the log, the Admin reads it through a `FOR SELECT` policy, and a `FOR INSERT` policy lets the Admin's reach add a row only in the Admin's own name, timed by its own transaction. The cascade from a deleted Child or adult runs as the owner.

- `today_ lets the Admin's reach rewrite a row, write one in a Teacher's name, and erase them all`
- `it.fails`: `keeps the access log append-only to the Admin's reach, and written only in the Admin's own name`

H4 is outside this probe. The database owner bypasses every policy and grant, so whoever holds the app's connection string can edit this log as they can every table. D1 answers that.
