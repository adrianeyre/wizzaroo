# A3: Passkeys and the QR hand-off

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #205 (A3), answering [H16](../../product-requirements-document/pen-testing.md#h16-the-passkey-hand-off-answers-anyone-holding-the-code--low). It names exploit chains, so it is kept private on the same terms as the PRD. How a finding is filed, triaged and verified is in [the findings workflow](../README.md).

The rules probed are section 8 of [`wizzaroo.md`](../../product-requirements-document/wizzaroo.md#8-accounts-and-roles) (passkeys, adding a passkey on a phone, and the Security notice email) and [ADR 0036](../../architectural-decision-record/0036-adding-a-passkey-on-a-phone-by-qr-code.md). The code is `src/server/auth/passkey-routes.ts` and `src/server/auth/passkey-hand-off-routes.ts`.

## The probes

Every probe is in `src/integration.test.ts`, under `against a real Postgres › pen test A3: passkeys and the QR hand-off`. A refuted probe is a passing test. A confirmed one is an `it.fails` for the property that should hold, beside a `today_…` test pinning what happens now.

### rpID and origin

The relying party is `PUBLIC_URL`'s host name and the expected origin is its origin, both handed to SimpleWebAuthn on every registration and sign-in.

- `rpID and origin › signs parentA2PasskeyOnly in with their passkey answered for this origin and relying party, the control for the refusals beside it`
- `… › refuses a passkey sign-in answered for another origin, a sibling subdomain, another port or plain HTTP, though its relying party is right`. The answer is signed by the fixture's real key over the right relying party, so only the origin is wrong. Each of `https://evil.wizzaroo.example`, `https://wizzaroo.example.evil`, `https://wizzaroo.example:8443` and `http://wizzaroo.example` gets 400 and no cookie.
- `… › refuses a passkey sign-in signed for another relying party, though its origin is right`: `evil.wizzaroo.example`, `example` and `wizzaroo.example.evil` all get 400.
- `… › refuses a passkey added from a hand-off code for another origin or another relying party, and adds one made for this origin and relying party`. A wrong origin, a wrong relying party, or both, all get 400 and leave no passkey row. The same construction made for this site is added (201), so the refusals come from the checks and not from the test.

A sibling subdomain matters because every subdomain of `adrianeyre.co.uk` is the same site (H11). A passkey made on one of them is refused here.

### Challenge expiry and single use

Each challenge is a row in `passkey_challenges`, bound to the adult it was made for (or to nobody, for signing in) and alive for 5 minutes. It is deleted when it is answered.

- `challenge expiry and single use › refuses a passkey answer once its challenge has expired, signing in and adding from a hand-off code alike`
- `… › refuses a passkey answer given a second time, signing in and adding from a hand-off code alike`. A replayed sign-in answer gets 400. So does a challenge that already added a passkey, answered again under a fresh code.
- `… › refuses a challenge asked for to sign in, to add a passkey, or for another adult's hand-off code, when it is answered for something else`

Observed, not a weakness: on the routes that add a passkey, a wrong answer rolls back its transaction, so the challenge (and the hand-off code) survive it and can be answered again within their lifetime. A sign-in challenge is spent even by a wrong answer. Since a holder can ask for fresh challenges freely, keeping a refused one gains them nothing.

### Sign count

- `sign count › refuses a passkey answer whose sign count hasn't gone up since the last one, as a cloned passkey's would, and keeps the higher count`. With `teacherAYears5And6`'s stored count set to 5, an answer counting 3 or 5 gets 400 and one counting 6 signs in, leaving 6 stored.
- `… › keeps signing in a passkey that never counts, as WebAuthn allows an authenticator with no counter to`

An authenticator that always reports 0, as synced passkeys and the fixtures' soft authenticator do, has no clone detection. WebAuthn allows that, and refusing such passkeys would refuse most phones, so it isn't a weakness. A counter that goes backwards is refused, but the passkey isn't flagged and nobody is told. That belongs with A3-2.

### The hand-off token

- `the hand-off token › refuses a hand-off code once it has expired, once a newer one has replaced it, and once it has added a passkey`. Both the options and the add are refused for a used code, and the adult is left with no hand-off row.
- `… › refuses an unknown, expired, replaced or used hand-off code, or one belonging to teacherADeactivated, with one and the same answer`. All five get the same status and byte-for-byte the same body, so a wrong code is no oracle.
- `… › keeps at most one live registration challenge for a hand-off code, however often its options are asked for` (`it.fails`), beside `today_answers a hand-off code's registration options as often as anyone holding it asks, writing a challenge each time and leaving the code to add a passkey`. Three requests write three live challenges, and the code still adds a passkey afterwards. **#238**
- `… › gives a caller holding only a hand-off code no email address or account id` (`it.fails`), beside `today_gives a caller holding only a hand-off code the account's email address, its id and the ids of its passkeys`. With nothing but the code, the options name `parentA2PasskeyOnly`'s email address as `user.name`, their account id (base64url) as `user.id`, and their passkey's credential id in `excludeCredentials`. **#238**

Observed, not filed: a code outlives sign-out of the browser that made it, until it expires or is replaced. ADR 0036 gives a 10-minute lifetime and replacement as the ways it ends, and making a new code is the way to kill one that was seen. Signing out isn't one of them. It's noted here so A1 sees it beside session revocation (H3).

### Telling the account's owner

- `telling the account's owner › emails coParentA1 when a passkey is added in their browser, added from a hand-off code, or removed` (`it.fails`), beside `today_tells coParentA1 nothing when a passkey is added in their browser, added from a hand-off code, or removed, and records each only in the Audit Log`. `coParentA1`'s address is confirmed, so a security notice could go to it. None does. The three changes are each written to the Audit Log (`passkey.added`, `passkey.added` with detail `hand-off`, `passkey.removed`), which only the Admin reads. **#239**

## Fixtures used

| Handle                | Id                                     | Used for                                                                                 |
| --------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------- |
| `coParentA1`          | `e2000000-0000-4000-8000-ad0000000012` | Making hand-off codes, adding and removing passkeys, the notice probe                    |
| `parentA2PasskeyOnly` | `e2000000-0000-4000-8000-ad0000000021` | Their fixture passkey for the rpID, origin and challenge probes; the options' disclosure |
| `parentB`             | `e2000000-0000-4000-8000-ad0000000031` | Another adult's hand-off challenge; an expired code                                      |
| `teacherAYears5And6`  | `e2000000-0000-4000-8000-ad0000000003` | Their fixture passkey for the sign-count probe                                           |
| `teacherADeactivated` | `e2000000-0000-4000-8000-ad0000000005` | A hand-off code belonging to a deactivated adult                                         |

**When:** the probes run in the gated suite, not on the shared pen-test deployment. Each run loads the fixtures from a seed of the test's own into a database of its own (`pen_test_a3`) in the suite's Postgres container, and the container is destroyed when the run ends. So the times are those of each gated run, and nothing a tester on the deployment sees is changed.

**What they change, in that database,** beyond [the expected state changes](../credentials-package.md#expected-state-changes): `teacherAYears5And6`'s passkey sign count is set to 5, then 6. A hand-off code is inserted directly for `teacherADeactivated`. Hand-off codes are expired by setting `expires_at` in the past. `coParentA1`'s `passkey_challenges` rows are deleted before counting them. `coParentA1` gains passkeys from soft authenticators made in the test. No fixture is loaded again.

To reproduce a probe on the deployment instead, sign in with the harness as the fixture named above. Every request and body is in the test, and each finding's steps say which `PEN_TEST_…` variable it needs.
