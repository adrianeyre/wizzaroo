# I1: HTTP hardening and the error handler

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #219 (I1). It names exploit chains, so it is kept private on the same terms as the PRD. How a finding is filed, triaged and verified is in [the findings workflow](../README.md).

I1 answers [H7](../../product-requirements-document/pen-testing.md#h7-unexpected-errors-return-the-failing-sql-and-its-parameters--medium) (unexpected errors return the failing SQL and its parameters) and [H12](../../product-requirements-document/pen-testing.md#h12-http-hardening-is-absent--medium) (no helmet, CSP, HSTS, frame options or nosniff). The rules probed are the PRD's checks every scope issue carries: "Every refusal comes from a closed set. No route answers a well-formed request with a 500, and no error message, driver text or stack reaches the caller", and "Nothing is left to a collaborator to bound". The code is `src/server/http-server.ts`, which registers no `setErrorHandler`, no security headers and no `bodyLimit`, and Fastify's own `fallbackErrorHandler` (`node_modules/fastify/lib/error-handler.js`), which sends `error.message` and `error.code` on a 5xx.

H12's `trustProxy` half is I4's in the scope partition, and isn't probed here.

## Fixed, unverified

All three are fixed in `src/server/http-hardening.ts`, unverified by a retest on the deployment. Each `it.fails` above now passes as a plain `it`, and each `today_…` probe is a `(regression)` test of the fixed behaviour.

- **#310:** a `setErrorHandler`, set before any plugin or route. A refusal (4xx) is answered as Fastify answers it. Anything else answers `500` with one body, `{"statusCode": 500, "error": "Internal Server Error", "message": "Something went wrong. Please try again."}`, the same for every route and cause. The error goes to the log alone, through D3's serializer, which withholds its message (#282), with its SQLSTATE beside it as before.
- **#311:** every answer, a 401, a 404 and a 500 included, carries `Content-Security-Policy` (scripts from the origin alone, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'none'`), `Strict-Transport-Security: max-age=31536000; includeSubDomains`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, a `Permissions-Policy` refusing the camera, microphone, location, payment and USB, and `same-origin` opener and resource policies. HSTS is set by the app, so the repository records it whatever the Cloudflare zone does. Styles keep `'unsafe-inline'` for the pages' one inline `<style>`, and voice-over audio plays from `blob:` URLs.
- **#312:** every route reads 16 KiB at most. The four CSV routes and `POST /api/play/events` keep 1 MiB. A body whose `Content-Length` is over its route's limit is refused `413` before the reach check looks the caller up, so a route that needs a credential refuses an oversized body with no credential too.

## The probes

Every probe is in `src/integration.test.ts`, under `against a real Postgres › pen test I1: HTTP hardening and the error handler`. A refuted probe is a passing test. A confirmed one is an `it.fails` for the property that should hold, beside a `today_…` test pinning what happens now.

Two servers are built over the fixtures. **The fixture server** is the app over a database of its own (`pen_test_i1`) with the fixtures loaded, listening on a port, with `admin`, `coParentA1` and `familyDeviceA1` signed in through the credentials package's harness. **The refused-password server** is the same app over the same database with a wrong password in its connection string, so Postgres refuses every connection it opens: the shape of a rotated secret, or of the database being unreachable.

Every route is driven from one table of 80 entries: each method and path the server registers, with a body that passes its schema and an unknown id for each path parameter. `names every route the server registers in I1's route table, so the sweep drives every route` compares the table with Fastify's own route tree, so a route added later fails it until the table names it.

### I1-1: a 5xx sends the failing query, its parameters, or the driver's text

There is no `setErrorHandler`, so Fastify's default sends `{ statusCode, code, error, message }` with the thrown error's own `message` and `code`. Drizzle wraps every failing statement in `DrizzleQueryError`, whose message is `Failed query: <SQL>\nparams: <values>`. A failure before any statement, such as `pool.connect()` when a transaction opens, isn't wrapped, so the driver's message and its SQLSTATE `code` go out as they are.

**NUL bytes first.** D4 found that a NUL byte in any text field reaches Postgres and makes 11 fields on 9 routes answer 500 (#294). I1 records what those bodies hold:

- `the 5xx body › today_answers a NUL byte, first of all at sign-in with no credential, with a 500 whose message is the failing query, its table and column names and its parameters, the typed value and a Picture Password hash among them`, beside
- `… › answers a NUL byte that reaches Postgres with a body that holds no query, parameter, table name or driver code` (`it.fails`).

| Caller           | Route and field                                    | The 500's `message`                                                                                                                                                   |
| ---------------- | -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| None             | `POST /api/sign-in` `email`                        | `Failed query: select "id", "password_hash", "totp_secret" from "users" where ("users"."email" = $1 and "users"."deactivated_at" is null)` and the typed email        |
| `coParentA1`     | `POST /api/children` `nickname`                    | The `insert into "children"`, with the Family's id, the School's id, the typed nickname and the server's `pbkdf2-sha256$100000$<salt>$<hash>` of the Picture Password |
| `familyDeviceA1` | `PUT /api/play/children/:childId/character` `name` | The `insert into "characters"`, with Ada's id and the typed name                                                                                                      |

Each body is exactly `statusCode`, `error` and `message`, with no `code` and no stack.

- `… › answers every route's unexpected error with one body that holds no query, table name, driver message, code or database user` (`it.fails`).

In production that names the database's host as the app sees it.

So any caller learns the SQL of every credential check, that sign-in and device tokens are kept as unsalted SHA-256 (`params` is the hash of the cookie they sent), the names of the tables and columns that hold password hashes and TOTP secrets, and the database user's name. A signed-in caller also gets back values the server made, such as the Picture Password hash. The parameters of every failing query also go to the container log (D3's #282).

### I1-2: no security response headers

`src/server/http-server.ts` registers no helmet and sets no header of its own. `@fastify/static` sends `Cache-Control`, `ETag`, `Last-Modified` and `Accept-Ranges`; Node sends `Date`, `Connection` and `Keep-Alive`. Nothing else.

- `response headers at the E1 origin › measures the app's own response headers, which the E1 stand-in for cloudflared passes on without adding, hiding or rewriting one` (passes). `docker-compose.pen-test.yml` holds no `add_header`, `more_set_headers`, `proxy_hide_header`, `proxy_pass_header`, `proxy_ignore_headers` or `sub_filter`, and sets `server_tokens off`. So the headers measured at the app are the ones the E1 origin, `http://localhost:43310`, sends, plus the stand-in's own `Server: nginx`, which the [deployment page](../deployment.md#the-cloudflared-stand-in) says to ignore.
- `… › today_sends no content security policy, HSTS, frame options, nosniff, referrer, permissions or cross-origin policy on any page, script or API answer`, over nine answers: the game page, the Parent dashboard, a script, `/health`, the Admin's `/api/me`, a Family Device's `/api/play/family`, a 401, a 404 and a 500. Beside it,
- `… › sends nosniff, HSTS and a referrer policy on every answer, and a content security policy that refuses framing on every page` (`it.fails`).

What that leaves open, read and not exercised:

- **Framing.** Nothing stops a page from framing the Parent and Admin dashboards. The sign-in cookie is `SameSite=Strict`, so a cross-site frame is signed out. A same-site one, a page on any other `adrianeyre.co.uk` name (H11, #247), loads the Admin's dashboard signed in and can overlay it to steer a click, such as confirming a deletion.
- **No second wall behind the code.** No CSP means any script injection, of which D4 and H19 found none, would run with the dashboard's full reach. `nosniff` is absent too. The 404 echoes the path (`Route GET:/api/… not found`), as `application/json`, which browsers don't sniff today.
- **HSTS** comes, if at all, from the Cloudflare zone's settings, which aren't in the repository and the stand-in doesn't reproduce. Nothing in the repository sets or records it.
- **CORS is refuted.** `… › grants no other origin a cross-origin read, a preflight or credentials, a same-site subdomain included` passes: `GET /api/me` with the Admin's cookie from `https://pen-test.example` and from `https://another.adrianeyre.co.uk` gets 200 and no `Access-Control-*` header, and their `OPTIONS` preflights get 404. Section 9 of `wizzaroo.md` records the decision as "one origin and no CORS".

### I1-3: every route reads up to 1 MiB

No route sets `bodyLimit`, so Fastify's default of 1,048,576 bytes applies to all 58 that take a body. The limit is checked against `Content-Length` and the bytes read, before any handler runs, so the refusal can't tell the caller anything.

- `the body limit on each route › today_keeps Fastify's 1 MiB body limit on every route that takes a body, refusing one byte more with 413 before the caller is known`. With no cookie, each route answers something other than 413 to exactly 1,048,576 bytes of JSON, and 413 `FST_ERR_CTP_BODY_TOO_LARGE` to 1,048,577. Beside it,
- `… › refuses a 64 KiB body with 413 on every route but the CSV uploads, their previews and a Family Device's upload` (`it.fails`). 64 KiB is the probe's yardstick, not a decided figure: it is far beyond any request those 53 routes' schemas are written for, a sign-in, a 6-character code or a name. The five excluded routes carry a CSV of up to 1,000,000 characters or 100 events.

What it means, by arithmetic and not by load: every unauthenticated route, sign-in, the reset routes, the Invite and passkey routes and the bodiless `POST /api/sign-out` and `POST /api/passkey-sign-in-options`, parses up to 1 MiB of JSON per request before deciding anything. Fields with no `maxLength`, such as every email address (D4-2, #295) and every password, are bounded by this limit and nothing else, so a 1 MiB email reaches a Postgres lookup and a 1 MiB password reaches argon2. Volume testing is out of scope; the rate is H8's (I2a).

### Disclosure: versions, commits, paths and table names

- `what a response discloses › discloses no version, commit, file path or stack in any answer, as any caller, from any route, whatever went wrong` (passes). It sweeps every route as nobody, every `GET` route as `admin`, `coParentA1` and `familyDeviceA1`, every route against the refused-password server, the NUL-byte answers and the nine header samples. None holds the `HEAD` commit or its 7-character short form, `process.version`, Fastify's version, `PostgreSQL`, the repository's or the client's path, `node_modules`, `file://`, a stack frame, or a `Server` or `X-Powered-By` header.
- `… › names no table in any answer below 500, so table names reach a caller only through a 5xx body` (passes): every string value of every answer below 500 is free of a quoted table name read from `pg_tables`.

Read from the code and not probed, since the gated run serves a stand-in client: the built client shows its own `package.json` version (`1.0.0`) in the footer, by design (`vite.config.ts` defines `__APP_VERSION__`), and the service worker carries a 12-character hash of the built files. Neither is a dependency's version or a commit. Vite writes no source maps by default and `vite.config.ts` doesn't turn them on.

**When:** the probes run in the gated suite, not on the shared pen-test deployment. Each run loads the fixtures from a seed of the test's own into a database of its own (`pen_test_i1`) in the suite's Postgres container, signs the fixtures in with the credentials package's harness (`signInAsPenTestFixture`) against a server of its own, and the container is destroyed when the run ends. So the times are those of each gated run, and nothing a tester on the deployment sees is changed.

**What they change, in that database,** beyond [the expected state changes](../credentials-package.md#expected-state-changes): failed sign-ins for `i1-probe@pen-test.example` and for `parentA1`'s address with a NUL byte are in the Audit Log, and `POST /api/passkey-sign-in-options` leaves unused passkey challenges, which expire. Every NUL-byte probe answers 500 and rolls its transaction back, and every other route is sent an unknown id or refused, so no fixture changes. The refused-password server reaches nothing.

To reproduce a probe on the deployment instead, sign in with the harness as the fixture named above; every request and body is in the test. To see the every-route probe's 500s there, stop Postgres (`pen_test_compose stop postgres`) and send any route a request; the six transaction-first routes then send a network error rather than `28P01`. `pen_test_compose start postgres` brings it back.
