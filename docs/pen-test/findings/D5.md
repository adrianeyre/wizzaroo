# D5: A whole-schema sweep of policies and grants

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #214 (D5). It names how the second wall can be walked round, so it is kept private on the same terms as the PRD. How a finding is filed, triaged and verified is in [the findings workflow](../README.md).

- **The rule probed:** [ADR 0027](../../architectural-decision-record/0027-row-level-security-through-a-reach-role.md). Every table holding a Child's or an adult's data has row-level security on, with a policy for the `wizzaroo_reach` role. The role gets grants table by table, never by default. The functions that look a Teacher up are `SECURITY DEFINER` with a fixed `search_path`, and answer only yes or no. Section 9 of `wizzaroo.md` makes the policies the second wall, so a query that forgets its filter still can't cross a Family or a School. [Keeping Families apart in Postgres](../../guide/security-and-backups.md#keeping-families-apart-in-postgres) describes it.
- **Read from `pg_catalog`, not from migration text:** `pg_class` (each relation's `relrowsecurity` and `relforcerowsecurity`, and its ACL through `aclexplode`), `pg_attribute` (column ACLs), `pg_policy` (each policy's command, roles and expressions), `pg_roles` and `pg_auth_members` (the reach role), `pg_namespace` and `pg_database` privileges, `pg_default_acl`, and `pg_proc` (`prosecdef`, `proconfig`, owner and result type).
- **What the routes need** was read from the code: every `insert`, `update` and `delete` in `src/server`, with whether it runs on a `reachDatabase` inside `runWithinReach` or on the owner's `database`. An upsert (`onConflictDoUpdate`) needs `UPDATE` as well as `INSERT`. A cascade from a foreign key needs no grant, since Postgres runs it as the table's owner.
- **H entries:** the opening register names none for D5, so this note amends none. The sweep bears on three entries other scopes answer. Unforced row-level security is part of [H4](../../product-requirements-document/pen-testing.md#h4-the-app-connects-to-postgres-as-its-superuser--high), which D1 (#210) confirmed as part of #273. The `family_parents` and `invites` writes below are routes into [H5](../../product-requirements-document/pen-testing.md#h5-row-level-security-checks-rows-not-columns--high), also D1's; D1 proved the `family_parents` one end to end as #275. The `admin_access_logs` grant is [H6](../../product-requirements-document/pen-testing.md#h6-some-admin-reads-are-not-logged-and-the-log-can-be-changed--high), which D2 confirmed as #269.
- **Probes:** the `pen test D5: a whole-schema sweep of policies and grants` block in `src/integration.test.ts`, in the gated run against a real Postgres. It migrates a database of its own, `pen_test_d5`, and loads [the fixtures](../fixtures.md) into it once. The catalog probes read that database. The behaviour probes run within the reach of `admin`, `teacherAYear3`, `teacherBYear3`, `parentA1`, `parentB` and `familyDeviceA1`. Nothing a probe does is committed: a temporary table is dropped when its transaction ends.

## Row-level security, table by table

`pg_class` holds 29 relations in the `public` schema, all ordinary tables: no view, materialised view, foreign or partitioned table, and no sequence, since every key is a `uuid`. Every one has `relrowsecurity` on. That matches the table list the existing test, "turns row-level security on for every table in the database, each with a policy", pins by name.

**Forced: confirmed as a documented decision.** `relforcerowsecurity` is off on all 29, so the owner's connection passes no policy. ADR 0027 considered forcing it on the owner and turned it down, since the credential checks before anyone is known read across every account. It records no date when that stops being true. D1 confirmed this under H4 as part of #273, so it is not filed again here.

- `today_ leaves row-level security unforced on every table, so the owner's connection passes no policy`
- `it.fails`: `forces row-level security on every table, so the owner's connection is held to the policies too`

## The grants

**Everything but the table grants: refuted.** Read from the catalog:

- every table is granted to `wizzaroo_reach` and to no other role, PUBLIC included;
- nothing beyond `SELECT`, `INSERT`, `UPDATE` and `DELETE` is granted: no `TRUNCATE`, `REFERENCES` or `TRIGGER`, and no column grants;
- the reach role is `NOLOGIN`, with no superuser, `BYPASSRLS`, `CREATEDB`, `CREATEROLE` or `REPLICATION`;
- it is a member of no role, and is granted to the owner alone;
- it has `USAGE` on `public`, and can create nothing in it or in the database;
- it has no way into the `drizzle` schema, where the migration journal lives;
- `pg_default_acl` is empty, so a new table is granted nothing until its migration says so, as ADR 0027 asks.

Its `TEMPORARY` privilege on the database comes from PUBLIC, as Postgres gives every database by default. That matters to probe 10.

- `grants tables to the reach role alone, never to PUBLIC, with no column grants and nothing beyond SELECT, INSERT, UPDATE and DELETE`
- `keeps the reach role a NOLOGIN role with no superuser, BYPASSRLS, CREATEDB, CREATEROLE or REPLICATION, a member of no role, and granted to the owner alone`
- `lets the reach role use the public schema and create nothing in it, keeps it out of the drizzle schema, and grants a new table nothing by default`

**Wider than the routes need: confirmed.** 26 of the 29 tables grant the reach role all four commands. Against what the code makes within reach:

Where each write the routes do make comes from, for the tables that need more than `SELECT`:

- `users`: the Admin's reach creates Teachers (`createTeacher`), deactivates adults and deletes a Family's Parents; an adult's own reach changes their password, two-factor and email.
- `sign_ins`: `markSignInTwoStep` within reach, and deleting other sign-ins on a password change, a deactivation and making a Family Device. A sign-in is only ever inserted by the owner.
- `invites`: the Admin's reach replaces a Teacher's pending Invite (`createInvite`). Accepting an Invite runs as the owner.
- `families`, `children`, `play_events`: `deleteFamily` and `deleteChild` within the Admin's reach. A Parent's reach adds a Child; a Family Device's sends events.
- `characters`, `room_showcases`, `child_teacher_locks`, `deletion_requests`, `totp_setups`: upserts, so `INSERT` and `UPDATE`.
- `teachers`, `teacher_year_groups`, `schools`: the Admin's reach.
- Credentials and codes (`email_address_checks`, `passkey_challenges`, `passkey_hand_offs`, `passkeys`, `recovery_codes`, `password_resets`, `pending_sign_ins`): the adult's own reach, and the Admin's on a deactivation. Password resets and pending sign-ins are only ever made by the owner.

So 20 tables grant writes no route makes, and `admin_access_logs` grants two more. The policies are what stands behind each of these grants, and most are `FOR ALL` with no `WITH CHECK`, so the grant is the only other layer. What each extra write would let a reach do, given a query bug inside its transaction, the case ADR 0027 builds the second wall for:

- **`family_parents` `INSERT`:** `family_parents_within_reach` checks only the Family, so a Parent's reach can add any adult who has no Family to its own: every Teacher, and the Admin unless they are also a Parent. `users_within_reach` then shows it that adult's row, with its `password_hash` and `totp_secret`, and lets it change them. That is H5's second bullet, which D1 carried to a sign-in as the Admin (#275). The grant is a second place to close it: no route inserts into `family_parents` within reach. Fixed, unverified (#275): the reach role now holds only `SELECT` on `family_parents`, so 19 tables are left.
- **`invites` `UPDATE`:** `invites_within_reach` reaches a co-Parent's Invites, so a Parent's reach could give a co-Parent's pending Invite a token it knows and a later expiry.
- **`sign_ins`, `password_resets` and `pending_sign_ins` `INSERT`:** each policy checks only that the row is the caller's own. A reach could mint its own sign-in, marked two-step, or a reset with a token it knows. Today only the owner makes these, before anyone is known.
- **`play_events` `UPDATE` and `kept_game_unlocks` writes:** a Family's reach rewrites its own play history, which Check History and Mastery are worked out from (ADR 0004).
- **`school_parents`, `families` `INSERT`, `teachers` `DELETE`, `teacher_year_groups` `UPDATE`:** their policies keep writes to the Admin, so the extra grant reaches only the Admin.
- **The `DELETE`s on `characters`, `room_showcases`, `child_teacher_locks`, `deletion_requests` and `family_devices`:** a Family's reach could remove its own rows, a Teacher's a Child's Teacher locks, and a Parent's a Deletion Request already made.

Filed as #298 (medium: a boundary with no defence in depth). `admin_access_logs` is #269, filed by D2, and is not filed again. Its pair is kept apart from the 20, so each `it.fails` turns green with its own fix.

_Fixed, unverified (#298):_ migration 0053 revokes from `wizzaroo_reach` every command in the last column above but one, so each table grants only what a route makes on it within reach. The table missed one command a route makes: spending a recovery code locks the adult's codes with `SELECT ... FOR UPDATE` within their reach (#255), and a locking read needs `UPDATE`, so `recovery_codes` keeps it and 18 tables are narrowed. Otherwise the table held, re-read against the code after #275 and #276. A later route that needs a command grants it in its own migration. `children` now grants `SELECT` column by column, without the Picture Password hash (#304, F2).

- `grants the reach role none of the writes on 18 tables that no route makes within reach, on the table or any column of it (regression)` (the `today_` probe, 20 tables before #275, 18 once `recovery_codes` kept `UPDATE`)
- `grants the reach role on each table only the commands a route makes within reach` (the `it.fails`, now passing)
- `today_ grants the reach role UPDATE and DELETE on admin_access_logs, which no route makes` (#269)
- `it.fails`: `grants the reach role only SELECT and INSERT on admin_access_logs` (#269)

The table of what routes make was read from the code, not measured. If it is wrong, narrowing the grants to it fails the integration test of the route that needs the command, so the fix can't remove a grant a route uses without the suite saying so.

## The SECURITY DEFINER functions

Six functions in the schema are `SECURITY DEFINER`, and no function anywhere else is. Each is `STABLE`, returns `boolean`, is owned by the owner, sets `search_path=public`, and is executable by PUBLIC, as Postgres gives every function by default:

| Function                                                       | What it answers                                                                                                                   | What it reads past the caller's policies                   |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `wizzaroo_teacher_can_reach_year_group(school_id, year)`       | Is the caller a Teacher at that School, of that Year Group?                                                                       | `teachers`, `teacher_year_groups`                          |
| `wizzaroo_teacher_can_reach_child(child_id)`                   | Is that Child at the caller's School, in one of their Year Groups today?                                                          | `children`                                                 |
| `wizzaroo_teacher_can_reach_family(family_id)`                 | Has that Family a Child in the caller's reach, or no Children and a Parent at the caller's School?                                | `children`, `family_parents`, `school_parents`, `teachers` |
| `wizzaroo_teacher_can_reach_user(user_id)`                     | Is that adult a Parent of a Family in the caller's reach, or a Parent at the caller's School with no Children?                    | `family_parents`, `school_parents`, `teachers`, `children` |
| `wizzaroo_can_see_school(school_id)`                           | Is the caller the Admin, a Teacher there, a Parent there, or the Family of a Child there?                                         | `teachers`, `school_parents`, `children`                   |
| `wizzaroo_can_visit_classmate_room(visitor_id, room_child_id)` | Is the caller a Family Device whose Child may visit that Classmate: same School, which approves visits, same Year, both opted in? | `children`, `schools`                                      |

**A fixed `search_path`: refuted.** All six set it.

- `fixes the search_path of every SECURITY DEFINER function, each owned by the owner and answering yes or no`

**What each answers: refuted as a weakness.** Each answers yes or no about the caller, from the settings the reach transaction set. None takes the caller as an argument. The probe asked every function about every fixture id, and every School and Year Group pair or Child pair, within six reaches:

- `admin`, `teacherAYear3`, `teacherBYear3`;
- `parentA1`, `parentB`;
- `familyDeviceA1`, whose Ada may visit Cara at School A.

Each "yes" was for a row the same reach's own policies already show it. So no function tells a caller anything their policies hide. Every function answered "yes" at least once, so the probe isn't empty.

- `answers each SECURITY DEFINER function's question with yes only for what the caller's own policies already show them, for every reach`

**The caller's own tables: confirmed.** `search_path=public` doesn't name `pg_temp`, and Postgres then searches the session's temporary schema _first_ for tables. Any role with `TEMPORARY` on the database can create one, and the reach role has it from PUBLIC. So within its own transaction, a reach can create a temporary table with the name of a table a policy's function reads, and the function reads that instead. Run in a reach transaction on a new connection, with nothing committed:

- **`teacherAYear3`** creates `teachers` holding themselves at School B. `wizzaroo_teacher_can_reach_year_group`, a `SECURITY DEFINER` function, reads it, and `select id from children` returns School B's Year 3 Child and not their own.
- **`parentA1`** creates `family_parents` linking `admin` and `parentB` to Family A1. `wizzaroo_can_reach_user` has no `search_path` of its own and reads it too. `select id from users` returns both, and with them their password hashes and TOTP secrets.

Every policy helper that reads a table is open to this, `SECURITY DEFINER` or not: the six above and `wizzaroo_can_reach_user`. Making them trust no one's temporary tables means a `search_path` of `pg_catalog, public, pg_temp`, or schema-qualified names in their bodies, and taking `TEMPORARY` away from the reach role.

It needs a statement of the attacker's own inside a reach transaction. A caller who has that can already do more. Read outside the suite against Postgres 18 (PGlite), they can set `wizzaroo.is_admin` themselves, or `RESET ROLE` back to the owner, which is a superuser (#273). So this adds nothing today. It is one more way round the policies once those are closed. Filed as #299 (low: hygiene).

_Fixed, unverified (#299):_ migration 0054 gives the seven `SECURITY DEFINER` functions and `wizzaroo_can_reach_user` a `search_path` of `pg_catalog, public, pg_temp`, and revokes `TEMPORARY` on the database from PUBLIC, so the reach role can't make a temporary table. No route needs one. The probe now makes its temporary tables on the session as the owner before the reach opens, and the policies still show only the real rows.

- `refuses a reach a temporary table, so neither a Teacher's nor a Parent's reach can make one to stand in for the tables the policies' functions read (regression)` (the `today_` probe)
- `keeps a reach's temporary tables out of the tables the policies' functions read` (the `it.fails`, now passing)

## Findings filed

- #298 (medium): the reach role is granted writes no route makes, on 20 tables. Fixed, unverified.
- #299 (low): a reach's temporary tables stand in for the tables the policies' functions read. Fixed, unverified.

## What this round didn't run

The sandbox these probes were written in has no container runtime, so the gated run skipped them there. They were typechecked and linted, and the catalog queries and both temporary-table chains were run outside the suite against the migrations replayed into PGlite 0.5.16, which is Postgres 18.6 compiled to WebAssembly. Both gave the results the probes pin. The verdicts rest on that and on reading the code until the gated run is executed on a host with Docker and its output posted on #214. Nothing was exercised against the pen-test deployment itself.
