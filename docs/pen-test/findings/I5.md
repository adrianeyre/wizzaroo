# I5: Email

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #224 (I5), which answers [H18](../../product-requirements-document/pen-testing.md#h18-staff-supplied-names-reach-email-headers--low): staff-supplied names in email headers, what a hostile School, Teacher or Parent name puts in front of a Parent, and where the links in an email come from. This note names exploit chains, so it is kept private on the same terms as the PRD.

- **Trust boundary:** what staff type, and what a request's headers say, against the email Wizzaroo sends a Parent from its own address. Section 8 of `wizzaroo.md` ("Accounts and roles") has the Admin create Schools and Teachers, and the Admin and Teachers create and invite Parents, by form or by CSV ("Bulk creation"), and keeps a Teacher's reach read-only ([ADR 0026](../../architectural-decision-record/0026-schools-and-teachers.md)). Its "Email" section sends Invites, password resets, email address checks and security notices to Teachers and Parents, with a Parent Invite that "names the School". [ADR 0002](../../architectural-decision-record/0002-self-hosted-behind-a-cloudflare-tunnel.md) leaves Wizzaroo's own sign-in as the only gate, so a link in one of those emails is a credential.
- **Code:** `src/server/email/emails.ts` (every email, with the School's name in two subjects, `:103` and `:119`, and the adult's name in each Invite's greeting), `src/server/email/send-email.ts` (the one Nodemailer sender, which hands `to`, `subject` and `text` over as they are), `src/server/auth/email-address.ts` (the address shape), `src/server/people/create-people.ts` (`readPersonName`), the name schemas in `src/server/people/people-routes.ts:142` and `src/server/schools/school-routes.ts:56`, `src/server/bulk/csv.ts` (quoted cells keep their line breaks), and every builder of an email's link: `src/server/people/invites.ts`, `src/server/auth/password-reset-routes.ts`, `src/server/auth/email-address-check-routes.ts` and `src/server/family-devices/family-device-routes.ts`.
- **Documented behaviour:** [Email](../../guide/email.md) and [Signing in](../../guide/signing-in.md).
- **Probes:** the `pen test I5: email` block in `src/integration.test.ts`, in the gated run against a real Postgres. A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now. A refuted probe is a passing test. The block runs its own server on a database of its own, loaded with [the fixtures](../fixtures.md) and signed in to as fixture identities through [the credentials package](../credentials-package.md). Its `PUBLIC_URL` is `https://wizzaroo-i5.example`, which is neither the address it listens on nor any `Host` a probe sends. Every email goes through the real `buildEmailSender` into a Nodemailer transport that keeps the message Nodemailer compiles for SMTP: its envelope recipients and its raw RFC 5322 text, headers and all. So a probe reads the headers a mail server would be handed, not the `Email` object they were built from.

## Header injection: refuted

**The `Subject`.** Two emails put a School's name in their subject: the Parent Invite (`<School> invites you to Wizzaroo`) and the Teacher Invite (`You're invited to Wizzaroo as a Teacher at <School>`). A School's name is any text of up to 80 characters with something other than whitespace in it (`pattern: "\\S"`), trimmed at its ends only, so CR and LF in the middle are kept. The Admin, the only one who names a School, made one called `I5 School\r\nBcc: i5-bcc@attacker.example\r\nX-I5-Injected: yes`, then a Parent and a Teacher there, each with an emailed Invite.

Nodemailer turns each CR LF in a header value into a space and folds the long line with a CR LF followed by a space, which is a continuation and not a new header. Each message has exactly the eight headers Wizzaroo always sends (`From`, `To`, `Subject`, `Message-ID`, `Content-Transfer-Encoding`, `Date`, `MIME-Version` and `Content-Type`), one `Subject`, which reads `I5 School Bcc: i5-bcc@attacker.example X-I5-Injected: yes invites you to Wizzaroo` once unfolded, no `Bcc`, `Cc` or `X-I5-Injected`, and only the invited adult as its envelope recipient. The text and the From address are no header vector: the text is the body, and From is a constant (`send-email.ts:7`).

- `keeps a School name's CR and LF out of a Parent's and a Teacher's Invite headers: one Subject line, no added header and no added recipient, even for a name stored before such names were refused`, which was `keeps a School name's CR and LF out of a Parent's and a Teacher's Invite headers: one Subject line, no added header and no added recipient`. Since #321 the Admin can't type such a name (the probe checks the 400), so the probe puts it in the database, as a name stored before the fix would be.

**The `To`.** The only other staff-supplied field in a header is the address. `isEmailAddress` (`email-address.ts:1`) refuses whitespace anywhere, and `normaliseEmail` trims only the ends. So `…@pen-test.example\r\nBcc: i5-bcc@attacker.example`, or the same with a bare LF, is refused 400 when the Admin or a Teacher types it in the form. As a quoted cell in a Teacher's CSV upload it is skipped as a row with a bad address, with nothing created. Nothing is handed to Nodemailer either way.

- `refuses an email address holding CR or LF, so a typed address can't carry a header into To`

## An address Nodemailer reads as another mailbox: confirmed

The shape is `^[^\s@]+@[^\s@]+\.[^\s@]+$`: exactly one `@`, no whitespace, and a dot after it. That allows a comma, a semicolon, a colon and angle brackets. Nodemailer reads the `to` it is given as an address list, so it doesn't deliver to the string Wizzaroo checked:

| Address Wizzaroo stores                | Nodemailer delivers to  |
| -------------------------------------- | ----------------------- |
| `x,attacker@evil.example`              | `attacker@evil.example` |
| `x:attacker@evil.example;`             | `attacker@evil.example` |
| `a<attacker@evil.example>`             | `attacker@evil.example` |
| `parent@home.example,b.c`              | `parent@home.example`   |
| `parent@home.example;attacker.example` | `parent@home.example`   |

Only one `@` gets through, so an address names at most one mailbox, and no second recipient or header can be added (refuted above). But the mailbox needn't be the address. `teacherAYear3` made a Parent with the address `i5-shadow-<uuid>,parent-a1@pen-test.example`. Wizzaroo looked it up and found it free, since no account has that exact string, which is `parentA1`'s own address with a prefix. It created the login and emailed its Invite. Nodemailer's envelope and `To` held `parent-a1@pen-test.example`: the Invite went to parentA1's mailbox. Opening it there set a password on the new login and marked its address confirmed, because an emailed Invite proves the address it was sent to (`invite-routes.ts:64`). A reset asked for the new address after that went to parentA1's mailbox too.

Consequence. The rule that one address is one account (`findUserIdByEmail`, checked across every account) and the rule that only a confirmed address counts ([Email](../../guide/email.md)) are both kept on the string, not on the mailbox it delivers to. A Teacher can make a second login for an existing Parent's mailbox without either rule noticing. They can put it in any Family in their reach, and through it send that Parent Wizzaroo email with the text of #321 in it, while the Admin's and the Teacher's lists show an address that doesn't look like the Parent's. The Admin can do the same, and so can a CSV upload by either, which checks addresses with the same shape. A Parent's own email change goes through the same `isEmailAddress` (`email-address-check-routes.ts:158`), although that field isn't staff-supplied. Nothing crosses a boundary the Teacher couldn't already cross by typing an address of their own (#264). That is why this is low. Filed as #322 (low).

- `refuses the address \`i5-shadow-…,parent-a1@pen-test.example\` in the Parent and Teacher forms, both CSV uploads and their previews, the email-address check and a reset request, so no login is made for it and parentA1's mailbox gets nothing (regression)`, which was `today_ delivers the Invite for an address a Teacher typed as \`i5-shadow-…,parent-a1@pen-test.example\` to parentA1's mailbox, marks that new login's address confirmed once it is opened there, and sends its reset links there after`
- `refuses an email address that Nodemailer would deliver to a mailbox other than the one typed`, which was an `it.fails`, and now tries each address in the table above too

The fix (_fixed, unverified_) does both. `isEmailAddress` takes only a dot-atom local part and a domain of letters, digits, hyphens and dots, so no quote, whitespace, control or `, ; : < > ( ) [ ] \ "` gets through, and then has Nodemailer's own `addressparser` read the address: it must come back as exactly one mailbox, with no name, equal to the address typed. The 254-character limit (#295) stays. Every place that takes an address already went through `isEmailAddress`, so the forms, both CSV uploads and their previews, and the email-address check all refuse such an address with the 400, or the skipped row, any other bad address gets.

## A hostile Parent or School name: confirmed

**Who writes what a Parent reads.** A Parent's own Invite opens `Hello <name>,`, with the name as the Admin or a Teacher typed it, and its second paragraph opens `<School> has invited you to Wizzaroo as a Parent`, with the School's name as the Admin typed it (`emails.ts:110-124`). A resent Invite uses the name stored then. Both names are checked only for being present and short: 60 characters for an adult's name and 80 for a School's, with a non-space character somewhere, trimmed at the ends. A line break, a URL and a Unicode control are all allowed, from JSON in the form and from a quoted cell in a CSV (`csv.ts:9`, which keeps line breaks inside quotes, as spreadsheets save them). Each email is plain text, so nothing is HTML-escaped, and nothing needs to be: what's typed is what the Parent reads.

**A Parent's name, typed by a Teacher.** `teacherAYear3` made a Parent named `Sam,\n\nLog in at https://i5-phish.example now\n\nHi Sam` (51 characters) with an emailed Invite. The Invite reads:

```text
Hello Sam,

Log in at https://i5-phish.example now

Hi Sam,

Pen-test Primary A has invited you to Wizzaroo as a Parent, …

https://wizzaroo-i5.example/parent/#accept-invite=…
```

The phishing link is its own paragraph, ahead of Wizzaroo's. From the CSV upload, a Parent named `Sam\u202E\nLog in at https://i5-phish.example` reached their Invite verbatim, the right-to-left override (U+202E) and the line break included. A right-to-left override reverses how the text after it is shown, so it can make a link look like another one.

**A School's name, typed by the Admin.** A School named `I5 School\n\nPay the trip at https://i5-phish.example` (51 characters) puts `I5 School` as a paragraph of its own and `Pay the trip at https://i5-phish.example has invited you to Wizzaroo as a Parent, …` as the next. That reaches every Parent invited from that School, by any Teacher or the Admin. In the `Subject` the same name is folded onto one line (refuted above), but the link is still there.

Consequence. A Teacher, whose reach is read-only by design (ADR 0026), can put up to 60 characters of their own text into an email Wizzaroo sends from its own address, with a working Invite in it. The text can hold paragraphs, a link of their choosing placed before Wizzaroo's, and controls that disguise a link. Through the bulk upload they can do it a thousand rows at a time, to any address that isn't already an account, or to one that is with #322. The Admin can do the same with 80 characters to every Parent of a School. A Parent has every reason to trust such an email: it is the one that brings them into Wizzaroo. Nothing here reads data or crosses a Family; it lets staff, or whoever holds a staff sign-in, phish Parents in Wizzaroo's own voice. Filed as #321 (low).

- `refuses a Parent's name holding a line break, a link or a right-to-left override, answering 400 from the Parent form and skipping the CSV row, in the upload and its preview, with its reason, so no Invite is sent (regression)`, which was `today_ writes a Parent's name, as a Teacher typed it in the form or a CSV upload, into their Invite verbatim: its line breaks make paragraphs of their own, its link comes before Wizzaroo's, and a right-to-left override goes through`
- `refuses a Teacher's name holding a line break or a link, answering 400 from the Teacher form and skipping the Teachers CSV row, so no Invite is sent (regression)`, new with the fix
- `puts a Parent's name in front of them only as part of one line of plain text, with no line break, no link but Wizzaroo's and no bidirectional control`, which was an `it.fails`
- `refuses a School name or town holding a line break, a link or a bidirectional control when the Admin creates or renames a School, and puts a name stored before in a Parent's Invite only as part of one line (regression)`, which was `today_ writes a School's name, as the Admin typed it, into a Parent's Invite verbatim, its line breaks and link included`
- `puts a School's name in front of a Parent only as part of one line of plain text, with no line break, no link but Wizzaroo's and no bidirectional control`, which was an `it.fails`

Each of those two holds when the Invite has its five one-line paragraphs, no link but Wizzaroo's and no bidirectional control, or when the name is refused and no Invite is sent.

The fix (_fixed, unverified_) does both. When it is typed, `isPlainName` (`src/server/plain-names.ts`) refuses a name holding any control character (line breaks and tabs included), any format character (the bidirectional controls among them, but not the zero-width joiner and non-joiner some names need), a Unicode line or paragraph separator, a URL scheme such as `https://` or a `www.` address. `readPersonName` uses it for the Parent and Teacher forms, the School routes for a School's name and town when it is created or renamed, and both CSV uploads and their previews skip such a row with a reason of their own. The schemas' `pattern: "\\S"` is unchanged; the check is in code, so it answers with its own message. When the email is built, `toOneLine` reduces every name an email carries (the adult's and the School's in each Invite, the School's in a Family join request notice, and a passkey's name) to one plain line: format characters dropped and every run of line breaks, controls and spaces made one space. So a name stored before the fix still can't make a paragraph or turn text around, although its words, a link among them, are still read.

## A hostile Teacher name: refuted

The Admin types a Teacher's name, and nothing renames one later. The probe gave `teacherAYear3` the name `Mr I5\n\nLog in at https://i5-phish.example` in the database, which is what the Admin's form would have stored. Then the Teacher sent Parents each kind of email a Teacher can: an emailed Invite for a new Parent, a resent Invite to `coParentA2Invited`, a password reset to `parentA1`, and a CSV upload's Invite. Four emails went out and none of them holds the Teacher's name or the link. No email builder takes a sender's name (`emails.ts`): a Teacher's own name reaches only that Teacher's Invite.

- `puts no Teacher's name in front of a Parent: not in an Invite, a resent Invite, a reset link or a CSV upload's Invite the Teacher sends`

## Links built from `PUBLIC_URL`: refuted

Every link in an email is built by `new URL(path, publicUrl)`, where `publicUrl` is `PUBLIC_URL`, read once at start (`vars.ts`) and passed to each route. No route reads `request.hostname`, `request.host`, `request.protocol`, the `Host` header or any `X-Forwarded-*` header (besides the cookies, the only request header the server reads is `CF-Connecting-IP`, for the Audit Log), and `trustProxy` is off (H12), so Fastify wouldn't take one either.

The probe sent every request that emails a link with `Host`, `X-Forwarded-Host` and `Forwarded` naming `i5-attacker.example`, and `X-Forwarded-Proto: http`:

1. a reset asked for `parentA1`, signed out;
2. an email address check asked for by `coParentA1`;
3. an emailed Invite for a new Parent, by `teacherAYear3`;
4. `coParentA2Invited`'s Invite resent by `teacherAYear3`;
5. a reset sent to `parentA1` by `teacherAYear3`;
6. a CSV upload's Invite, by `teacherAYear3`;
7. an emailed Teacher Invite, by the Admin;
8. a Teacher CSV upload's Invite, by the Admin;
9. a copied Invite, made by the Admin and opened, which emails an address check;
10. a new Family Device, signed in by `parentA1`, whose notice links to the Parent page.

All ten emails were sent. Their ten links and the copied Invite's link all start with `https://wizzaroo-i5.example/parent/`, and no compiled message holds `i5-attacker.example`. The security notice for a password change has no link, so it isn't in the list.

- `builds every link in every email, and the copied Invite link, from PUBLIC_URL, whatever Host, X-Forwarded-Host, X-Forwarded-Proto and Forwarded say`

## What this round didn't run

The probes were written, typechecked and linted in a sandbox with no container runtime, so the gated run skipped them there. What was run there, with no Postgres: the real `buildParentInviteEmail` and `buildTeacherInviteEmail`, sent through the real `buildEmailSender` into the probe's recording Nodemailer transport. They gave the headers, subjects and envelopes above, the shadow address's envelope and `To`, the hostile names' paragraphs, and the probe's property, which holds for a clean Invite and fails for each hostile one. The real CSV writer and reader were run too: they keep a quoted name's line break and right-to-left override, and pass on the CR LF address that `readEmailAddress` and `isEmailAddress` then refuse. The verdicts above rest on that, on reading the code, and on the probes as written, until the gated run is executed on a host with Docker and its output posted on #224. Nothing here was sent through a real SMTP server or read in a real mail client. How a client shows a right-to-left override, or a URL in plain text, was read and not tried.
