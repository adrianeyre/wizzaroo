# D1: row-level security and database privilege

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #210 (D1) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H4 and H5. It names exploit chains, so it is kept private on the same terms as the PRD.

- **Read against:** the tree at the commit that adds this note, and the [fixtures](../fixtures.md) by handle. No credential appears here.
- **The probes** are the tests under `pen test D1: row-level security and database privilege` in `src/integration.test.ts`. They run against a real Postgres in a database of their own, `pen_test_d1`, load the fixtures again before every probe, and sign in through [the credentials package's harness](../credentials-package.md). A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now; a refuted probe is a passing test.
- **The app's own connection string** in the gated run is the Testcontainers Postgres's, whose user is the image's `POSTGRES_USER`. That is how `docker-compose.yml` makes `wizzaroo`, which the app's `DATABASE_URL` and the backup's `PGUSER` both use, so the probes hold the same privilege a tester holding the deployment's `DATABASE_URL` would.
- **Left to other scope issues:** a whole-schema sweep of grants and policies from `pg_catalog` is D5's. Who may read or change the Audit Log through the app is D6's; D1 only shows the app's connection can empty it. The `restore-drill` container's `trust` authentication is H13's.

## The app's own connection (H4)

D1-1 is fixed, unverified (#273).

`docker-compose.yml` starts Postgres with `POSTGRES_USER: wizzaroo`, which the official image creates as a superuser, and the app's `DATABASE_URL` logs in as that user. The app applies the migrations at boot (`src/server/database.ts`), so it owns every table, and migration 0018 grants it `wizzaroo_reach`. In the probe database `current_user` has `rolsuper` and `rolbypassrls` both true.

A request's reach is `set_config('role', 'wizzaroo_reach', true)` on the app's own session (`src/server/reach.ts`). That is a `SET LOCAL ROLE`, and any statement in the same transaction can undo it:

- **`RESET ROLE`** inside `parentB`'s reach: before it, `select id from children` returns Eli alone; after it, the same query returns all five fixture Children.
- **`ALTER TABLE children DISABLE ROW LEVEL SECURITY`** succeeds, and `parentB`'s reach then reads all five. The probe rolls it back.
- **`COPY d1_program_output FROM PROGRAM 'id -un'`** succeeds and reads back `postgres`: the app's connection runs any shell command in the database container as its `postgres` user, with the data directory under it. The probe rolls the table back.
- **`TRUNCATE audit_log_entries`** succeeds on the app's connection and leaves no entries, and it would through a reach after `RESET ROLE`. The probe rolls it back.

`TRUNCATE` through a reach is refuted: `wizzaroo_reach` holds no `TRUNCATE` grant, so the Admin's reach is refused (`42501`) on `audit_log_entries`, `users`, `children` and `play_events`.

So the second wall holds only against a query that runs inside a reach and doesn't say any of the above. None of these needs anything but SQL text the app sends, so a tester needs an injection or an API bug to reach them, and D4 (H19) sweeps for exactly that. The other path to them is the connection string itself, which the app container, the backup container (below) and any process reading their environment hold.

**Row-level security isn't forced on any table** (`relforcerowsecurity` is false everywhere), so every query the app runs outside `runWithinReach` reads and writes every Family's rows. ADR 0027 decides this for the credential checks before anyone is known and for staff writes once the reach is checked, and rejects forcing it on the owner. It is confirmed as that documented decision. Its fix, a role for those paths that is neither the superuser nor the tables' owner, is the same as D1-1's, so it is filed there rather than on its own. ADR 0027 and `docs/guide/security-and-backups.md` disagree about it: the guide says the owner is used only before anyone is known, and ADR 0027 and the code also use it for staff writes and two staff lookups.

## Columns within a reach (H5)

Each policy that lets a reach change a row is `FOR ALL … USING (…)` with no `WITH CHECK`, so the check on a changed or new row is the same row test, and `wizzaroo_reach` holds `UPDATE` and `INSERT` on whole tables, never on columns. What the API never does is therefore enforced in the API alone.

- **A Parent's reach and its co-Parent's account.** Fixed, unverified (#274). `parentA1`'s reach updates `coParentA1`'s `roles` to `{parent,admin}`, `password_hash` to a hash it chose and `email` to an address it chose: one row each. `POST /api/sign-in` with that address and password answers `204` as `coParentA1`.
- **A Parent's reach and its own roles.** Fixed, unverified (#274). `parentA1`'s reach sets its own `roles` to `{parent,admin}`. Their next sign-in, with their own TOTP, is served `GET /api/admin/families` with every Family. `loadSignedInUser` reads `roles` from the row each request.
- **A Parent's reach and `family_parents`.** Fixed, unverified (#275): migration 0049 takes `INSERT`, `UPDATE` and `DELETE` on `family_parents` from `wizzaroo_reach` and makes its policy `FOR SELECT`, so no reach, the Admin's included, changes who is in a Family. Staff and a Parent agreeing to a join request do that on `wizzaroo_server`'s paths once the API has checked their reach. `parentB`'s reach can't see or change the Admin's `users` row (0 rows). It inserts `{user_id: admin, family_id: familyB}` into `family_parents` (accepted: the policy checks only the Family, and the foreign key to `users` ignores row-level security). `wizzaroo_can_reach_user` now counts the Admin as `parentB`'s co-Parent, so the same update changes the Admin's `password_hash` and clears `totp_secret` (1 row), and `POST /api/sign-in` as the Admin with the planted password answers `204`. That sign-in is not two-step, so staff routes still refuse it, and #242 (H1) then turns on a TOTP of the attacker's own. Any adult with no Family row (every Teacher, and the Admin unless they are also a Parent) can be adopted like this. `family_parents.user_id` is the primary key, so a Parent already in another Family can't.
- **A Family Device's reach and `revoked_at`.** Fixed, unverified (#276): migration 0049 lets a reach with no adult only read `family_devices`. Inserting, revoking and un-revoking need a reach naming a Parent of that Family, and a device's last contact is recorded on `wizzaroo_server`'s path before its reach opens. Migration 0050 holds the same reach to what play changes on `children`: a Child's first Picture Password hash, as `PUT /api/play/children/:childId/picture-password` sets it. Any other column, or a hash already set, is refused (`lets a Family Device's reach set only a Child's first Picture Password, and no other column of a Child, while a Parent's reach still changes them (#276)`). `familyDeviceA1`'s reach (`user_id` empty, Family A1) sets `revoked_at` on its own row (1 row) and clears it on `familyDeviceA1Revoked` (1 row). The revoked device's token, refused `401` before, is then served `GET /api/play/family`. A revoked device's own requests are refused before any reach is opened, so the device that matters is a sibling still signed in. Read, not probed: the same reach can insert a `family_devices` row with a token hash it chose, a new device credential, and update any `children` column, the Picture Password hash included.

## Queries run as the owner

Every query outside `runWithinReach` is listed here, read from `src/server`. Each one either takes its row from a hash of a secret the caller sent, or takes ids the API has already checked within the caller's reach.

| Path                                                                                                                          | What the caller supplies                                     | Steerable?                                                                                     |
| ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| Sign-in, pending sign-in, Family Device cookie, reset link, Invite, email check, passkey hand-off                             | A token, looked up by its SHA-256                            | No. The hash itself, sent as the token, is refused (probe 12)                                  |
| `/api/sign-in`, `/api/password-reset-requests`, email-in-use checks                                                           | An email, matched with `=` after `normaliseEmail`            | No. `%` patterns and quoted SQL match nothing (probe 13)                                       |
| Passkey sign-in and challenges                                                                                                | A credential id, then a signature over the challenge         | No. A3 refuted the rpID, origin, challenge and sign-count checks                               |
| `POST /api/parents`, `/api/people/:userId/invites`, `/api/people/:userId/password-resets`, `/api/families/:familyId/children` | A Family, School or adult id, checked within the reach first | No. Each one aimed outside `teacherAYear3`'s reach answers `404` and writes nothing (probe 14) |
| `POST /api/bulk/families/preview` and `/api/bulk/families`: who owns each typed email, and their Family's Children            | Emails in the CSV                                            | **Yes** (probes 15 and 16)                                                                     |
| Audit Log entries written in an owner transaction                                                                             | Nothing: the actor comes from the sign-in                    | No                                                                                             |

The reach check and the owner write are two transactions on two connections, the owner one opened while the reach one is still open. A change between them (a Child moving Year Group, a Teacher losing one) could let a write through that a check a moment later would refuse. Read, not probed: the window is one request, and a tester can't hold it open.

**A Teacher's upload names a Parent outside their reach (probe 15).** `previewFamilies` looks every typed email up as the owner and accepts an existing Parent when they are in the Teacher's reach **or** belong to the Teacher's School (`existing.schoolIds.includes(school.id)`). `teacherAYears5And6` (School A, Years 5 and 6) can't see Family A2, whose twins are in Year 3. Their upload of one row, a Child born for Year 5 with `parentA2PasskeyOnly`'s email, answers `201` with `createdRowCount: 1`, and the Child is inserted into Family A2 as the owner. Before it, `GET /api/parents` doesn't list `parentA2PasskeyOnly`. After it, it does, because the new Child puts Family A2 in the Teacher's reach. The PRD's "Existing people" rule says a Parent email that exists adds the Child to that Family, and its "Reach" rule limits a Teacher only to their School and Year Groups. ADR 0027 says the lookup is there so "an upload can refuse a Parent outside the Teacher's reach". The code follows the PRD, not the ADR. With #249, the Teacher can then copy an Invite for the passkey-only Parent who has just come into reach and take the account, and with it the Year 3 twins they don't teach. Fixed, unverified (#277): the row is now skipped, "Parent 1 is already a Parent outside your Year Groups, so the Admin adds this Child", whatever School the Parent is at, and nothing is added to Family A2.

**The preview tells a Teacher which emails have accounts (probe 16).** `teacherAYear3`'s preview of three rows answers: the Admin's email, "Parent 1's email belongs to someone who isn't a Parent"; `parentB`'s, "Parent 1 is already a Parent at another School, so the Admin adds this Child" (since #277, "Parent 1 is already a Parent outside your Year Groups, so the Admin adds this Child", the answer for every Parent outside the Teacher's reach); an unknown one, valid. So a Teacher learns which addresses are staff, and which belong to a Parent at another School. Read, not probed: the duplicate check ("This Family already has a Child with this name, birth month and year") answers, for a Parent the upload accepts, whether their Family has a Child of that name and birth. Fixed, unverified (#278, with #291): a Teacher's preview treats every address taken outside their reach, staff and a Parent at any School alike, as one no one has, so all three rows above pass it. The upload then skips such a row with one reason that names no role and no School, "Someone in Wizzaroo already uses Parent 1's email, so the Admin adds this row". The duplicate check and "The two Parents are already in different Families" now run only for Parents in the Teacher's reach. The Admin's preview keeps its precise answers.

## The backup container's credentials

From `docker compose config` on `docker-compose.yml` alone, with placeholder secrets:

- the `backup` service's `PGUSER` is `wizzaroo`, the same as `POSTGRES_USER` and the user in the app's `DATABASE_URL`, and its `PGPASSWORD` is the same `POSTGRES_PASSWORD`;
- it is on `database` and on `offsite`, which isn't internal, so it can reach the internet, as rclone needs to.

`pg_dump` needs to read every table, and to read past row-level security it needs `BYPASSRLS` or ownership. It doesn't need to write, run programs or change roles. A flaw in `pg_dump`, `age`, `rclone` or the image's packages, in the one container with a way out, holds the superuser's password. So does anything that can read the container's environment. The restore, `backup/restore.sh`, runs as the superuser too; it isn't a long-running container, so D1 leaves it to H13.

## What the probes change

Each probe runs on `pen_test_d1` in the gated run, never on the pen-test deployment. The `ALTER TABLE`, `COPY` and `TRUNCATE` probes roll back. The fixtures are loaded again before each probe, which puts back every column a probe changed. Rows a probe adds are deleted by that probe: the Admin's `family_parents` row and the uploaded Child.
