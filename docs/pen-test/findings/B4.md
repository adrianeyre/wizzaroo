# B4: every route as every identity

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #209 (B4), the authenticated-but-unauthorised sweep: every route, called as every [fixture identity](../fixtures.md#the-identities) and as no one. It names how each route refuses each caller, so it is kept private on the same terms as the PRD ([the findings workflow](../README.md)).

The opening register names no H entry for B4. Its one finding touches [H8](../../product-requirements-document/pen-testing.md#h8-nothing-is-rate-limited--medium) in passing, and H8 records it.

## The rules probed

- **Who reaches what:** the roles table in section 8 of [`wizzaroo.md`](../../product-requirements-document/wizzaroo.md#8-accounts-and-roles), and section 11's separation of Families, Schools and Year Groups. A Parent reaches their own Family. A Teacher reaches the Children in their Year Groups at their School, those Children's Families and Parents, and can lock but not change. The Admin reaches everyone.
- **Where reach is decided:** [ADR 0026](../../architectural-decision-record/0026-schools-and-teachers.md) and [ADR 0027](../../architectural-decision-record/0027-row-level-security-through-a-reach-role.md), with Teacher locks in [ADR 0035](../../architectural-decision-record/0035-teachers-lock-what-a-child-plays.md).
- **Second factors:** section 8 again, which says Teachers and the Admin need a second factor.
- **Family Devices:** [ADR 0005](../../architectural-decision-record/0005-family-devices-and-picture-passwords.md), under which a Family Device reaches its own Family's Children and nothing an adult's sign-in reaches.
- **Refusals:** the PRD's check that ["refusals give nothing away"](../../product-requirements-document/pen-testing.md#checks-every-scope-issue-carries). A refusal looks the same whether the thing asked about exists or not.

The code is `src/server/auth/signed-in-parent.ts` and `src/server/family-devices/signed-in-family-device.ts` for the gates, `src/server/reach-rules.ts` for reach, and every `*-routes.ts` under `src/server`.

## How it was probed

Every probe is a test in the gated run, `src/integration.test.ts`, under `pen test B4: every route as every identity`. The block has its own database, `pen_test_b4`, and its own listening server.

**The routes** are not typed in by hand. `listServerRoutes` reads Fastify's own route table, and the first test fails if a route is added, removed or renamed without a row here. B1's enumeration isn't in the tree yet, so B4 reads the same table B1 will. Each row of the table in the test names the route's gate, what its path or body names (a Child, Family, School, adult, Family Device, passkey or deletion request), whose of those the rules say each caller reaches, and a well-formed body. A request that fails validation would be answered 400 before any gate, which would prove nothing. Where a body names the thing it changes, it sends that thing's own values from the fixture plan, so a served write changes nothing a later cell depends on.

**The identities** are all 15 fixtures that hold or once held a credential, and no one:

**The targets.** A route whose path names a thing is called once for every fixture of that kind and once for an id that doesn't exist: five Children, three Families, two Schools, eleven adults, four Family Devices, both passkeys and the one deletion request. The same goes for the four routes whose body names the thing: `POST /api/children` (`schoolId`), `POST /api/parents` (`familyId`), `POST /api/deletion-requests` (`childId`) and `POST /api/play/events` (a play event's `childId`). Every other route is called once per identity. That is 3,616 cells, and a `HEAD` beside each of the 512 `GET` cells.

**Each cell's answer** is read into one of a closed set. A gate refusal is told by its message: not signed in (401), not a Family Device (401), second factor required, not a Parent, not the Admin or a Teacher, not the Admin (each 403). Any other 404 on a route that names a thing counts as not found. Anything else, a business refusal such as 409 or 400 included, counts as past the gate. The expected answer comes from the rules above, not from the code. For routes open to anyone, it is whatever the same request gets with no sign-in.

**Fixtures used, and what changed.** All of them, by the ids above and in [the fixtures](../fixtures.md#the-identities). The sweep is in the gated run only, against `pen_test_b4`, and sent no request to the pen-test deployment, so nothing changed there. Inside `pen_test_b4`, every cell that was answered with a 2xx to anything but a `GET` is followed by emptying every table, loading the fixtures again and putting back the sweep's own sign-ins. Loading again alone leaves rows a probe added, and one such row moves reach: a Child the Admin adds to Family B at School A makes Family B a School A Family, so `teacherAYear3` then reaches it. So every cell starts from the same fixtures. The served changes include Children, Parents, Teachers, Schools, Family Devices, Invites, resets, awards and deletion requests made, and Families, Children and adults deleted or deactivated. Addresses the probe makes are `b4-probe…@pen-test.example`.

**When.** The sweep was run, not in the gated run but as described below, on 17 November 2026 from 12:50 to 13:06 UTC.

**Not run under Docker in the sandbox.** The sandbox has no container runtime, so the gated run skips these tests there. To see what they pin, the B4 block was run in the sandbox against a real Postgres 18.6 binary (`@embedded-postgres/linux-arm64`, installed outside the repository), through an untracked copy of the suite with the container swapped for that server. All 12 tests did what they should: ten pass and both `it.fails` fail on their assertion. The sweep took about 30 seconds. The verdicts count as verified once the gated run passes on a host with Docker.

## The table

One row per route, one column per identity (the column names are in the table above). What each cell holds:

- **✓**: answered past the gate. On a route open to anyone, that is the same answer as with no sign-in.
- **A list of things, or "all", "all but…"**: on a route that names a thing, the fixtures the caller reaches and is answered past the gate for. Every other fixture of that kind, and the missing id, is refused 404 with the same body.
- **404**: every fixture of that kind, and the missing id, is refused 404 alike.
- **401**: refused, not signed in. **401 dev**: refused, not a Family Device.
- **403 2f**: refused, a second factor is needed. **403 P**: not a Parent. **403 S**: not the Admin or a Teacher. **403 A**: not the Admin.

The expected answer and the one given agree in every cell, so the table is both. `HEAD` rows aren't shown; each answers as its `GET` does.

## B4-1: a caller with no sign-in is answered before they are refused

**Probe 8.** Each route checks the caller inside its handler, with `runAsSignedInUser`, `runAsSignedInAdult`, `runAsSignedInParent`, `runAsSignedInStaff`, `runAsSignedInAdmin` or `runAsSignedInFamilyDevice`. Fastify runs the route's schema validation before the handler, so a request with no credential and a malformed body or path parameter is answered with the schema error, not 401:

```text
POST /api/teachers {}                         → 400 "body must have required property 'name'"
GET  /api/children/not-an-id!/progress         → 400 "params/childId must match format \"uuid\""
POST /api/admin/children/not-an-id!/star-awards → 401 "Sign in to Wizzaroo first"
```

43 routes answer this way: every route that needs a credential and takes a body or a path parameter, but three. Those three are `POST /api/admin/children/:childId/star-awards`, `POST /api/admin/families/:familyId/family-chest-coin-awards` and `GET /api/admin/audit-log-entries`, which run `buildSignedInAdminCheck` as a `preValidation` hook. That check exists, by its own description, "so a caller who isn't the Admin can't probe the route's schema", but nothing else uses it. Some handlers do work of their own before the sign-in check too: `PUT /api/children/:childId/birth` with a birth too recent for Reception answers "That birth month and year is too young for Reception…" with no sign-in.

None of this tells the caller whether any Child, Family or adult exists: the answer is the same for every id. What it gives away, to anyone on the internet, is each route's fields, enums and limits, which the client bundle also holds. It is hygiene and disclosure, so **low**.

**Probe 9.** On three routes the handler hashes the body's Picture Password before the sign-in check: `POST /api/children`, `PUT /api/children/:childId/picture-password` and `PUT /api/play/children/:childId/picture-password`. The hash is 100,000 rounds of PBKDF2-SHA-256 through WebCrypto (`src/server/children/picture-password.ts`). The probe counts calls to `crypto.subtle.deriveBits` while each route is called with no credential and a well-formed body, and those three are the routes that call it.

By arithmetic, not load: in this sandbox one hash took 8.6 ms, and 200 at once took 430 ms, about 465 a second on the worker threads. Those are the threads argon2 uses to check passwords at sign-in (A1 measured about 400 argon2 checks a second on them). So about 465 unauthenticated requests a second, with nothing to limit them (H8), would hold every worker thread. Each one is refused 401 only after its hash. Fixing the order is B4-1's. The rate figures are I2a's.

- `today_ checks the shape of a request with no sign-in before refusing it, on every route with a body or a path parameter but three of the Admin's`, now `refuses a request with no sign-in before checking its shape, on every route with a body or a path parameter, the Admin's and everyone else's alike (regression)`
- `it.fails`: `refuses a request with no sign-in for want of one on every route that needs one, whatever the request holds`, now a plain `it` that passes
- `today_ hashes a Picture Password for a caller with no sign-in on three routes before refusing them`, now `hashes no Picture Password for a caller with no sign-in, on the three routes that hash one (regression)`
- `it.fails`: `hashes nothing for a caller with no sign-in`, now a plain `it` that passes

_Fixed, unverified (#300):_ #259's fix (`18fb5f8`, its tests turned in `4b49767`) makes every route declare its reach in `config.reach`, and runs that reach's check as the route's first `onRequest` hook, before Fastify reads the path parameters, query string or body. So a caller with no sign-in, or no Family Device, gets 401 "Sign in to Wizzaroo first" from every route that needs one, whatever the request holds, before any schema check, any check of the handler's own, such as the Reception age check, or any Picture Password hash. `buildSignedInAdminCheck` had no callers left and is gone.

## Findings

- **#300, low, _fixed, unverified_:** routes that need a sign-in validate, and on three routes hash a Picture Password, before checking the caller. So anyone with no credential learns each route's schema and spends the server's worker threads.

Nothing was fixed here. #300 is fixed, unverified, by #259's `onRequest` reach check, which turned each `it.fails` into the passing test, and each `today_` test into a `(regression)` test.
