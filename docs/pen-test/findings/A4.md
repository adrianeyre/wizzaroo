# A4: password resets, Invites and email changes

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #202 (A4), which answers H2 and H3 in [the pen-testing PRD](../../product-requirements-document/pen-testing.md). It names exploit chains, so it is kept private on the same terms as the PRD.

Every probe runs in the gated suite, `src/integration.test.ts`, under `pen test A4: password resets, Invites and email changes`, against a real Postgres loaded with [the fixtures](../fixtures.md) and reloaded before each probe. Each identity signs in through the credentials harness (`signInAsPenTestFixture`), the way it normally would. A confirmed probe is a `today_…` test pinning what happens now beside an `it.fails` for the property that should hold; a refuted probe is a passing test.

## An Invite for an adult who has only passkeys (H2)

_Fixed, unverified (#249)._ An Invite is now refused, when it is made and when it is opened, for an adult with a password, a passkey or an accepted Invite.

`createInvite` refuses only an adult whose `password_hash` is set (`src/server/people/invites.ts:77`), and `findLiveInvite` accepts any live Invite for an adult whose `password_hash` is null (`:168`). An adult who removed their password to keep only passkeys matches both, though they accepted their first Invite long ago.

- **Teacher → Parent.** `teacherAYear3` (password and TOTP) sends `POST /api/people/<parentA2PasskeyOnly>/invites` with `{"invite":"link"}` and gets `201` with the Invite's URL. `POST /api/invite-acceptances` with its token and a password the Teacher chose answers `204` and a sign-in cookie. `GET /api/me` with it answers `parent-a2-passkey-only@pen-test.example`, role `parent`, Family `Pen-test Family A2`, and `GET /api/children` lists Cara and Dev. From then on the Teacher's password signs in to the account with `POST /api/sign-in` (`204`, no second factor). Teacher reach, read-only by design ([ADR 0027](../../architectural-decision-record/0027-row-level-security-through-a-reach-role.md)), becomes a Parent's full write reach over Family A2.
- **Admin → Teacher.** `teacherAYears5And6` signs in with their passkey and removes their password (`DELETE /api/password`, `204`), as section 8 lets them. The Admin then does the same with a copy-link Invite: `201`, then `204`, and `GET /api/me` answers as the Teacher, with `needsSecondFactor: true`. The Teacher's password is now one the Admin chose, and it signs in. What that password-only staff session can then enrol is H1, probed by A5.
- **What the adult is told.** One email, to their own address: "Confirm your email address for Wizzaroo", which says "If you didn't ask for this, ignore this email and nothing will change". Their address is marked unconfirmed (`email_confirmed_at` set to null, `src/server/auth/invite-routes.ts:69`), so they can't reset the password from their own mailbox until they open that link. Their own passkey session stays signed in.

## Changing an email address from a bare session (H3)

_Fixed, unverified (#250)._ A new address now takes, in the same request, the current password, a fresh code or the adult's own passkey, and from Teachers and the Admin always the code or the passkey; a staff sign-in with no second factor is refused.

`POST /api/email-address-checks` runs under `runAsSignedInUser` (`src/server/auth/email-address-check-routes.ts:153`), which skips the staff second-factor check, and its body schema takes only `email`, so there is nowhere to give a password. `POST /api/email-address-confirmations` takes only the token.

- **As a Parent.** `parentB`'s session asks to move to `mallory-for-parent-b@pen-test.example` (`204`); the link sent there confirms it (`200`). The account's address is now Mallory's, and the session that asked stays signed in.
- **As staff.** The same for `teacherAYear3`, whose session used TOTP, and `teacherBYear3`, whose session used a password alone and so `needsSecondFactor: true`. Both: `204`, then `200`, and the address is changed. A staff session that can reach no staff route can still move the account's address.
- **What the old address is told: nothing.** The only email is the check, sent to the new address. Nothing reaches the old one, at the request or at the confirmation. _Fixed, unverified (#251):_ the old address, if confirmed, is now told when the change is asked for and again when it is confirmed, with the new address masked and no link.

## A stolen session, an email change and a reset (H3)

_Fixed, unverified (#250)._ The chain stops at step 1: a session alone is refused (`403`).

With `parentB`'s session cookie and nothing else:

1. `POST /api/email-address-checks` with `mallory-takes-parent-b@pen-test.example`: `204`.
2. `POST /api/email-address-confirmations` with the token from Mallory's mailbox: `200`.
3. `POST /api/password-reset-requests` with Mallory's address: `204`, and the reset link goes to Mallory, because her address is now the account's confirmed one.
4. `POST /api/password-resets` with that token and Mallory's password: `204`. Every sign-in to the account is ended, the owner's included.
5. `POST /api/sign-in` with Mallory's address and password: `204`, as Family B's Parent.

The owner's own address and password are refused (`401`), no account has the owner's address any more, so a reset they ask for goes nowhere, and **not one email went to the owner's address**. Mallory's mailbox got the check, the reset link and the "Your Wizzaroo password was changed" notice that was meant to warn the owner. A 30-day session becomes the account for good, and the owner is never told.

Not probed here, and worth knowing: on an account with TOTP (`parentA1`) the chain ends with Mallory holding the password but not the code, and the owner still locked out. On a passkey-only account the reset sets a password where there was none, so the chain works as it does for `parentB`.

## The email-change refusal (H3)

_Fixed, unverified (#253)._ The request now answers `204` with no body whether or not the address is taken. A taken address gets a short note with no link instead of a confirmation link, and the confirmation still refuses it.

`coParentA1`'s session asks to move to `admin@pen-test.example` and gets `409` "Another Parent already uses that email address" (`src/server/auth/email-address-check-routes.ts:161-162`). An address no account uses gets `204`. The check covers every adult, staff included, so any signed-in Parent can tell which addresses belong to the Admin, a Teacher or another Parent. The `204` path also emails a link to whatever address the caller typed.

## Tokens

_Fixed, unverified (#252)._ Changing, setting, removing or resetting the password, confirming an email change and deactivation now each delete every outstanding reset link and email address check for the account.

| Token                                            | Works once | Expires | After the password changes                        | After the email address changes | After deactivation |
| ------------------------------------------------ | ---------- | ------- | ------------------------------------------------- | ------------------------------- | ------------------ |
| Password reset (`/api/password-resets`)          | Refuted    | Refuted | **Confirmed**: still sets the password            | **Confirmed**: still sets it    | Refuted            |
| Email check (`/api/email-address-confirmations`) | Refuted    | Refuted | **Confirmed** after a reset: still changes it     | Replaced by the next check      | Not probed         |
| Invite (`/api/invite-acceptances`)               | Refuted    | Refuted | Refused while a password is set; H2 once it isn't | Not probed                      | Refuted            |

- **A reset link survives a password change.** `PUT /api/password` ends the other sign-ins (`src/server/auth/password-change-routes.ts:146`) but not the reset links. A link asked for at 10:00 still sets the password after the owner changes it at 10:05, and the owner's new password stops working.
- **A reset link survives an email change.** A link sent to the old address still sets the password after the account moves to a new one, for the rest of its hour. Moving away from a mailbox someone else reads doesn't close it.
- **A pending email change survives a reset.** A reset ends every sign-in (`src/server/auth/password-reset-routes.ts:173`) but leaves `email_address_checks` alone. So when an owner notices a stolen session and resets their password, the session is gone, but the email change it asked for can still be confirmed for 24 hours, and the chain above goes on from step 2.
- **Single use and expiry hold** for all three: a second use of each is refused (`404`), and each is refused once its `expires_at` has passed. Deactivation deletes the adult's reset links (`src/server/people/people-routes.ts:769-771`) and `findLiveInvite` refuses a deactivated adult's Invite.

Beyond the [expected state changes](../credentials-package.md#expected-state-changes), the probes set passwords on `parentA2PasskeyOnly`, `teacherAYears5And6`, `parentB` and `coParentA1` (and on `coParentA2Invited` by accepting their Invite), removed `teacherAYears5And6`'s password, moved `parentB`'s, `coParentA1`'s and both Year 3 Teachers' addresses to new ones at `pen-test.example`, deactivated `coParentA1` and `coParentA2Invited`, and backdated reset links and email checks to expire them. Loading the fixtures again puts every one of those back. It leaves the Invites the probes created, the unused reset links and email checks, and the sign-ins.

To repeat a probe by hand on the deployment, the credentials are the package's variables for the handles above, such as `PEN_TEST_TEACHER_A_YEAR3_PASSWORD` and `PEN_TEST_TEACHER_A_YEAR3_TOTP_SECRET`, and the attacker's addresses are any at `pen-test.example`, so the fixtures can be loaded again afterwards.
