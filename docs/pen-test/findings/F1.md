# F1: The Family Device credential

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #215 (F1), which answers the credential half of [H9](../../product-requirements-document/pen-testing.md#h9-a-family-device-credential-lives-for-ever-and-carries-every-picture-password-hash--medium). The Picture Password half (the hashes a device holds, and how fast they fall) is F2's. This note names exploit chains, so it is kept private on the same terms as the PRD.

- **Trust boundary:** a Family Device's credential is the security boundary for play. The Picture Password only keeps siblings apart ([ADR 0005](../../architectural-decision-record/0005-family-devices-and-picture-passwords.md)). Section 8 of `wizzaroo.md` ("Requirements", under "Family Devices") gives a device "a long-lived credential for play only, which a Parent can revoke", and its "Email" table sends a security notice when a new Family Device is signed in.
- **Code:** `src/server/family-devices/signed-in-family-device.ts` (the cookie and the check), `src/server/family-devices/family-device-routes.ts` (making, listing and signing out a device, and three play routes), `classmate-room-routes.ts` and `play-event-routes.ts` beside it (the other two play routes), `family_devices` in `src/server/schema.ts` and `src/server/drizzle/0008_family-devices.sql`, and the export in `src/server/family-data/family-export.ts`.
- **Documented behaviour:** [Family Devices](../../guide/family-devices.md).
- **Probes:** the `pen test F1: the Family Device credential` block in `src/integration.test.ts`, in the gated run against a real Postgres. It loads [the fixtures](../fixtures.md) into a database of its own and loads them again before every probe, so each probe starts from the plan. A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now. A refuted probe, or one confirmed as a documented decision, is a passing test. `familyDeviceA1` is the copied credential, sent from an address and a browser of its own (`203.0.113.41`, from the documentation range). `familyDeviceA1Revoked` is the device a Parent signed out a week before loading. `coParentA1` (password only) and `parentA1` (TOTP) are the Parents whose sign-ins make devices. The probe inserts each sign-in as a row, so it tests the device and not signing in, which A1, A2 and A5 test.

H9's credential half is **confirmed**. A copied cookie works from anywhere for ever, and the Parent can't tell. Revocation is the one control that holds, and it holds everywhere. A sign-in turns into a device credential that nothing but that revocation ends.

## What a copied device cookie can do, and from where: confirmed as a documented decision

The cookie is a 32-byte bearer token, kept as its SHA-256 in `family_devices.token_hash`. `loadSignedInFamilyDevice` looks it up by hash and checks only that `revoked_at` is null. Nothing ties it to the browser it was issued to: no address, user agent or second secret. So whoever holds the value is the device, from any address.

The probe sends `familyDeviceA1`'s token from another address and browser:

- **The routes it opens are the five under `/api/play`**, and no others. The suite's existing Family Devices test pins that it gets no further than no credential on every other route.

  | Route                                              | Answer from the copy                                                     |
  | -------------------------------------------------- | ------------------------------------------------------------------------ |
  | `GET /api/play/family`                             | 200: Ada and Ben, with their Picture Password hashes, limits and rewards |
  | `POST /api/play/events`                            | 204: a session for Ada is stored                                         |
  | `GET /api/play/children/:childId/classmate-rooms`  | 200: the Rooms of Ada's Classmates in other Families who have opted in   |
  | `PUT /api/play/children/:childId/picture-password` | 409, since Ada has one. A Child with none would get the copy's choice    |
  | `PUT /api/play/children/:childId/character`        | 409, since Ada has one. A Child with none would get the copy's name      |

- **It stays within its Family.** Cara's Classmate Rooms, asked for in Family A2's name, answer 404.
- **It renews itself.** Every play route that succeeds sets the cookie again with `Max-Age` of 400 days. The two refused with 409 don't.

This is what ADR 0005 and section 8 give a Family Device: a long-lived credential for play, for that Family's Children only. A bearer token copied from a device is that device. It is recorded as a documented decision, not filed. What makes a copy dangerous is how long it lasts and that nobody can see it, and those are filed below.

[The guide](../../guide/family-devices.md) says the credential "opens the play routes, `GET /api/play/family`, `POST /api/play/events` and `GET /api/play/children/:childId/classmate-rooms`, and nothing else". It opens the two `PUT` routes for a first Picture Password and Character too. The guide is behind the code here, which is noted in the outbox rather than changed by this probe.

Test: `opens the five play routes for its own Family's Children from any address and browser that presents it, renewing itself for 400 days, and reaches no other Family's Child, as documented`.

## For how long: confirmed

`family_devices` holds `id`, `token_hash`, `family_id`, `name`, `created_at` and `revoked_at`, and nothing else. There is no expiry and no last-used time. The 400 days is the cookie's `Max-Age`, an instruction to the browser that issued it. A copied token is replayed with whatever cookie jar the copier likes, so it is never sent past 400 days. And each successful play call renews the original for another 400 days anyway.

The probe makes a device and moves its `created_at` back five years. With no last-used time stored, its creation is the last contact the server knows of. `GET /api/play/family` still answers 200 and hands back a fresh 400-day cookie.

The guide says the cookie is "kept for 400 days, the longest browsers keep a cookie, from the device's last contact". That reads as a limit, and the server doesn't enforce one: the control is weaker than its documentation says. A token taken from a device, a backup of its browser profile, or a copy of the cookie works until a Parent signs that device out. Filed as #301 (medium), and now fixed, unverified (#301).

- `today_ serves a Family Device made five years ago and not seen since, and renews its cookie for another 400 days`
- `it.fails`: `refuses a Family Device that hasn't been seen for longer than the 400 days its cookie lasts`

## Revocation: refuted

`DELETE /api/family-devices/:familyDeviceId` sets `revoked_at` within the Parent's reach. Every play route runs `runAsSignedInFamilyDevice`, which runs `loadSignedInFamilyDevice` first. That reads the row afresh on every request, with `revoked_at is null` in the query, and nothing caches it. The probe:

- signs `familyDeviceA1` out as `coParentA1`, then sends its token to all five play routes with valid bodies: each answers 401 and renews nothing;
- sends the fixtures' `familyDeviceA1Revoked`, signed out a week before loading, to the same five: each answers 401;
- counts Family A1's play events before and after: the refused upload stored none.

So revocation is immediate on every route under `/api/play`. Read from the code, not probed: a request whose check has already passed when the device is signed out finishes, since the check and the work are two statements. That window is one request long, so it is recorded here and not filed. Who can change `revoked_at` in Postgres is H5's, answered by D1.

Test: `refuses a Family Device on every play route from the moment a Parent signs it out, and goes on refusing the fixtures' revoked device`.

## Whether the Parent can see when and where a device was last used: confirmed

`GET /api/family-devices` gives each device's `id`, `name` and `createdAt`. The Family's export gives the same and `revokedAt`. A play call writes nothing to `family_devices`, and no address is stored anywhere. `play_events.received_at` records when a device last uploaded events, but `GET /api/play/family`, the classmate Rooms and the two `PUT` routes leave no trace, and the Parent is shown none of it.

The probe lists the devices as `parentA1`, and exports the Family, before and after the copied token calls all five play routes from `203.0.113.41`. The list, the export's devices and the `family_devices` row are byte for byte the same.

So a copy playing from somewhere else looks exactly like the tablet in the kitchen. The one signal a Parent gets is the security notice when a device is made, and only if their address is confirmed. Nothing tells them later that a device they recognise by name is in use elsewhere, or that one they no longer use is still active. The credential is the only boundary for play (ADR 0005), and it has no detection behind it. Filed as #302 (medium).

_Fixed, unverified (#302):_ every play route records the device's last contact as the database owner, `last_seen_at` and the caller's address in `last_seen_from`, read as the Audit Log reads a sign-in's. It writes at most once a minute from one address, and at once from a new one. Only the last address is kept, and signing a device out clears it. `GET /api/family-devices`, the Parent page's list and the Family export show both, so the copy's `203.0.113.41` now stands out.

- `shows the Parent, in the list and the export, when and from which address a copied cookie last played, keeping only the last address and writing at most once a minute from one address (regression)`
- `tells the Parent when, and from where, a Family Device was last used` (was `it.fails`)

## What making a device asks of the Parent's sign-in: confirmed

`POST /api/family-devices` runs `runAsSignedInParent` and takes a name. That is all it asks. There is no re-entered password and no TOTP code or passkey, whether or not the Parent has a second factor. The probe makes a device from a password-only sign-in for `coParentA1` and from a two-step one for `parentA1`. Both answer 201, and the first device plays.

Making the device ends the sign-in that made it, and emails the Parent's confirmed address. Nothing else follows:

- the device needs no Parent after that, so it has no 30-day end like a sign-in (#244) and lasts as long as F1-1 says;
- the probe makes a device from one of `coParentA1`'s sign-ins, then has `coParentA1` change their password (`PUT /api/password`) and then reset it from a reset link. Each ends the Parent's other sign-ins, as A1 found, and the device answers 200 after both. Read from the code: deactivating an adult doesn't touch `family_devices` either, since devices belong to the Family and record no Parent.

So anyone who holds a Parent's sign-in for a moment, by a cookie copied off a shared computer, a stolen session (H3) or a takeover (#250), can make a device credential for that Family. It outlives everything the Parent would do to take the account back: a password change, a reset, waiting 30 days for the sign-in to expire. What stops it is the security notice reaching a confirmed address, and the Parent then signing out a device whose name the attacker chose. Filed as #303 (medium).

The second `it.fails` is one way the property could be met. Signing out every Family device on a password change would also stop the Children playing, so the fix may record which sign-in made a device, or ask the Parent on a password change. That choice belongs to the fix's issue.

_Fixed, unverified (#303):_ `POST /api/family-devices` now takes the same fresh proof as moving an email address: the Parent's password, a code from their authenticator app, or a passkey answering a challenge just given. No proof, or more than one, answers 403 `account-proof-required`, and a wrong one 403. Each try counts against the Parent's email address with the sign-in's per-account limit for wrong passwords, and a right one gives its try back, so a held sign-in guesses no faster here than at the sign-in page. Each device records the adult whose sign-in made it (`created_by_user_id`, migration 0056, filled from the Audit Log for older devices). A password change or reset signs out every device that adult made, logged as `family-device.revoked` "with a password change" or "with a password reset". Devices another Parent made, and older ones with no maker on record, keep playing.

- `refuses to make a Family Device from a password-only sign-in or a two-step one with no proof or a wrong one, keeping the sign-in, and makes one with the Parent's password or a current code (regression)`
- `asks for the Parent's password or second factor again before a sign-in makes a Family Device` (was `it.fails`)
- `signs out the Family Devices the Parent's sign-ins made, and only those, when they change their password and when they reset it, as each ends their other sign-ins (regression)`
- `signs out a Family Device that a sign-in made once the Parent's password change or reset has ended that sign-in` (was `it.fails`)

## What this round didn't run

The probes were written, typechecked and linted in a sandbox with no container runtime, so the gated run skipped them there. The verdicts above rest on reading the code and on the probes as written, until the gated run is executed on a host with Docker and its output posted on #215. Nothing here was exercised against the pen-test deployment itself.
