# I4: containers, Compose and the tunnel

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #223 (I4) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers the container, Compose and backup-target half of [H13](../../product-requirements-document/pen-testing.md#h13-secrets-and-containers-are-fail-closed-but-not-hardened--medium) and the network-exposure half of [H12](../../product-requirements-document/pen-testing.md#h12-http-hardening-is-absent--medium). It names exploit chains, so it is kept private on the same terms as the PRD. How a finding is filed, triaged and verified is in [the findings workflow](../README.md).

- **Trust boundary:** the home server's Docker. [ADR 0002](../../architectural-decision-record/0002-self-hosted-behind-a-cloudflare-tunnel.md) puts `app` behind a Cloudflare Tunnel with Postgres "on an internal network only". [ADR 0028](../../architectural-decision-record/0028-backups-are-age-encrypted-dumps-sent-with-rclone.md) and [ADR 0030](../../architectural-decision-record/0030-backups-go-to-the-nas-and-a-locked-b2-bucket.md) send backups to the NAS, which "must never be reachable from the internet", and to a B2 bucket whose key "can only write" and whose Object Lock means "the home server … can't remove anything from it, even if it is compromised".
- **Code:** `docker-compose.yml`, `Dockerfile`, `backup/Dockerfile`, `backup/backup.sh`. The set-up the owner follows is [deploying to the home server](../../processes/deploying-to-the-home-server.md) and [restoring a backup](../../processes/restoring-a-backup.md#drilling-a-restore).
- **Probes:** the `pen test I4: containers, Compose and the tunnel` block in `src/integration.test.ts`, and the `pen test I4: the off-site key and Object Lock, against the throwaway bucket` block in `src/backup-restore.test.ts`, both in the gated run against a real Postgres. Compose is read as `docker compose config` resolves it, with placeholder secrets and both the `drill` and `tunnel` profiles on, so every production service is in it. Those probes are skipped, loudly, where `docker compose` isn't installed. Images were also read from Docker Hub's registry on 17 November 2026, and the `postgres` image's entrypoint from `docker-library/postgres`.
- **Left to other scope issues:** the variables (minimum secret length, `SMTP_SECURE`, `TUNNEL_TOKEN` defaulting to empty, `:?` and refusing to start) are I3's. The response headers and `trustProxy` are I1's, and the IP a rate limit keys on is I2a's. The `CF-Connecting-IP` an Audit Log entry keeps is D6's (H21). The backup container's superuser login is D1's (#279).

## Fixed, unverified

All five are fixed, unverified by a retest. Each `it.fails` now passes as a plain `it`, and each `today_…` probe is a `(regression)` test of the fixed behaviour. The pen-test deployment was stood up from these files, seeded, backed up and restored into the drill, with every container hardened.

- **#313:** every base and pulled image is named `tag@sha256:digest`, at the digests the tags resolved to on 17 and 18 November 2026. The app's build checks pnpm's tarball against the sha512 npm publishes for 12.18.0 before installing it, and the backup's installs `age=1.3.2-r1` and `rclone=1.75.2-r0`. Alpine keeps only a release's newest build of a package, so a replaced one fails the build until someone pins the new one.
- **#314:** every container in `docker-compose.yml` sets `read_only: true`, `cap_drop: [ALL]` and `security_opt: [no-new-privileges:true]`, with a tmpfs at `/tmp`. `postgres` and `restore-drill` add back only `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETGID` and `SETUID`, for the entrypoint to own the data directory and become `postgres`, and keep their socket in a tmpfs. A restore run as root to read the age key now adds `--cap-add DAC_READ_SEARCH`.
- **#315:** `restore-drill` is started with `POSTGRES_PASSWORD` from `.env` and no `trust`, so over the network it asks for the superuser's password, as `postgres` does. The drill's restore is given it as the live restore is.
- **#316:** the tunnel's routes are in `docker-compose.yml`, as the `tunnel-routes` config `cloudflared` runs from with `--config`: `wizzaroo.adrianeyre.co.uk` to `http://app:4310` and `http_status:404` for anything else. Cloudflare reads them only for a tunnel made with `cloudflared tunnel create`, so [the deployment guide](../../processes/deploying-to-the-home-server.md) now makes one that way. `cloudflared` and `app` share only the internal `tunnel` network. Each goes out on a bridge of its own, `wizzaroo-tunnel` and `wizzaroo-mail`, which the guide's firewall rules keep off the LAN. Those rules live on the home server, so that half is the owner's to apply and read, as the table below says.
- **#317:** each night `backup.sh` sends a probe to `wizzaroo-lock-probes/` beside the off-site backup, deletes it for good (`--b2-hard-delete`), and checks it is still there. If it is gone, or the check can't tell, it logs `backup.offsite.delete-allowed …` and the night fails, so the backup goes unhealthy. Otherwise it logs `backup.offsite.delete-refused …`. Only `BACKUP_OFFSITE_LOCK_CHECK=off-for-a-stand-in` skips it, which the pen-test overlay sets for its bucket stand-in and `docker-compose.yml` never does.

## Images and builds

**Pinned by digest (probe 1): confirmed, I4-1.** Every image is named by a tag:

| Where                       | Image                              | Resolved on 17 November 2026 to the index                                 |
| --------------------------- | ---------------------------------- | ------------------------------------------------------------------------- |
| `Dockerfile`, both stages   | `node:26-slim`                     | `sha256:e6bedef217677b276c591795e169840edd9096dbf13f29df8ef8d1856b8820bc` |
| `backup/Dockerfile`         | `postgres:18-alpine`               | `sha256:b6972e1115a4ff8eba5d7f7d19184926d1e16d7d1136ae1e1a7ebf286da0f015` |
| `postgres`, `restore-drill` | `postgres:18-alpine`               | as above                                                                  |
| `cloudflared`               | `cloudflare/cloudflared:2026.11.0` | `sha256:b94b96edf2c9c4360f8879c8580cfaa99077f19c849ec595ca2f711b27d4f344` |

`node:26-slim` and `postgres:18-alpine` are moved by their publishers with every patch release, so two builds a week apart run different code, and a build takes whatever the tag points at that day. `cloudflared`'s tag names a release, but a tag can still be pushed again. The builds also fetch by name: `npm install -g pnpm@12.18.0` with no integrity check (the lockfile pins the app's packages, not pnpm), and `apk add --no-cache age rclone` with no version at all, so the backup image takes whichever age and rclone Alpine has that day. The digests above are a record of the day's tags, not a recommendation.

- `docker-compose.yml and the Dockerfiles › today_ names every base image and every pulled image by a tag, which can be moved, and none by digest` / `names every base image and every pulled image by its digest`

**A user other than root (probe 2): refuted.** The app's image ends `USER node` and the backup's `USER postgres`, and Compose overrides neither, nor any other container's user. `postgres` and `restore-drill` start the image's entrypoint as root, which then runs the server as `postgres` (`exec gosu postgres`); D1's `COPY … PROGRAM 'id -un'` read back `postgres`. The `cloudflared` image's own configuration sets user `65532:65532` (read from the registry, not probed in a running container).

- `docker-compose.yml and the Dockerfiles › runs the app as node and the backup as postgres, and overrides no container's user in Compose`

**Hardening (probe 3): confirmed, I4-2.** None of the five services sets `read_only`, `cap_drop` or `security_opt: no-new-privileges`. So each keeps Docker's default capabilities (among them `NET_RAW`, `CHOWN`, `SETUID`, `SETGID` and `DAC_OVERRIDE`), a writable root filesystem, and the ability to gain privileges through a setuid binary. Running as `node` or `postgres` keeps those capabilities out of the process's effective set, which is why this is low: the user is one layer, and these would be the second. A process that reaches root inside `app`, through a setuid binary in `node:26-slim` (read, not probed) or a kernel bug, holds them. `postgres` and `restore-drill` start as root by design, so they keep them until `gosu`.

- `docker-compose.yml and the Dockerfiles › today_ sets read_only, cap_drop and no-new-privileges on no container` / `makes every container's filesystem read-only, drops every capability and refuses new privileges`

## The drill's Postgres

**`restore-drill` (probe 4): confirmed, I4-3.** It is `postgres:18-alpine` with `POSTGRES_HOST_AUTH_METHOD: trust` and no password. The image's entrypoint then appends `host all all all trust` to `pg_hba.conf`: any role, from any address, with no password.

- **Who:** every container on the `database` network, which is `app`, `backup`, `postgres` and `restore-drill` itself. It publishes no port, and `database` is internal, so nothing outside Docker reaches it through Compose. Whether a process on the home server itself reaches it at its container address depends on the Docker Engine and the firewall there, which only the owner can read (below).
- **When:** only while it runs. It starts by hand with `--profile drill`, has no restart policy, so a reboot ends it, and keeps its data in a `tmpfs`, so stopping it destroys the restore. A drill restores a whole backup into it: every Family, every password hash and every TOTP secret in the clear (H17). It holds them until step 6 of the drill, `rm --stop --force`. A drill left half-done keeps them, with no password, until the next reboot.
- **What it gives:** a Postgres started from Compose's own `restore-drill` settings lets `wizzaroo` in with a wrong password, and `wizzaroo` is a superuser. So whoever reaches it can read the restore, and run programs in that container with `COPY … PROGRAM`.

Today that adds no reach: each container on `database` already holds the live database's superuser password, `app` in `DATABASE_URL` and `backup` in `PGPASSWORD` (H4, #273 and #279). It is low because of that, and it stops being low the day #273 is fixed: once the app logs in as a role of its own, a drill in progress is a passwordless superuser copy of every Family, one hop from the app. Nothing records why it trusts every connection, and the drill steps never say so.

- `docker-compose.yml and the Dockerfiles › today_ starts restore-drill, by hand with the drill profile, as a Postgres that trusts every connection, on the database network the app, the backup and postgres share` / `starts restore-drill asking for a password, as postgres does`
- `docker-compose.yml and the Dockerfiles › a Postgres started as restore-drill is › today_ lets anyone who reaches it in as wizzaroo, a superuser, with a wrong password` / `refuses a wrong password`

**The live `postgres` (probe 5): refuted.** It is started with `POSTGRES_PASSWORD` and no `POSTGRES_HOST_AUTH_METHOD`, so the image asks every network connection for the password. A Postgres started the same way refuses a wrong one with `28P01`.

- `refuses a wrong password at a Postgres started as the postgres service is, with a password and no trust`

## Network exposure

**The app's port (probe 6): refuted.** The only port Compose publishes is `app`'s, as `127.0.0.1:4310->4310`. Postgres, the backup, the drill and cloudflared publish nothing, so the LAN reaches nothing directly. What reaches `app` without going through the tunnel, read from the networks: the server's own loopback, `cloudflared` on `tunnel`, and `postgres`, `backup` and `restore-drill` on `database`. Each of them can send any `CF-Connecting-IP`, which is D6's to probe (H21). Whether the LAN can reach a port published on loopback also depends on the Docker Engine: older engines on Linux could be made to forward LAN traffic to it, and current ones drop it. That is the owner's to read (below).

- `docker-compose.yml and the Dockerfiles › publishes only the app's port, on the server's loopback, and nothing from Postgres, the backup, the drill or the tunnel`

**The database network (probe 7): refuted.** `database` is `internal: true`, `postgres` is on it alone, and `cloudflared` isn't on it. So Postgres and the drill have no way out of Docker, and the tunnel no way to them.

- `docker-compose.yml and the Dockerfiles › keeps the database network internal, so Postgres and the drill have no way out of Docker and cloudflared no way to them`

**What cloudflared routes (probe 8): confirmed, I4-4.** `cloudflared` runs `tunnel --no-autoupdate run` with its token and nothing else: no ingress file, no mount, no config. That is a tunnel managed from Cloudflare's dashboard, so the hostnames it serves and the service each one goes to are set there, and the repo holds only the instruction to add `wizzaroo.adrianeyre.co.uk` → `http://app:4310`. Nothing in the repo can tell what it serves today.

What it could serve is whatever `cloudflared` can reach. It is on `tunnel`, which isn't internal: it is a bridge with a way out, so `cloudflared` reaches `app`, the home server's own addresses, the LAN, and the NAS at `192.168.1.50`. A second public hostname added in the dashboard, to the NAS's dashboard or to anything else on the LAN, publishes it to the internet with no Cloudflare Access in front (ADR 0002), and no file in the repo changes. ADR 0030 accepts the out-of-support NAS only because it is never reachable from the internet; that rests on the dashboard alone. `app` shares `tunnel`, which it needs for SMTP, so a process that takes over `app` reaches the LAN and the NAS's SMB service too. The services with a way out of Docker are `app`, `backup` (D1's #279) and `cloudflared`.

- `docker-compose.yml and the Dockerfiles › today_ runs cloudflared from its token alone, so the tunnel's routes live only in Cloudflare, on a network with a way out of Docker that it shares with the app` / `names in the repo every route the tunnel serves, as an ingress file cloudflared runs from`

## The off-site bucket

The pen-test deployment's bucket is `rclone serve s3`, and [its page](../deployment.md#backups) says it "will delete whatever it is asked to". The probes start the same stand-in beside the backup container, with the same `RCLONE_CONFIG_OFFSITE_*` settings `docker-compose.pen-test.yml` gives it.

**The backup deleting off-site (probe 9): refuted.** `backup.sh` prunes only `BACKUP_RCLONE_REMOTE` and only copies to `BACKUP_RCLONE_OFFSITE_REMOTE`. The existing backup test pins it: `the nightly backup › sends an encrypted dump to both targets and keeps only the set number of nights on the pruned one`, where every older file on the off-site target is still there, as D3's probe also found.

**The write-only key and Object Lock (probe 10): confirmed, I4-5.** What can be shown against the throwaway bucket, and what can't:

- **Shown:** the backup's off-site credential deletes the backup it has just sent, and `backup.sh` had counted the night as backed up (exit 0). The backup has no idea whether its credential could delete what it sent, and nothing it does would notice a key that can.
- **Shown:** the throwaway bucket can't stand in for the lock. The deploying page's check (`rclone touch … && ! rclone deletefile … && echo "delete refused, as it should be"`), run against it, deletes its probe and never prints the line.
- **Can't be shown here, and needs the owner:** the real key's capabilities, the bucket it is limited to, the bucket's default retention and its mode, and the lifecycle rule. They live in Backblaze, set once by hand. The repo's only check of them is the page's one-off command before the first start, with no record of having run. The [drill log](../../processes/restoring-a-backup.md#drill-log) has no entries. A key made with `deleteFiles`, a bucket in governance mode or with no default retention, or a lock that was never turned on, would look the same as the right one to every test and to the backup itself, until something deletes the backups.

ADR 0030's promise that a compromised server "can't remove anything from it" is the one that matters most if the home server is taken. It rests on settings nothing re-reads.

- `the nightly backup › pen test I4: the off-site key and Object Lock, against the throwaway bucket › today_ lets the backup's off-site credential delete the backup it has just sent to the throwaway bucket, and counts that night as backed up all the same` / `fails the night, loudly, when the off-site credential can delete the backup it sent`
- `the nightly backup › pen test I4: … › can't stand in for Object Lock: the deploying page's check, run against the throwaway bucket, deletes its probe and never says the delete was refused`
