# F3: Events: forging, device clocks and the idempotency key

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #217 (F3). It names exploit chains, so it is kept private on the same terms as the PRD. How a finding is filed, triaged and verified is in [the findings workflow](../README.md).

F3 answers [H10](../../product-requirements-document/pen-testing.md#h10-a-device-can-write-any-event-its-family-could-have-earned--medium): a Family Device can write any event its Family could have earned, with any time, and an event's id is a global key. Forging within one's own Family is a Child cheating their own game, which [ADR 0004](../../architectural-decision-record/0004-offline-play-records-events-the-server-decides.md) accepts, so F3 probes the parts that cross a boundary: another Family's Children and event ids, the Check History a Teacher reads, and what a device's clock decides. The cost of a Family's growing history is F4's.

The rules probed:

- ADR 0004: a device appends events, "the server replays the events and is the only place that works out Mastery, Placement, Star balances and the Family Chest". "When something happened is the device's clock … Children altering the clock isn't treated as a threat." The server stores when it received each event "as a sanity check".
- [ADR 0031](../../architectural-decision-record/0031-the-challenge-arena-practises-the-statutory-checks.md) (the Challenge Arena): "Teachers see the same [Check History] read-only … Like everything else, scores are worked out on the server from events".
- [ADR 0031](../../architectural-decision-record/0031-classmates-can-see-each-others-rooms.md) (Classmates' Rooms): "a Child can visit classmates only while their own Room can be visited", and a device sees "no classmate whose Parent hasn't opted in".
- Section 9 of `wizzaroo.md` and [ADR 0027](../../architectural-decision-record/0027-row-level-security-through-a-reach-role.md): row-level security checks the same reach again, so a query that forgets its filter still can't cross a Family.
- The PRD's checks: "An idempotency key is bound to its payload and its owner", and "A rule enforced in one layer is a finding".

The code is `src/server/family-devices/play-event-routes.ts` (the upload), `src/server/family-devices/classmate-room-routes.ts`, the replay in `src/server/children/family-rewards.ts`, `child-progress.ts` and `check-histories.ts`, and the policies on `play_events` and `room_showcases` (`src/server/drizzle/0018_row-level-security.sql`, `0020_schools-and-teachers-reach.sql`, `0023_rooms-and-classmates.sql`, `0029_schools-approve-classmate-visits.sql`).

## The probes

Every probe is in `src/integration.test.ts`, under `against a real Postgres › pen test F3: event forging, device clocks and the idempotency key`. A refuted probe is a passing test. A confirmed one is an `it.fails` for the property that should hold, beside a `today_…` test pinning what happens now. Stars, Mastery, time spent and Check History are read as `teacherAYear3` reads them, from `GET /api/school-children`, unless a test says otherwise.

### Events naming another Family's Child or gift recipient

The upload collects every `childId` and `giftForChildId` in the batch and refuses the whole batch with `ChildNotFoundError` (404) unless every one is a Child of the device's Family.

Since the fix for #283 (D3), the upload stores the events naming the device's own Children and lets go of every event naming any other, answering `200 {"letGoPlayEventCount": n}`, so a Child deleted from the Family doesn't hold up their siblings' play. The verdict holds: no event naming another Family's Child is stored, and the answer names no Child. The probe below is renamed to `lets go of every event in an upload that names another Family's Child, or makes one a gift's recipient, storing none of them and only the device's own Family's play beside them (#283)`, and Cara's own Activity in the first batch is now stored.

- `events naming another Family's Child or gift recipient › refuses a whole upload that names another Family's Child, or makes one a gift's recipient, and stores none of it`. Each of these is 404, and none of the six events is stored:
  - `familyDeviceA2` sending an Activity for Cara and one for Ada in one batch;
  - `familyDeviceA2` sending a Gift from Cara to Ada;
  - `familyDeviceB` sending an Activity for Ada;
  - `familyDeviceB` sending a Gift from Eli to Cara;
  - `familyDeviceA1` sending an Activity for Eli;
  - `familyDeviceA2` asking for Classmates' Rooms with Ada as the visitor.

#### F3-1: the rule is the API's alone

`play_events_within_reach` is `FOR ALL … USING (wizzaroo_can_reach_family("family_id"))`. With no `WITH CHECK`, Postgres checks a new row against the same expression, which looks at `family_id` and nothing else. The foreign key on `child_id` is checked as the table's owner, so it accepts any Child. A Family's reach therefore inserts a row with its own `family_id` and another Family's `child_id`.

What reads it depends on the column each read filters on:

- `loadCheckHistories` and `loadPlaySummaries` select by `child_id` alone;
- `play_events_within_teacher_reach` lets a Teacher read a row by `child_id` (`wizzaroo_teacher_can_reach_child`), and the Admin reaches every row;
- the Child's own Parents reach only rows whose `family_id` is theirs, so they never see it;
- `loadFamilyRewards` selects by `family_id`, and the replay skips a Child who isn't in the Family, so Stars and Mastery don't move.

- `… › refuses a Family Device's own reach in Postgres an event naming another Family's Child` (`it.fails`), beside
- `… › today_lets a Family Device's reach in Postgres write an event naming another Family's Child, which that Child's Teacher and the Admin then read in their Check History while their Parents don't`. Within `familyDeviceA2`'s reach (`familyA2`, no user), a `check-finished` for Ada with seven questions, all right, is inserted. `teacherAYear3` and the Admin each see a 7 out of 7 in Ada's Check History; `coParentA1` doesn't. **#323**: _fixed, unverified (#323)_

Read from the code and not probed: the same row with a `session-started` and `session-ended` would add to Ada's time spent as her Teacher and the Admin see it, and, as F3-3 shows, could make their lists answer 500. A Family's reach also inserts rows naming its own `family_id` with another Family's `family_device_id`, which nothing reads.

The upload's own check holds, so this needs a query bug, or SQL of the attacker's own, inside a Family Device's reach. That is the case the second wall exists for, and the PRD's targets put a separation rule enforced in one layer at high.

### An event id already used by another Family

`play_events.id` is the table's primary key, and the upload inserts with `onConflictDoNothing({ target: playEvents.id })`. Postgres checks a primary key across every row, whatever the reach can see, so an id that is already anyone's makes the insert do nothing. The route answers 204 either way, and only its log line counts what was stored.

- `an event id already used by another Family › refuses with a 409 an event whose id is already another Family's, rather than answering as if it were kept` (`it.fails`), beside
- `… › today_answers 204 to an event whose id is already another Family's, or already its own with another body, and drops it without a word, while the Stars show whether the id was taken`. **#326**: _fixed, unverified (#326)_
  - `familyDeviceA2` sends an Activity for Cara whose id is one of Family A1's fixture events (204). Family A1's row is unchanged, and Cara's Stars don't move.
  - `familyDeviceA1` sends the same id again for Ben, with another Skill (204). The row is still Ada's, as it was.
  - The same Activity with a new id gives Cara 3 Stars (204).

Ids come from `crypto.randomUUID()` on the device, so another Family's id can't be guessed. To lose another Family's play this way, someone has to know an id before that Family's device has sent it. A device that has been signed out, or a Parent who has left the Family, knows only ids already stored, which do nothing. So the harm is to a Family's own play: an id sent twice with different bodies keeps the first and says nothing. Low.

_Fixed, unverified (#326)._ An event whose id is already stored by another Family, a row the device's reach can't see, or by its own with another body, or sent twice in one upload with different bodies, is refused with `409` naming the ids (`takenPlayEventIds`), and the upload is rolled back whole, so nothing is half-stored. The same event sent again with the same body is still `204`. The device's outbox gives the named events new ids (`crypto.randomUUID()`) and sends the batch again at once, so the play is kept and the outbox isn't jammed; it gives up for that try after three refusals in a row. The probes are now `… › refuses with a 409 an event whose id is already another Family's, rather than answering as if it were kept` and `… › refuses with a 409 naming the id an event whose id is already another Family's, or already its own with another body, storing nothing of the upload, while the same event sent again stays a harmless 204 (regression)`.

### Forged `question-answered` and `activity-finished` events

The replay (`applyPlayRecords`) gives 3 Stars for each Activity finished, unless its Skill was Mastered before that day, and 20 when a Skill becomes Mastered. A Skill is Mastered after enough good days on separate local dates (3 at 80% for Number bonds to 10). Nothing bounds how many Activities a day holds, how long one took, or how many days one upload covers.

The probe sends, from `familyDeviceA1`, a hundred Activities finished today in Adding three-digit numbers, at Oasis Pools, and then a right answer in Number bonds to 10 on each of the three days before today. Both uploads are 204.

- `forged question-answered and activity-finished events › gives a Child no Stars, Mastery or Trophy for a hundred Activities and three days of right answers a device sends in one go` (`it.fails`), beside
- `… › today_gives a Child the Stars, a Mastered Skill and a Trophy Classmates see for every Activity and right answer a device states, as their Parents and Teacher read it`. Ada gains 320 Stars, the same for `coParentA1` and `teacherAYear3`. Number bonds to 10 goes from never played to Mastered. Oasis Pools needs 90 Stars for its Trophy; Ada had 18 there from the fixtures' six Activities and gains 300, so the Trophy now stands in her Room, where Cara sees it on a Classmate visit. **#327**: fixed by ADR 0004's end (#327). The pair is now `… › names, in ADR 0004, a second School as the end of taking the Stars, Mastery and Trophies a device states, what replaces it, and a review date (#327)`, and the behaviour, which stays, `… › gives a Child the Stars, a Mastered Skill and a Trophy Classmates see … as documented under ADR 0004 until a second School is added`.
- `… › moves no Check History with forged questions and Activities, since only a finished Timed Check goes into it` (refuted). Ada's Check History is the same before and after.

Read from the code and not probed: a hundred Activities fill the Family Chest three times over, giving every Child in the Family its Items, and Games in the Region unlock as the Stars arrive. An `item-bought` needs no Stars at all: [ADR 0004](../../architectural-decision-record/0004-offline-play-records-events-the-server-decides.md) honours every purchase and stops the balance at zero, so a device gets every Item for sale, Gifts included, without forging any play. All of this stays within the Family except the Trophies, which Classmates see, and the Stars and Mastery, which the Teacher sees.

The PRD's H10 says ADR 0004 accepts forging within the Family. Nothing records when that has to stop being true. The second-School gate brings Teachers who read Mastery as evidence of what a Child can do, so F3-5 is filed as a documented decision with no recorded end. Low.

### Forged `check-finished` events and the Check History a Teacher reads

A `check-finished` carries its own outcomes: each question's key, type, Skill, whether it was right and in time, and how long it took. `buildCheckHistory` scores them as sent and sorts the Check History by `happenedAt`, newest first, so the first entry is the one a Teacher's "latest Check score" shows.

The probe sends, from `familyDeviceA1`, a Multiplication Tables Check of 50 questions, all right and in time, each in a millisecond, finished at `9999-12-31T23:59:59Z` on the local date `9999-12-31`. In the same upload it sends a Check finished now with one right out of two. The upload is 204.

- `forged check-finished events and the Check History a Teacher reads › lists the Check finished now as the latest in the Check History a Teacher reads, ahead of one a device dated in the year 9999` (`it.fails`), beside
- `… › today_puts whatever score and date a device states into the Check History a Teacher reads, and keeps a Check dated 9999 as the latest ahead of one finished now`. `teacherAYear3` sees the 50 out of 50 first, dated 31 December 9999, and the Check finished now second. **#324**: _fixed, unverified (#324)_

ADR 0031 says scores are worked out on the server from events. They are: a score is counted from outcomes the device states, and nothing checks that a question was asked, that its time is possible, or that the Check finished on a date that has happened. A real Check finished afterwards never displaces the one dated 9999. This crosses from a Family to the Teacher who reads the score as the Child's, so it is filed apart from F3-5: a control weaker than its documentation says. Medium.

_Fixed, unverified (#324)._ The upload lets go, through #283's path (`200 {"letGoPlayEventCount": n}`, so the device forgets the batch and its outbox isn't jammed), of any event that happened more than an hour after the server received it or more than 400 days before, the time a Family Device's credential lasts unused (#301), and of any whose `localDate` is later than the UK's tomorrow or more than 401 days before its today. It also lets go of a `check-finished` with more outcomes than that Check's paper asks (25 for the Multiplication Tables Check) or with a right answer taken in under 200 ms. A Check History lists a Check stored before the fix with a later date by when it was received, so it never stays the latest. The probe's Check finished now takes 2.5 s a question, as a Child would; the 9999 Check is let go (`letGoPlayEventCount: 1`) and the Check finished now is listed first. The probes are now `… › lists the Check finished now as the latest in the Check History a Teacher reads, ahead of one a device dated in the year 9999`, `… › lets go of a Check a device dated in the year 9999, … (regression)`, `… › lets go of each Check it can't stand behind on its own … (regression)` and `… › lists a Check stored with a date after it arrived by when it arrived … (regression)`.

### `happenedAt` and `localDate` in the far past and future

The upload's schema takes any `date-time` and any `date` from 0001 to 9999 (year 0000 is D4's, #297). `happenedAt` orders the replay and Check History, and Sessions are timed from it. `localDate` is the day a Mastery rule counts. The server stores `received_at` beside each event, which ADR 0004 calls a sanity check, but only the Family's export reads it: nothing compares it with `happenedAt`.

#### F3-3: time spent overflows

`loadPlaySummaries` sums each Child's Sessions in seconds and casts the sum to `integer`, whose largest value is 2,147,483,647 seconds, about 68 years. One query sums every Child the caller is shown.

- `happenedAt and localDate in the far past and future › keeps serving the Teacher's and the Admin's lists of Children when one Child's Session runs from 1900 to 2100 on their device's clock` (`it.fails`), beside
- `… › today_overflows time spent with one Session from 1900 to 2100, so the Teacher's and the Admin's lists answer 500 for every Child in them while the other Family's Parents still see theirs`. **#325**: _fixed, unverified (#325)_
  - `familyDeviceA2` sends a Session for Cara that starts on 1 January 1900 and ends on 1 January 2100 (204), which is 6,311,433,600 seconds.
  - `GET /api/school-children` answers 500, with the failing query, for `teacherAYear3` and for the Admin. So does `teacherAYear3`'s progress for Cara.
  - `teacherAYear3`'s progress for Ada, and `coParentA1`'s `GET /api/children`, answer 200.
  - Once the Session is deleted, the Teacher's list answers 200 again.

So one Family's device takes the Teacher's whole class away from them, Family A1's Ada included, and every Child from the Admin, until someone deletes the Session in Postgres. Nothing on any dashboard says which Child or event is to blame. Read from the code and not probed: Family A2's own Parents' `GET /api/children` and the Admin's progress for Cara answer 500 too. It takes one upload and no knowledge beyond a device's own token. While H7 is open, each 500 also returns the query and its parameters. Medium.

_Fixed, unverified (#325)._ Two layers. The upload lets both of the Session's events go, by the dates #324 bounds. And time spent counts each Session for no more than a day, sums them as `numeric`, which no number of Sessions overflows, and caps the sum at the largest `integer` before casting it for the answer; `loadPlaySummaries` is the only query that sums Session lengths. The probes are now `… › keeps serving the Teacher's and the Admin's lists of Children when one Child's Session runs from 1900 to 2100 on their device's clock`, `… › lets go of a Session a device's clock runs from 1900 to 2100, … (regression)`, and `… › counts a Session already stored from 1900 to 2100 as one day, and caps the time spent of more such Sessions than an integer holds, … (regression)`, which stores 24,856 such Sessions as the owner and reads 2,147,483,647 seconds with every list answering 200.

#### Daily limits

A Parent's daily time is kept on each device, counted per device from its own clock ([the guide](../../guide/parent-limits-and-sound.md)). The server stores the limit and enforces none of it.

- `… › a daily limit › never counts more of one day's play than the Child's daily limit allows` (`it.fails`), beside
- `… › a daily limit › today_keeps a six-hour Session on a day whose limit is 30 minutes, and adds all of it to the time spent Parents and Teachers see`. `coParentA1` sets Ada's daily time to 30 minutes (200). `familyDeviceA1` sends a Session that ended now and started six hours before (204). Ada's time spent rises by 21,600 seconds. **#327**: fixed by ADR 0004's end (#327). The pair is now `… › a daily limit › names, in ADR 0004, a second School as the end of counting a daily limit on each device by its own clock, …` and the behaviour, which stays, `… › a daily limit › keeps a six-hour Session … as documented under ADR 0004 until a second School is added`.

The guide says two devices together may go over a limit, and ADR 0004 says a Child altering the clock isn't a threat. Turning a device's clock on a day gives a fresh day's time on it. That is the documented decision F3-5 records.

#### Local dates thousands of years away

- `… › local dates thousands of years away › refuses a question answered on a local date thousands of years from the day the server received it` (`it.fails`), beside
- `… › local dates thousands of years away › today_takes a device's local dates as they come, so right answers dated in the year 9000 make a Skill Mastered with no review for 7,000 years, and ones dated 1900 make one Mastered and due for review`. **#327**: _fixed, unverified (#324, #327)_. The answers are let go with #324's local-date bound rather than refused with a 400, which would jam the device's outbox: the `it.fails` is now a plain test that both uploads answer 200 and store nothing, and the `today_` is `… › lets go of right answers dated in the year 9000 or 1900, so no Skill is Mastered, or due for review, … (regression)`.
  - `familyDeviceA1` sends right answers in Adding within 20 on 1, 2 and 3 January 9000 (204). The Teacher sees it Mastered, with its next review on 10 January 9000.
  - It sends right answers in Adding two-digit numbers on 1, 2 and 3 January 1900 (204). The Teacher sees it Mastered and due for review since 10 January 1900.

Each Mastered Skill also gives 20 Stars. An Activity finished on a local date in the future also makes that date the Child's last day played, so the Welcome back Item, given for a day later than that, never comes again (read from the code and not probed). All of it stays within the Family, apart from what the Teacher reads, so it is part of F3-5.

### Classmate Room visits from a device that hasn't opted in

The route reads the visitor through the device's Family and answers an empty list unless the visitor's own switch and their School's approval are both on. `wizzaroo_can_visit_classmate_room` checks both Children's switches, the School's approval, the same School and Year Group, different Families, and that the caller is a Family Device of the visitor's Family.

- `Classmate Room visits from a device that hasn't opted in › shows a Child who hasn't opted in, or whose School hasn't approved visits, no Classmate's Room, and never shows a Room whose Child hasn't opted in` (refuted). Each answers 200:
  - Dev on `familyDeviceA2`, who hasn't opted in, sees no Room;
  - Ben on `familyDeviceA1`, who hasn't opted in, sees no Room;
  - Eli on `familyDeviceB`, opted in at School B, which hasn't approved visits, sees no Room;
  - Ada sees exactly Cara's Room, and never Dev's;
  - Cara sees exactly Ada's.
- `… › shows no Classmate's Room, through the API or in Postgres, to a Family none of whose Children has opted in` (refuted). With Cara's switch turned off as well as Dev's, both see no Room, and Family A2's reach in Postgres reads only its own Children's rows in `room_showcases`.
- `… › lets a Family's reach in Postgres see an opted-in Classmate's Room while any one of its Children has opted in, as a sibling on the same Family Device already can by choosing that Child` (refuted). With Cara opted in, Family A2's reach reads Ada's row as well as its own. In Postgres the visitor's switch is the Family's, not the Child's. Dev could see the same Room through the API by choosing Cara on the device, and [ADR 0005](../../architectural-decision-record/0005-family-devices-and-picture-passwords.md) and the PRD put a Picture Password outside the boundary. So this isn't a weakness: what a Family Device's reach sees is what any Child on that device can.

Forged Trophies do reach Classmates' Rooms (above, F3-5): a visitor sees what the replay gives, and the replay takes what the device says.

## Checked outside the suite

The Postgres claims behind F3-1, F3-3 and F3-4 were also run in PGlite 0.5.16 (Postgres 18.6 compiled to WebAssembly), with every migration in `src/server/drizzle/` replayed and a few rows of its own. The replay was checked the same way, with the curriculum's own functions: a hundred Activities and the three sets of right answers give 300 Stars and 20 for each Skill Mastered, the Oasis Pools Trophy, Mastery and review dates as above, and a Check History with the 9999 Check first.
