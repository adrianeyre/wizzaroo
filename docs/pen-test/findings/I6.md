- **Probes:** the `pen test I6: the CI supply chain and dependency currency` block in `src/integration.test.ts`, in the gated run. A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now. A refuted probe is a passing test. None of these probes touches Postgres: they read the workflows, the lockfile and the images, and run `pnpm` in scratch projects under `tmpdir()`. The `pnpm audit` probes need the npm registry, and skip loudly without it (`SKIPPED pen test I6's advisory probes: …`).

A tag is a pointer its publisher, or anyone who takes over the publisher's account or token, can move to any commit, and the next run executes it. Two of the four are third-party: `pnpm/action-setup` and `amannn/action-semantic-pull-request`. Code run that way in the `pr-checks` job has:

- the whole repository and its history in the workspace (`fetch-depth: 0`), `docs/pen-test/` and this PRD's unremediated critical chains included, and an unrestricted network to send them out on;
- the job's own result to report: the build, typecheck, lint and tests can be made to pass whatever the pull request holds;
- a token that reads the repository's contents (or, in the title check, its pull requests), and no secret, since none is passed.

The same three actions are pinned by SHA two jobs further down the same file, so the repository already holds the pattern; the tagged lines predate it. `CODING_STANDARDS.md`'s toolchain table names `actions/checkout@v7`, `pnpm/action-setup@v6` and `actions/setup-node@v7` as the estate's versions, which says which major to use, not that a tag is the pin. A boundary with no defence in depth: medium. Filed as #333.

- `pins every action in the two dependency jobs by a full commit SHA`
- `today_pins four actions to a tag their publisher can move: checkout, pnpm's setup and setup-node in the pr-checks job, and the PR title check`
- `it.fails`: `pins every action in every workflow by a full commit SHA`

**Fixed, unverified (#333).** Every `uses:` in every workflow is pinned by a full commit SHA, with the release it was taken from in a comment beside it: `actions/checkout` v7.0.1, `pnpm/action-setup` v6.1.1 and `actions/setup-node` v7.1.0 in the `pr-checks` job (the same SHAs the dependency jobs already used), and `amannn/action-semantic-pull-request` v6.1.2 in the title check. ## Permissions, triggers, secrets and the lockfile: refuted

- **Permissions.** `pr-checks.yml` sets `contents: read` and `lint-pr-title.yml` `pull-requests: read`, each at the top of the file, and no job sets `permissions:` of its own, so every job's token is read-only, whatever the repository's default.
- **Triggers.** Both run on `pull_request` to `main` and on `workflow_dispatch`, nothing else. `pull_request` runs a fork's pull request with a read-only token and no secrets, which `pull_request_target` would not.
- **Secrets and expressions.** The only `${{ … }}` in either file is `secrets.GITHUB_TOKEN`, passed to the PR title check as its action documents. No `run:` evaluates an expression, so a pull request's title, branch name or body can't become shell. No other secret is named, so a compromised step has none to take.
- **`persist-credentials`.** The `pr-checks` job's checkout leaves its read token in `.git/config` while dependencies install and tests run; the `dependency-advisories` job sets `persist-credentials: false`. That token reads the repository's contents, which the job has already checked out with its whole history, so it gives a script in that job nothing it doesn't already hold. Recorded, not filed.
- **The lockfile.** The one `pnpm install` in CI and the one in the `Dockerfile` are both `--frozen-lockfile`. The lockfile's `packages:` holds 557 entries and 557 `resolution: {integrity: sha512-…}` lines, and no `tarball:`, `repo:`, `directory:` or `commit:` source, so every package comes from the registry and is checked against its hash.

Tests:

- `grants each workflow's token one read scope, at the top, with no job widening it`
- `runs each workflow only on a pull request to main or by hand, never on pull_request_target, workflow_run, issue_comment or push`
- `evaluates no expression in any workflow but the GITHUB_TOKEN handed to the PR title check, so no secret and no pull request's text reaches a step`
- `installs only from the committed lockfile, in CI and in the image, and the lockfile takes every package from the registry by its sha512 integrity`

## The advisory gate: refuted as missing

H15 was written at `35cd990`, before #227 added the `dependency-advisories` and `dependency-review` jobs to `pr-checks.yml`. The probe checks the gate does what the local standards say:

- **Its level.** `dependency-advisories` runs `pnpm audit --audit-level=high`, `dependency-review` sets `fail-on-severity: high`, and the local standards say "The level is **`high`**". No advisory is waived: `pnpm-workspace.yaml` has no `auditConfig.ignoreGhsas`, and the review has no `allow-ghsas`.
- **It fails on a high advisory.** A scratch project whose lockfile holds `lodash` 4.17.20 makes the gate's command exit non-zero, and `pnpm audit --json` lists a `high` advisory against `lodash` (on 17 November 2026, GHSA-35jh-r3h4-6jhm and GHSA-r5fr-rjxr-66jc).
- **It fails closed.** With no lockfile it exits non-zero ("No pnpm-lock.yaml found"), and with the advisory endpoint unreachable it exits non-zero ("Failed to request the audit endpoint"), so a registry outage turns the check red rather than green.

What the probe can't show from inside the repository is whether `dependency-review` can run at all. GitHub's dependency review on a private repository needs the dependency graph and, for private repositories, GitHub's code security licence; without them the action fails every pull request. That is a repository setting, recorded in this issue's comment as unverified.

- `fails a pull request at the advisory level the local standards set, in both dependency jobs, and waives no advisory`
- `fails the gate's own command on a lockfile holding a package with a high advisory, on a project with no lockfile, and when the advisory endpoint can't be reached`

## Dependency currency: confirmed

`pnpm outdated` on 17 November 2026 lists five direct dependencies behind their latest, none by a major but TypeScript: `@fastify/static` 10.1.10 (10.1.11), `nodemailer` 10.5.0 (10.6.0), and in development `eslint` 10.14.0 (10.15.0), `pnpm` 12.18.0 (12.21.0) and `typescript` 6.0.3 (7.0.2). Currency today is good, and nothing keeps it so:

- **No scheduled audit.** `pnpm audit` runs only in `pr-checks.yml`, on `pull_request` and `workflow_dispatch`. An advisory published against a package already in the lockfile, a production one such as `fastify` or `@simplewebauthn/server` included, is reported only when the next pull request is opened, and then fails that unrelated pull request.
- **No Dependabot or Renovate.** There is no `.github/dependabot.yml`, no Renovate configuration and no `renovate` key in `package.json`. `CODING_STANDARDS.md`'s repository shape asks for `.github/dependabot.yml` with the `npm` and `github-actions` ecosystems, and `docs/standards/local.md` records no deviation. Nothing proposes an update to a package, and nothing moves the four SHA-pinned actions: a SHA pin with nothing to update it keeps an action's own security fixes out for good. Fixing I6-1 by pinning the other four by SHA would freeze them too.
- **Moderate advisories.** The two above appear only in a job log on each pull request; no issue or list tracks them for when their parents move.

GitHub's Dependabot alerts read the dependency graph, which the local standards say can miss most of a pnpm tree, so a scheduled `pnpm audit` is the watch that reads the lockfile. Whether Dependabot alerts are on for the repository is a setting this sandbox can't read. No boundary is crossed and currency is good today: low. Filed as #334.

- `today_runs pnpm audit only on a pull request or by hand, never on a schedule, so an advisory against a package already merged waits for the next pull request`
- `it.fails`: `runs pnpm audit against the lockfile on a schedule, so an advisory against a package already merged is reported without a pull request`

**Fixed, unverified (#334).** `.github/dependabot.yml` watches the `npm` packages (pnpm's lockfile included) and the `github-actions` ecosystem, daily, so it proposes updates to packages and to the SHA-pinned actions alike. `.github/workflows/scheduled-audit.yml` runs the gate's own command, `pnpm audit --audit-level=high`, against the lockfile every day at 06:17 UTC and by hand, with a read-only token and its actions pinned by SHA; a high advisory against a package already merged fails that run, which GitHub reports to the owner, without waiting for a pull request. The two `it.fails` are now plain tests, and their `today_` probes are now `runs pnpm audit on every pull request and every day … (regression)` and `has Dependabot as its one update configuration … (regression)`. The triggers and permissions probes now list the third workflow: `schedule` and `workflow_dispatch`, with `contents: read`. Whether Dependabot version updates and alerts are switched on is still a repository setting the repository can't show.

- `today_has no Dependabot or Renovate configuration, so nothing proposes an update to a package or to an action pinned by SHA`
- `it.fails`: `has a Dependabot configuration that watches the npm packages and the GitHub Actions`

Walking every package under `node_modules/.pnpm` for a `preinstall`, `install` or `postinstall` script, or a `binding.gyp` (which npm builds with no script), finds four:

| Package               | Script                                                                | Pulled in by                                             | `allowBuilds` |
| --------------------- | --------------------------------------------------------------------- | -------------------------------------------------------- | ------------- |
| `esbuild` 0.28.2      | `postinstall`: `node install.js`                                      | `tsx` and `vite` (development)                           | `true`        |
| `cpu-features` 0.0.10 | `install`: `node buildcheck.js > buildcheck.gypi && node-gyp rebuild` | `ssh2` ← `docker-modem` ← `dockerode` ← `testcontainers` | `false`       |
| `protobufjs` 7.6.6    | `postinstall`: `node scripts/postinstall`                             | `@grpc/proto-loader` and `dockerode` ← `testcontainers`  | `false`       |
| `ssh2` 1.17.0         | `install`: `node install.js`                                          | `docker-modem` ← `dockerode` ← `testcontainers`          | `false`       |

`allowBuilds` names exactly these four, and allows only `esbuild`. The three denied ones are optional speed-ups for Testcontainers' Docker client, and their builds didn't run (no `build/` folder exists). pnpm 12 refuses what the list doesn't name: in a scratch project carrying the repository's `pnpm-workspace.yaml` and a local dependency whose `postinstall` writes a marker file, `pnpm install --offline` exits 1 with `ERR_PNPM_IGNORED_BUILDS` and the marker is never written; naming it `false` installs it, still without the marker. So a new dependency with an install script fails the install until someone names it, in a commit a reviewer sees.

`esbuild`'s `postinstall` checks its platform binary, which arrives as an optional dependency pinned and hashed in the lockfile. Read, not run: if that optional dependency is missing, `install.js` falls back to `npm install` or to downloading the package from `registry.npmjs.org` itself, outside the lockfile's integrity check. CI and the image install optional dependencies, so the fallback doesn't run there.

- `names in allowBuilds exactly the installed packages that carry an install script, and allows only esbuild's to run`
- `refuses an install whose dependency carries an install script allowBuilds doesn't name, and runs no script it denies`
