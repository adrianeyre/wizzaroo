# B1: every route compared with the wrapper it should have

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #206 (B1) in [the first pen-test round](../../product-requirements-document/pen-testing.md#scope-partition). It names how reach is chosen route by route, so it is kept private on the same terms as the PRD.

**The trust boundary.** Every route that acts for someone has to start by choosing one wrapper from `src/server/auth/signed-in-parent.ts` or `src/server/family-devices/signed-in-family-device.ts`. The wrapper turns the request's credential into a caller and refuses anyone the route isn't for. It then runs the work inside `runWithinReach` (`src/server/reach.ts`), the only place the `wizzaroo_reach` role and its row-level security come in. A route that chooses no wrapper, or a weaker one than it needs, still runs, as the database owner. That is the API wall of [section 9 of `wizzaroo.md`](../../product-requirements-document/wizzaroo.md#9-technical-architecture), [ADR 0026](../../architectural-decision-record/0026-schools-and-teachers.md) and [ADR 0027](../../architectural-decision-record/0027-row-level-security-through-a-reach-role.md).

**H entries.** The opening register names no H entry for B1, so this note amends none. Two neighbours are left to their own scope issues: what the `runAsSignedInUser` routes let an _established_ staff member's password-only sign-in do is H1 (A5), and the passkey hand-off answering anyone with the code is H16 (A3).

## The wrapper table

Every route the server registers at this commit, as `printRoutes` lists them, with the wrapper it runs under and the one it should have. Each `GET` route also answers `HEAD` through the same handler, so it has the same wrapper. Probe 1 fails if a route is added or removed without this table changing.

"Should be" comes from section 8 of `wizzaroo.md` (who can do what), [the signing-in guide](../../guide/signing-in.md), ADR 0026, ADR 0027 and [ADR 0036](../../architectural-decision-record/0036-adding-a-passkey-on-a-phone-by-qr-code.md). The rungs, weakest first:

- **User** (`runAsSignedInUser`): any live sign-in, with or without a second factor. The guide says staff who haven't set up a second factor "see only Your account until they set one up". These routes are that account, so they can't ask for the second factor.
- **Adult** (`runAsSignedInAdult`): a sign-in that has its second factor if it is staff. The route then decides what the caller reaches through `reach-rules.ts`.
- **Parent**, **Staff** (the Admin or a Teacher) and **Admin**: an Adult who also holds that role.
- **Family Device** (`runAsSignedInFamilyDevice`): the device cookie, and no adult.

## Why each route with no wrapper needs none

Each of these is reached before anyone is known, so it is checked as the database owner as ADR 0027 allows. Where it acts on an account, it has a credential of its own in place of a sign-in.

- **The client files and `/`.** The offline-first PWA has to load before anyone signs in, and open with no network ([ADR 0004](../../architectural-decision-record/0004-offline-play-records-events-the-server-decides.md)). They hold no data.
- **`GET /health`.** Compose's health check and the deployment's own checks read it, so it can't need a credential. It answers `{"status":"ok"}` and nothing else. Its 500 carries driver text when Postgres is down, which is H7 (I1).
- **`GET /voices/:fingerprint/:name`.** Added after the test ([ADR 0062](../../architectural-decision-record/0062-read-it-to-me-speaks-with-every-piper-voice-on-the-device.md)). It serves Read it to me's public-domain and openly licensed Piper voices to whoever loads the app, as the client's own files are. It answers only the 22 pinned files, from a folder the app reads but never writes, and 404 for anything else; it reads no database row.
- **`POST /api/sign-in`, `/api/passkey-sign-in-options` and `/api/passkey-sign-ins`.** These are how a sign-in is made.
- **`POST /api/sign-in/two-factor-code`.** The second step of a password sign-in. Its credential is the pending sign-in cookie, which the password step set and which lasts five minutes and five tries.
- **`POST /api/sign-out`.** Its credential is the sign-in cookie it ends, and it deletes only that sign-in's row. It has to clear the cookie even when a wrapper would refuse it, for a deactivated adult or an expired sign-in, so it takes no wrapper.
- **`POST /api/password-reset-requests` and `/api/password-resets`.** The adult has forgotten their password, so they can't be signed in. The request answers 204 whatever the address. The reset's credential is the emailed token.
- **`POST /api/email-address-confirmations`.** The link is opened from a mailbox, often on another device. Its credential is the emailed token.
- **`POST /api/invite-acceptances`.** The new adult has no password yet. Its credential is the Invite token.
- **`POST /api/passkey-hand-off-registration-options` and `/api/passkey-hand-off-passkeys`.** ADR 0036: the phone isn't signed in, and the hand-off token from the signed-in computer is the credential.

Probe 3 pins exactly these 13 as answering a caller with no credential with something other than a sign-in refusal.

### 1 and 2: the table, and no route weaker than it

For each route, the probe sends every caller one rung below its table entry, with a body the route's schema accepts. It asserts that the route's own wrapper refuses them, with that wrapper's status and message:

| Table entry   | Callers that must be refused, and how                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------- |
| User          | No credential, and `familyDeviceA1`'s cookie alone: 401 `Sign in to Wizzaroo first`                                       |
| Adult         | As User, and `teacherBYear3` before a second factor: 403 `second-factor-required`                                         |
| Parent        | As Adult, and `teacherAYear3`: 403 `Only a Parent can do this`                                                            |
| Staff         | As Adult, and `coParentA1`: 403 `Only the Admin or a Teacher can do this`                                                 |
| Admin         | As Adult, and `coParentA1` and `teacherAYear3`: 403 `Only the Admin can do this`                                          |
| Family Device | No credential, and `coParentA1`'s sign-in cookie: 401 `This browser isn't a Family Device, or a Parent has signed it out` |

The refusal names the wrapper, so a route under a different wrapper from its entry fails the probe too. Checked without a database, every probe body passes its route's schema and the route's own checks and reaches the wrapper: each wrapped route answered 401 with no credential.

### 4: nothing ties a route to its wrapper (#259)

_Fixed, unverified (#259):_ every route declares its wrapper as `config.reach`, an `onRoute` hook in `buildHttpServer` refuses an `/api/` route that declares none and runs the declared wrapper's check as the route's first `onRequest` hook, and `src/server/http-server.test.ts` compares each route's declared wrapper with the table above.

A wrapper is a function each handler remembers to call. Fastify knows nothing of it, and nothing that registers a route, no hook, type or test, refuses one without it. A route that forgets it runs on `database`, the owner's connection, outside any reach. Row-level security doesn't apply there, so the second wall doesn't back up the first. The suite's tests for this table, ADR 0027's test that every table has row-level security, and the existing route sweeps in "two Families" and "Family Devices" all walk the routes that exist. None of them knows what wrapper a new route needs.

The `today_` test registers `GET /api/b1-probe/unwrapped-children` on a server built by `buildHttpServer`, reading `children` as handlers do. A caller with no credential gets every fixture Child in every Family. The `it.fails` asks the server to refuse to register it.

**The test to file as the fix.** Make the wrapper a property of the route, declared where the route is registered, rather than a call in the handler. For example, `config: { reach: "parent" }` on every route, or one `registerReachRoute(server, reach, …)` that both registers and wraps. Then:

1. an `onRoute` hook in `buildHttpServer` throws for any route under `/api/` that declares no reach, so the server doesn't start, and `none` has to be written out with its reason;
2. the hook, or the helper, runs the declared wrapper as an `onRequest` hook, so a route can't declare one rung and call another. Running it there also answers B1-2;
3. a unit test in `src/server/http-server.test.ts`, which needs no Postgres, builds the server and asserts that the declared reach of every route equals a table like the one above. A route added without an entry, or with a weaker one, fails it. Every route with a wrapper refuses a caller with no credential before any database call, so that half runs without a database too;
4. this note's probes 1 and 2 stay in the gated run, where the signed-in rungs are checked against a real Postgres, and the `today_` test becomes the regression test for the hook.

### 5: the wrapper runs after the route has read the request (#260)

_Fixed, unverified (#260):_ #259's fix runs each route's declared wrapper check as the route's first `onRequest` hook, before Fastify reads the params, body or query, so a caller with no credential, or below the route's rung, gets that wrapper's refusal before any schema check, domain check or Picture Password hash. The `it.fails` now passes as a plain `it`, and the `today_` test is its regression test.

The wrapper is called inside the handler. So Fastify's schema validation, and anything the handler does first, runs for a caller with no credential:

- **32 of the 67 wrapped routes** answer an unauthenticated empty body with 400 and the schema's first complaint. That message names a required field, an enum's values or an id's format, for example `body must have required property 'classmateVisitsAllowed'`. Their params are checked the same way: `DELETE /api/admin/children/not-a-child-id` answers 400 `params/childId must match format "uuid"`. Only three routes put the wrapper first, the Admin's awards and audit log, through `buildSignedInAdminCheck` as `preValidation`. Its own comment gives the reason: "so a caller who isn't the Admin can't probe the route's schema".
- **Domain checks before the wrapper:** `POST /api/children`, `PUT /api/children/:childId` and `…/birth` work out the Year from the birth, and `POST /api/parents` and `POST /api/teachers` read the name and email address. So with no credential, they answer `That birth month and year is too young for Reception…` or `That isn't an email address`.
- **CPU before the wrapper:** `POST /api/children`, `PUT /api/children/:childId/picture-password` and `PUT /api/play/children/:childId/picture-password` hash the Picture Password (PBKDF2-SHA256, 100,000 iterations) before the wrapper runs. Measured against the built server with no database: about 8.5 ms of CPU per unauthenticated request, against 0.2 ms for a route that refuses first. That is about 120 requests a second to keep one core busy, from anyone, with no rate limit (H8).

The schema is in the source, which grey-box testers have, so nothing secret leaks. This is disclosure and cost, not reach. The `it.fails` sends every wrapped route an empty body with no credential and wants 401 from each. The `today_` test pins the 32 routes answered from their schema, and three of the domain answers.

### 6: the Parent wrapper keeps the Admin's reach (#261)

`runAsSignedInParent` passes `isAdmin` into the reach, so for an Admin who is also a Parent, every Parent route runs with row-level security letting them read every Family's rows. The owner is exactly that: `pnpm seed:owner` makes them Admin and Parent. The API's own filters keep each Parent route to `familyId` today. But section 9 of `wizzaroo.md` promises that "a query that forgets its filter still can't cross a Family", and on the owner's Parent routes that isn't so. Such a read would also not be in the Admin access log, since it is made as a Parent. `GET /api/family-export` is the exception: it sets the Admin's reach off by hand, as ADR 0027 asks, "so it can never include another Family". No other Parent route does. A Teacher who is also a Parent keeps their Teacher reads on Parent routes in the same way.

The probe registers `GET /api/b1-probe/parent-reach-children` under `runAsSignedInParent`, reading `children` with no filter, as a query that forgot its filter would. For the stand-in owner it returned all five fixture Children, where Family A1's two are what the test asks for.

Fixed, unverified (#261). `runAsSignedInParent` now runs the work within the Parent's own Family's reach alone, as the Family export does: the Admin's reach is off, and so are a Teacher's reads, which the policies now skip when `runWithinReach` sets `wizzaroo.own_family_only` (migration 0049). The route still learns the adult's roles, so `/api/family` still tells the owner they are the Admin.
