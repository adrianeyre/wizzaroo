# A5: the staff second-factor rule

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #201 (A5), which answers [H1](../../product-requirements-document/pen-testing.md#h1-a-staff-password-alone-enrols-a-second-factor--critical). It names an exploit chain, so it is kept private on the same terms as the PRD ([the findings workflow](../README.md)).

## The rule probed

Teachers and the Admin must sign in with two-factor authentication or a passkey (section 8 of [`wizzaroo.md`](../../product-requirements-document/wizzaroo.md), [ADR 0026](../../architectural-decision-record/0026-schools-and-teachers.md)). [Signing in](../../guide/signing-in.md#passkeys-and-two-factor-authentication) documents one exception: after a password-only sign-in, staff "see only Your account until they set one up". [ADR 0036](../../architectural-decision-record/0036-adding-a-passkey-on-a-phone-by-qr-code.md) relies on that same sign-in to show a new Teacher the QR code.

## How it was probed

Every probe is a test in the gated run, `src/integration.test.ts`, under `pen test A5: the staff second-factor rule`. That block has its own database, `pen_test_a5`, and reloads the fixtures before each probe, so no probe sees another probe's changes. It signs the Admin in with password and TOTP, and `teacherAYears5And6` with their passkey, through the credentials harness (`signInAsPenTestFixture`). It makes every password-only sign-in itself with the fixture's derived password, as an attacker holding only that password would.

| Fixture              | Id                                     | Used for                                                        |
| -------------------- | -------------------------------------- | --------------------------------------------------------------- |
| `teacherAYears5And6` | `e2000000-0000-4000-8000-ad0000000003` | The established Teacher: password and a passkey, no TOTP        |
| `teacherBYear3`      | `e2000000-0000-4000-8000-ad0000000004` | Staff with no second factor at all, 30 days after being created |
| `teacherAYear3`      | `e2000000-0000-4000-8000-ad0000000002` | Staff with TOTP, for the reset link                             |
| `admin`              | `e2000000-0000-4000-8000-ad0000000001` | Staff with TOTP, for the reset link; sends the Invites          |
| `schoolA`            | `e2000000-0000-4000-8000-5c0000000001` | The School the new Teacher is created at                        |
| `childA1Year5`       | `e2000000-0000-4000-8000-c10000000002` | Ben, in Years 5 and 6's reach, as proof of staff reach          |
| `childBYear3`        | `e2000000-0000-4000-8000-c10000000005` | Eli, in `teacherBYear3`'s reach, as proof of staff reach        |

**When, and what changed:** the probes ran only in the gated run, against its own database. No request was sent to the pen-test deployment, so nothing changed there. Inside `pen_test_a5` the probes add TOTP secrets, passkeys, password resets, Invites, an email address check for `a5-probe@pen-test.example`, and one new Teacher, `a5-new-teacher@pen-test.example`. Reloading the fixtures puts back every fixture they change, and the new Teacher's address keeps the fixtures loadable.

**Not run in the sandbox.** The sandbox this was written in has no container runtime, so the gated run skipped these tests there. The observations below are what the tests pin, read from the code. They count as verified once the gated run passes on a host with Docker, where each `today_` test passes and each `it.fails` test fails as expected.

## Probe 1: a staff password alone

`POST /api/sign-in` creates a full sign-in, `isTwoStep: false`, for any account with no TOTP secret (`src/server/auth/sign-in-routes.ts`, the `user.totpSecret !== null` branch). It never checks whether the account has a passkey. `loadSignedInAdult` (`src/server/auth/signed-in-parent.ts`) refuses that sign-in on every route behind `runAsSignedInAdult`, `runAsSignedInParent`, `runAsSignedInStaff`, `runAsSignedInAdmin` and `buildSignedInAdminCheck`, with 403 `second-factor-required`. `runAsSignedInUser` doesn't refuse it.

To list every route, the probe uses a second server on the same database with body validation switched off. Otherwise a schema 400 would hide what the sign-in check answers. Every route except `HEAD` is called once with no sign-in and once with the password-only sign-in. A route counts as needing a sign-in when the first call answers 401. It counts as opened when the second call's answer is neither 403 `second-factor-required` nor the same body the first call got.

For both `teacherAYears5And6` and `teacherBYear3`, the password-only sign-in opens exactly these 17 routes:

| Route                                                                       | What it lets the holder of the password do                                                               |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `GET /api/me`                                                               | Read who they are signed in as, with `needsSecondFactor: true`                                           |
| `GET /api/sign-in-methods`                                                  | See the account's password, passkeys and TOTP state                                                      |
| `GET /api/email-address`, `POST /api/email-address-checks`                  | Read the email address, and start changing it (H3, A4)                                                   |
| `PUT /api/password`, `POST /api/password`, `DELETE /api/password`           | Change, set or remove the password                                                                       |
| **`POST /api/totp-setups`, `POST /api/two-factor`**                         | **Turn on TOTP, which marks the sign-in two-step**                                                       |
| `DELETE /api/two-factor`                                                    | Turn TOTP off                                                                                            |
| **`POST /api/passkey-registration-options`, `POST /api/passkeys`**          | **Add a passkey, which marks the sign-in two-step**                                                      |
| `DELETE /api/passkeys/:passkeyId`                                           | Remove a passkey, within the last-second-factor rule                                                     |
| `POST /api/passkey-confirmation-options`, `POST /api/passkey-confirmations` | Prove the sign-in with a passkey the account already has, the intended way in for an established Teacher |
| **`POST /api/passkey-hand-offs`**                                           | **Make a QR hand-off, which adds a passkey on another device**                                           |

Every other route that needs a sign-in refuses it with 403 `second-factor-required`. That includes `GET /api/school-children`, `GET /api/parents`, `GET /api/schools`, `GET /api/teachers`, `GET /api/admin/families`, `GET /api/children/:childId/progress`, `POST /api/parents`, `POST /api/teachers`, `POST /api/people/:userId/invites` and `POST /api/people/:userId/password-resets`. So a staff password alone reads no Child's data directly. The routes in bold are what make it a takeover.

- `today_ opens Your account to an established Teacher's password alone, every route that adds a second factor included, and refuses every staff route for want of one`
- `it.fails`: `opens no route that adds a second factor to an established Teacher's password alone, so a Teacher with a passkey proves it before anything else`
- Documented, passing: `opens Your account and nothing more to the password of a Teacher with no second factor yet, as documented for a new Teacher`

## Probe 2: enrolling a second factor from that sign-in

1. Sign in as `teacherAYears5And6` with `PEN_TEST_TEACHER_A_YEARS5_AND6_PASSWORD` alone: 204, and a sign-in cookie.
2. `GET /api/school-children`, `/api/parents` and `/api/schools`: 403 `second-factor-required` each.
3. `POST /api/totp-setups`: 200 with a setup key. `POST /api/two-factor` with a code from it: 201 with ten recovery codes. The handler calls `markSignInTwoStep` on the sign-in that asked.
4. The same three routes: 200 each, and `/api/school-children` lists Ben (`childA1Year5`).
5. No email goes to the Teacher. Wizzaroo has no notice for TOTP turned on or a passkey added (`src/server/email/emails.ts`). The Audit Log records `two-factor.turned-on` (read from the code; the probe doesn't assert it).

A passkey does the same. `POST /api/passkey-registration-options` and then `POST /api/passkeys` with the attacker's own authenticator returns 201, and `insertVerifiedPasskey` is followed by `markSignInTwoStep`. A passkey added through the QR hand-off (`POST /api/passkey-hand-offs`, then `/api/passkey-hand-off-passkeys`) doesn't mark the computer's sign-in. It signs in by itself with `isTwoStep: true`, and that sign-in reads the same data.

For `teacherBYear3`, who has no second factor and was created 30 days before loading, the same steps open their Year 3 at School B (Eli, `childBYear3`). This is the documented new-Teacher path, but nothing bounds it in time.

Read from the code, not probed: once the attacker's TOTP is on, `countSecondFactors` is 2, so the same sign-in may `DELETE /api/passkeys/:passkeyId` the real Teacher's passkey. `PUT /api/password` then signs out every other session. A reset link afterwards still meets the attacker's TOTP, so the real Teacher can't get back in without the Admin.

- `today_ lets an established Teacher's password alone turn on TOTP, without telling them, and then read their Year Groups' Children`
- `it.fails`: `keeps an established Teacher's password-only sign-in away from their Year Groups' Children once it has turned on TOTP`
- `today_ lets an established Teacher's password alone add a passkey, on the computer or by the QR hand-off, and so reach their Year Groups' Children`
- `it.fails`: `keeps an established Teacher's password-only sign-in away from their Year Groups' Children once it has added a passkey`
- `today_ lets the password of a Teacher who has gone 30 days without a second factor set one up and reach their Year Groups' Children, as a new Teacher's first sign-in can`

## Probe 3: starting from a password reset link

1. `POST /api/password-reset-requests` for the Teacher's address. Wizzaroo emails a one-hour link to anyone with a confirmed address, staff included.
2. `POST /api/password-resets` with the token and a new password: 204. Every sign-in the account had is deleted, but TOTP and passkeys are kept.
3. Sign in with the new password. If the account has no TOTP, this is a full, not-two-step sign-in, and probe 2 follows: 201, then 200 on the staff routes.

For `teacherAYears5And6` and `teacherBYear3`, whoever controls the mailbox ends up holding the account's staff reach. For the Admin and `teacherAYear3`, who have TOTP, step 3 answers 202 and asks for a code, with no sign-in cookie. So the mailbox alone gets no further, and H1's reset clause is **refuted** for staff with TOTP.

- `today_ lets whoever holds a staff mailbox, for a Teacher with no TOTP, reset the password, turn on TOTP and read the Teacher's Year Groups' Children`
- `it.fails`: `keeps whoever holds an established Teacher's mailbox away from their Year Groups' Children, since a reset link can't prove the passkey they have`
- Refuted, passing: `still asks staff with TOTP for a code after a reset link, so the mailbox alone signs neither the Admin nor a Teacher in`

## Probe 4: starting from an accepted Invite

- **A new Teacher** (`POST /api/teachers` by the Admin, as a copied link): accepting the Invite sets a password and signs in with `isTwoStep: false`. The staff routes refuse that sign-in until it turns on TOTP, then serve School A's Year 5 (Ben). This is the documented path, so it is **confirmed as a documented decision**. Whoever holds the link, or the mailbox an emailed one goes to, becomes the Teacher, and #243 records that nothing bounds how long a Teacher can stay without a second factor.
- **An established Teacher with a password:** `POST /api/people/:userId/invites` answers 409, because `createInvite` refuses an adult who has a password. **Refuted.**
- **An established Teacher who signs in with a passkey alone:** once `teacherAYears5And6` has removed their password, the Admin can send them an Invite. Accepting it gives a not-two-step sign-in that turns on TOTP and serves their Year Groups. Taking an account over with an Invite belongs to H2 and A4. What A5 pins is the step it shares with probe 2: a sign-in that never proved the passkey the account has still enrols a new second factor. That is **confirmed**, under #242.

Tests:

- Documented, passing: `opens only Your account to a new Teacher who accepts the Admin's Invite, and their Year Groups' Children once they set up TOTP, as documented`
- Refuted, passing: `refuses the Admin an Invite for an established Teacher who still has a password`
- `today_ lets an Invite for an established Teacher who signs in with a passkey alone open a sign-in that turns on TOTP and reads their Year Groups' Children`
- `it.fails`: `keeps an Invite accepted for an established, passkey-only Teacher away from their Year Groups' Children once it has turned on TOTP`

## Probe 5: new Teacher or established?

ADR 0036's deliberate first sign-in **also opens for an established Teacher.** The server has no notion of a first sign-in.

- `POST /api/sign-in` asks for a second step only when there is a TOTP secret, so a staff account protected by a passkey alone gives a full session to its password.
- The enrolment routes run under `runAsSignedInUser`, which doesn't ask whether the account already has a second factor that the sign-in could have proved with `/api/passkey-confirmations`.
- Enrolling marks that same sign-in two-step.

So for a Teacher with a passkey and no TOTP, a password is as good as the passkey. So is a reset link, which needs only their mailbox. The documented exception was meant for a Teacher with nothing to prove. For staff with TOTP, password and reset alike stop at the code.
