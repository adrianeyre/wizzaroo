# D4: The query-construction sweep

> **Personal use only.** Wizzaroo is intended for your own personal use only. It is not intended for use with or by a school, teacher, parent or student. Only use it for yourself.

The findings note for scope issue #213 (D4). It names exploit chains, so it is kept private on the same terms as the PRD. How a finding is filed, triaged and verified is in [the findings workflow](../README.md).

D4 answers [H19](../../product-requirements-document/pen-testing.md#h19-query-construction-is-clean-sweep-it-anyway--low): query construction reads clean, so sweep every builder rather than trust one reading. The rules probed are the PRD's checks that every scope issue carries: "Odd input stops above the database: NUL bytes, numbers written as `0x10`, `1e3` or `1.5`, very long strings", and "Every refusal comes from a closed set. No route answers a well-formed request with a 500". The code is every `sql` template, `sql.raw`, `sql.identifier`, `orderBy`, filter and JSON path in `src/server`, and every request schema whose fields reach a query.

How a 500 reads to the caller is [H7](../../product-requirements-document/pen-testing.md#h7-unexpected-errors-return-the-failing-sql-and-its-parameters--medium), which I1 answers. D4 records which inputs reach Postgres and make it fail. Every 500 below answers with Drizzle's `Failed query: <SQL>\nparams: <values>`, so while H7 is open each one also returns its query and parameters.

## The sweep

Read at commit `fc74504`, every file in `src/server` except the tests and the migrations.

### `sql` templates

65 templates in 26 files. Each falls into one of three groups, and none puts a request value into the SQL text:

- **Constants and columns only** (57): the `/health` check, the check constraints in `schema.ts`, the two `lock table` statements (`owner/create-owner.ts`, `schools/school-routes.ts`), every `now()` and `now() + make_interval(… => ${lifetime})` with a module constant, the `isLive` and `hasPassword`-style booleans, the `array_agg` and `coalesce` columns (`auth/signed-in-parent.ts`, `people/people-routes.ts`, `bulk/bulk-families.ts`, `audit/audit-log-routes.ts`), the session sums in `children/child-progress.ts`, the `excluded.*` upsert in `children/room-showcases.ts`, and `false` and `'parent' = any(roles)` in `reach-rules.ts`.
- **A value from the caller's credential, bound** (1): `runWithinReach` (`reach.ts`) sets `wizzaroo.user_id`, `wizzaroo.family_id`, `wizzaroo.is_admin` and `wizzaroo.today` with `set_config` and bound values. The role name is a constant. The values come from the session or device row, never from the request.
- **A value from the request, bound** (4): the Audit Log's `${from}::date` and `${to}::date` (`audit/audit-log-routes.ts`), `payload ->> 'giftForChildId' = ${childId}` (`family-data/family-deletion.ts`), and `wizzaroo_can_visit_classmate_room(${childId}::uuid, …)` (`family-devices/classmate-room-routes.ts`). Each `childId` has passed a `uuid` format first. The dates are where D4-4 lives: bound, so no injection, but cast by Postgres after the schema has let through a year it can't hold.

The other three templates hold the `sql.raw` and `sql.identifier` calls below.

### `sql.raw` and `sql.identifier`

- `schema.ts`: `sql.raw(String(mostStarsInOneAward))` and `sql.raw(String(mostCoinsInOneAward))`, the constant 1000 from `src/curriculum/rewards.ts`, written into `star_awards_stars_check` and `family_chest_coin_awards_coins_check`.
- `pen-test-fixtures/seed-pen-test-fixtures.ts`: `sql.identifier(column.name)`, each column of a Drizzle table, in the seed's upsert. It is a command-line seed, not a route.

### Order and filters

Every `orderBy` in `src/server` names fixed columns: `admin/admin-routes.ts`, `audit/audit-log-routes.ts`, `auth/sign-in-methods-routes.ts`, `children/child-progress.ts`, `children/family-rewards.ts`, `family-data/family-export.ts`, `family-data/family-data-routes.ts`, `family-devices/classmate-room-routes.ts`, `family-devices/family-device-routes.ts`, `people/invites.ts`, `people/people-routes.ts` and `schools/school-routes.ts`. No `like` or `ilike` exists. The only filter a request shapes is the Audit Log's. The `inArray` lists are uuids that passed a `uuid` format (`play-event-routes.ts`) or normalised emails (`bulk/bulk-teachers.ts`, `bulk/bulk-families.ts`), all bound. `buildCandidateChildrenFilter` (`reach-rules.ts`) is built from the caller's credential.

### JSON paths

Two, both with constant keys: `payload ->> 'giftForChildId' = ${childId}` when a Child is deleted, and `group by payload ->> 'sessionId'` when time spent is summed. No route reads a JSON key a request names.

### H19's other claims

Read and not probed, since they aren't query construction: there is no `dangerouslySetInnerHTML` or `innerHTML` in `src`, no server-side `fetch` or `http.request` in `src/server`, and no `reply.redirect`. The CSV upload is a JSON string capped at 1,000,000 characters (`bulk/bulk-routes.ts`). `@fastify/static` is registered with `redirect: true`, which redirects a folder to its trailing slash. Whether that can be steered off-site is I1's, and noted for it.

## The probes

Every probe is in `src/integration.test.ts`, under `against a real Postgres › pen test D4: the query-construction sweep`. A refuted probe is a passing test. A confirmed one is an `it.fails` for the property that should hold, beside a `today_…` test pinning what happens now. Every `today_…` test also checks that each of its 500s answers with Drizzle's `Failed query:`, so the failure is Postgres refusing the input and not something else.

### `sql` templates

- `sql templates › binds every value a request carries into a template as a parameter, so quotes, comments and placeholders are stored as typed and run nothing`. `POST /api/sign-in` with `' or '1'='1` as both email and password, and with `parentA1`'s email followed by `' --`, answers 401 both times. `coParentA1` renames Ada and her Character `'); drop table children; --` (200). The Admin renames School B `School B'); delete from schools; --` in the town `$1 \ %_ "quoted" ::text` (200). `familyDeviceA1` saves an outfit named `'); delete from users; --` (204). Each is stored exactly as typed, no row count changes, and each is put back.

### `sql.raw` and `sql.identifier`

- `sql.raw and sql.identifier › builds every sql.raw and sql.identifier in src/server from a constant or a schema column, never from a request`. It reads every `.ts` file in `src/server` outside the tests and finds exactly the three calls above, so a new one fails this test until it is read.
- `… › holds the constants sql.raw writes into the award checks, so Postgres itself refuses one more Star or Coin than one award may give`. As the owner, 1001 Stars or Coins is `23514`, and 1000 is stored.

### Order and filters

- `dynamic order and filters › never lets a query string choose a list's order: ordering parameters change no list, and the Audit Log refuses them`. `/api/children` and `/api/family-devices` as `coParentA1`, and `/api/schools`, `/api/teachers`, `/api/parents`, `/api/admin/families` and `/api/admin/deletion-requests` as the Admin, answer byte for byte the same with `orderBy`, `sort`, `order` and `direction` set (one carrying `; drop table children`). The Audit Log answers 400.
- `… › refuses an Audit Log action outside the closed list, and a date that isn't one, before the query`. An `action` carrying `' or '1'='1`, a `from` carrying `'::date or true --`, a `to` of 30 February and a `from` ending in `%00` are each 400.

### JSON paths

- `JSON paths › matches a gift's giftForChildId exactly when the Admin deletes a Child, and refuses a giftForChildId or Child id that isn't a uuid`. A probe Child is added to Family A1, with two gifts from Ada, one to the probe Child and one to Ben. The Admin deletes the probe Child (204): the gift to them is gone and the gift to Ben is kept. A device upload whose `giftForChildId` is `' or '1'='1`, and the Admin deleting a Child by that id, are each 400.

### D4-1: a NUL byte reaches Postgres from every text field

Postgres can't store `\u0000` in `text` and refuses it in `jsonb`. No request schema or reader in `src/server` refuses it first: a `pattern` of `\S` needs only one other character, `normaliseEmail` and `.trim()` leave it, and `isEmailAddress`'s `[^\s@]` allows it.

- `hostile input into every field that reaches a query › refuses a NUL byte in every text field that reaches a query with a 400, before the database` (`it.fails`), beside
- `… › today_sends a NUL byte in a text field on to Postgres, which refuses it, so 11 fields on 9 routes answer 500 with the failing query, sign-in among them with no credential`, now `… (regression)`. **#294**, _fixed, unverified (#294)_

### D4-2: an email address has no length limit

Every name, nickname and School field has a `maxLength`. No email field does, at any route: sign-in, a reset request, an email change, a new Parent or Teacher, or a row of either bulk upload. A real mailbox is at most 254 characters.

- `… › answers a very long email address at sign-in as it answers any wrong one`. A 4,017-character address is 401, the same refusal as any wrong email, so a lookup with one is harmless.
- `… › refuses an email address longer than any mailbox can have with a 400 on every route that keeps one` (`it.fails`), beside
- `… › today_keeps a 4,017-character email address as a pending email change, and answers a staff member's new Parent with one with a 500 and the failing query`. `coParentA1`'s change to it is 204, the check row holds all 4,017 characters, and a confirmation email is sent to it. The Admin's new Parent with it is 500: the address is too big for the unique index on `users.email` (`54000`). **#295**, _fixed, unverified (#295)_

_Fixed, unverified (#295):_ `isEmailAddress` (`src/server/auth/email-address.ts`) now refuses an address longer than 254 characters. Every place that keeps an address reads it there first: an email change, a new Parent or Teacher, a row of either bulk upload and the owner seed. So a long address gets the same 400 as one that isn't an address, "That isn't an email address", before any query, and a CSV row with one is a row problem at preview and upload. Sign-in and reset requests only look an address up, so they still answer as they do for any unknown one. The `it.fails` now passes as a plain `it`, and the `today_` test is `… › refuses a 4,017-character email address as it refuses one that isn't an address, so no pending email change keeps it, a staff member's new Parent with one is refused, and a CSV row with one is a row problem at preview and upload (regression)`.

Read from the code and not probed: confirming that email change would hit the same index and answer 500, so the address can't become the account's. A row in a bulk upload with one would be accepted by the preview and fail the upload.

### D4-3: `"Infinity"` passes every integer range check

Fastify's Ajv coerces a string to a number where the schema says `integer`. Ajv's generated check skips `minimum` and `maximum` for a value that isn't finite, so `"Infinity"` (or `"1e400"`) is coerced to `Infinity` and passes, however tight the range. A bare JSON `1e400` parses as `Infinity` too, but Ajv's `integer` check refuses it when nothing was coerced, so only the string form gets through an integer field.

- `… › refuses an integer written as "Infinity" with a 400 on every integer field that reaches a query` (`it.fails`), beside
- `… › today_lets an integer written as "Infinity" past every range check, so the Audit Log page and a Star award answer 500 with the failing query, and a daily limit and an activity's seconds are stored as null`. **#296**, _fixed, unverified (#296)_

_Fixed, unverified (#296):_ once a route's schema has coerced a request, a `preHandler` hook on every route (`src/server/non-finite-numbers.ts`) looks through its body, query string and path parameters, and answers any number that isn't finite with a 400 and "That number is too big for Wizzaroo", before the handler runs. That covers `"Infinity"`, `"-Infinity"` and `"1e400"` in every integer field, a play event's payload included, and a bare JSON `1e400` in a `number` field. `0x10`, `1e3` and `?page=2` are still coerced as before. The `it.fails` now passes as a plain `it`, and the `today_` test is `… › refuses an integer written as "%s" with the one closed refusal before any query, so the Audit Log page and a Star award answer 400, and no daily limit or activity's seconds is stored (regression)`, run for each of `Infinity`, `-Infinity` and `1e400`.

| Caller           | Route and field                                                | Schema              | Today                                         |
| ---------------- | -------------------------------------------------------------- | ------------------- | --------------------------------------------- |
| `admin`          | `GET /api/admin/audit-log-entries` `page`                      | 1 to 10,000         | 500: `offset` is not a `bigint`               |
| `admin`          | `POST /api/admin/children/:childId/star-awards` `stars`        | 1 to 1000           | 500: not an `integer`                         |
| `coParentA1`     | `PUT /api/children/:childId/limits` `dailyMinutes`             | 5 to 600, or `null` | 200, stored as `null`, which means no limit   |
| `familyDeviceA1` | `POST /api/play/events` an activity's `secondsSpent` (`jsonb`) | 0 or more           | 204, stored as `null` where an integer is due |

`JSON.stringify` writes `Infinity` as `null`, so a `jsonb` column keeps a value the schema would have refused. Read from the code and not probed, the same holds for a Family Chest award's `coins`, a Child's `birthYear` (`"-Infinity"` makes the Child's Year `Infinity`, so the insert fails), and a question's `wrongAnswerCount` and `millisecondsTaken` in an upload. Mastery sums `null` seconds as 0, so no replay was seen to break. A Parent can choose no limit anyway, and a device writes only for its own Family, so nothing here crosses a boundary: low.

- `… › turns 0x10 and 1e3 into the integers 16 and 1000 before the query, and refuses 1.5` (refuted). `page=0x10` answers page 16 and `page=1e3` page 1000; `page=1.5` is 400. A Star award of `"0x10"` stores 16 and a bare `1e3` stores 1000; `1.5`, `"1.5"` and `1001` are 400. Ajv also takes `0b11`, `0o17` and padded `" 16"`. Each becomes an ordinary integer inside the field's range before any query, so none is a weakness.

### D4-4: a year Postgres doesn't have

Ajv's `date` and `date-time` formats accept any four-digit year, 0000 included. Postgres has no year 0 and refuses it (`22008`).

- `… › refuses with a 400 a date or time the schema lets through but Postgres can't hold` (`it.fails`), beside
- `… › today_lets a date or time in the year 0000 through the schema, so the Audit Log's filters and a Family Device's upload answer 500 with the failing query`. `from=0000-01-01` and `to=0000-01-01` on the Audit Log, and `familyDeviceA1` uploading a session that started at `0000-01-01T00:00:00Z`, each answer 500. **#297**, _fixed, unverified (#297)_

_Fixed, unverified (#297):_ the server narrows Ajv's own `date` and `date-time` formats when it builds its validator (`src/server/held-dates.ts`). A `date` must be in year 1 or later, and a `date-time`, once its offset is applied, must fall from year 1 to year 9999 in UTC. So the year 0000, and `9999-12-31T23:59:59-23:59`, which an offset carries into the year 10000, are refused with a 400 by the schema of every route that takes either format, before any query. The `it.fails` now passes as a plain `it`, and the `today_` test is `… › refuses in the schema a date or time in the year 0000, or one an offset carries into the year 10000, so the Audit Log's filters and a Family Device's upload answer 400 and keep no event (regression)`.

An event's `localDate` takes the same format but is kept inside `jsonb` and never cast, so it is stored. What a device's dates mean is F3's (H10). A year after 9999 can't be typed, since the formats take four digits; an offset can still carry `9999-12-31T23:59:59-23:59` into the year 10000, which was not probed then and is refused since #297's fix.

**When:** the probes run in the gated suite, not on the shared pen-test deployment. Each run loads the fixtures from a seed of the test's own into a database of its own (`pen_test_d4`) in the suite's Postgres container, signs the fixtures in with the credentials package's harness (`signInAsPenTestFixture`) against a server of its own, and the container is destroyed when the run ends. So the times are those of each gated run, and nothing a tester on the deployment sees is changed.

**What they change, in that database,** beyond [the expected state changes](../credentials-package.md#expected-state-changes):

- Ada and her Character, and School B, are renamed and named back.
- An outfit with a hostile name is uploaded for Ada and kept.
- Ada's limits are set with `"Infinity"` and put back; the activity uploaded with it is deleted.
- Ada gets Star awards of 16 and 1000, from the `0x10` and `1e3` probe.
- A probe Child is added to Family A1 and deleted by the Admin, with the gift to them; the gift to Ben is deleted after.
- `coParentA1` has pending email changes to addresses that can't be delivered.
- Failed sign-ins for odd emails are in the Audit Log.

A 500 rolls its transaction back, so the probes that answer 500 change nothing. No fixture is loaded again.

To reproduce a probe on the deployment instead, sign in with the harness as the fixture named above. Every request and body is in the test, and each finding's steps say which `PEN_TEST_…` variable it needs.
